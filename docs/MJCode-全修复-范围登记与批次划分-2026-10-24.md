**S7 清单（代码级 10 个）**：`memory-m4-hardening` `memory.test.js` `orchestrator-invoke` `tools-cwd` `mcp-handshake` `memory-team` `memory-scope` `memory-salvage` `orchestrator.test.js` `memory-mem-command`。
**改法（两行式，实测三种写法后确定）**：
```js
process.exitCode = process.exitCode || 0;
setTimeout(() => process.exit(process.exitCode || 0), 0);
```
实测（`node -e "Promise.reject(new Error('x')); …"`，主理人独立复算）：
| 写法 | exit | 能否抓到浮动 rejection |
|---|---|---|
| `process.exit(0)`（原样） | 0 | ❌ |
| `process.exit(process.exitCode \|\| 0)`（我原先的单点改法） | **0** | **❌ 无效**——`exit()` 同步截断，rejection 来不及上报 |
| `process.exitCode = 0`（仅赋值） | 1 | ✔ 但依赖自然退出，开放句柄会挂住 |
| **两行式（采纳）** | **1** | ✔ 且保留强制终止语义，不依赖自然退出 |
> 这条订正是编码者实测发现的：单点改法的**证明力为零**——若验收判据是「插浮动 rejection ⇒ exit 1」，单点改法必然红。所以统一按两行式返工（含已按单点改法改过的 9 个）。
> 验收：改后单跑 `exit=0` 且条数不变；在 `memory-scope` 与另 1 个文件上插浮动 rejection，须 `exit=1`。
> 计数订正（2026-10-24）：先前记 11 个是**错的**——`docs-consistency.test.mjs:21` 的命中在**注释**里（`// 改前写法：…process.exit(0)`）。`rg -l` 不排除注释即计数，就是本项目反复出现的「正则扫注释」假阳。以 **10** 为准。
> **长期项（不排期）**：`process.exit()` 会截断未完成异步，是「浮空 promise 来不及上报」的根因；彻底做法是全改 `process.exitCode`，但全仓 **197** 个套件用到它，属独立重构，不在本轮范围。

> **第一次修正**：原判据「声明条数 == 汇总总条数」是空过判据（`total++` 在 `check` 入口）。
> **第二次修正（2026-10-24 22:3x）**：原拟「在 `run-all` 里按汇总行做时序断言」**撤销**——覆盖率 = 你能枚举的方言数，漏一种那批套件就静默不设防。实测方言 **≥6 种**：`${pass}/${total} 通过`、`PASS：N/M 项通过`、`pass 通过 / fail 失败`、`${pass} passed, ${fail} failed`、`crash durability: ${pass}/8 checks passed`，以及各套件自定义措辞。

合法判据为以下 1+2 必做、3 辅助：
1. **静态属性检查（主判据，与输出方言无关、零覆盖缺口）**：分三档，见下方「落地口径」——不能写成「所有 `check` 必须 async」。
2. **进程级兜底：改为「测试侧 preload」，`--unhandled-rejections=strict` 作废**（这条被推翻过两次，以下是实测终态）。
   - **strict 在本仓「净收益为零」的完整证明**（三步，缺一步都会有反例）：
     1. 无 listener 时：默认行为已经是 `exit=1`（实测 `node -e 'Promise.reject(...)'` → 1）⇒ strict 无增量；
     2. 有 listener 时：本仓库唯一的 listener 来源是 `main.js`（UR + UE 双 handler）⇒ strict 被 `:476 uncaughtException` 吸收 ⇒ `exit=0`；
     3. 有没有「只有 UR handler」的套件？`rg -l unhandledRejection test/*.test.*` 命中 `diagnostics` / `workerPool` **两处，但都是注释与字符串参数，不是 `process.on(...)` 注册** ⇒ 该形态不存在。
     ⇒ 结论：**删掉 strict 判据**，但把这三步留在文档里，避免下一轮再试一次。
   - **替代杠杆（采纳）**：`run-all` spawn 套件时 `--require <test/helpers/unhandled-preload.cjs>`，preload 里注册自己的 `unhandledRejection` 并**直接 `process.exit(1)`**：
     ```js
     process.on('unhandledRejection', (reason) => {
       console.error('[test-preload] 未捕获的 Promise 拒绝 → 判定失败:', String(reason?.message || reason));
       process.exit(1);
     });
     ```
     实测：无产品 handler ⇒ `exit=1`；**带上产品那两个 handler（真实形态）⇒ 仍 `exit=1`**，且打印 `[test-preload]`（preload 的 listener 先注册先执行，直接终止，`uncaughtException` 来不及吸收）。
   - 优点：①不受 UE 吸收影响；②一处落地全仓生效；③覆盖 strict 救不了的那几个套件；④不改产品、不改套件。
   - **preload 内必须用 `process.exitCode = 1`，不要 `process.exit(1)`**：后者会截断 handler 队列、丢掉后续诊断输出。
   - **⚠ 关键耦合（实测，缺这条 preload 就是空门禁）**：preload 只置 `exitCode`，若套件自己用 `process.exit(0)` 或 `process.exit(pass === total ? 0 : 1)` 结算，会把 1 覆写掉。主理人复算：

     |---|---|
     | preload 置码 + 套件 `process.exit(0)` | **0（被覆写，白干）** |

     | # | 场景 | 期望 |
     |---|---|---|

     ```js
     const realExit = process.exit.bind(process);
     process.exit = (code) => {
       const n = Number(code) || 0;
       if (n !== 0) return realExit(n);                                        // 非 0：同步，零额外执行
       setTimeout(() => realExit(process.exitCode ? process.exitCode : 0), 0); // 只对 exit(0) 复核在途失败
     };
     ```
     主理人实测：
     | 场景 | 一律延迟 | **条件式（采纳）** |
     |---|---|---|
     | 同 tick 在途失败 + `exit(0)` | 1 | **1 ✔** |
     | 无失败 + `exit(0)` | 0 | **0 ✔** |
     | `exit(1)` 后紧跟 `console.log` | 会打印（多跑一轮） | **不打印 ✔（同步）** |
     | `exit(0)` 后紧跟 `console.log` | 打印 | 打印（仅剩代价，只落在 0 路径） |
     ⇒ 爆炸半径从 37 降到 **2**（详见下条审计）；35 处实参恒为字面 `1` ⇒ 零额外执行。
     > **审计口径（关键）**：「exit 后还有可执行代码」必须按**祖先链**判（任一祖先不是其所在数组最后一项），不能按「同一语句块内」——后者只得 1 处、漏 36 处。AST/espree 全量：`process.exit(` 语句 **265** 处，祖先链口径 **37** 处，其中 35 处实参恒非 0、**2 处可能为 0**（`plugin-bypass-hardening.test.js:20`、`sandbox-linux.test.mjs:290`，均已审：后续只是 `}` / `run().catch(…)`，良性）。
     > **落地前必须审的一项代价**：延迟包装让 `process.exit()` 变成异步 ⇒ `exit` 之后的语句会多跑一轮。全仓约 **111 处** `process.exit(` 调用，须逐个确认「exit 后是否还有副作用语句」（文件末尾/IIFE 尾部无害；若 exit 后紧跟写库/写盘则必须改写）。这一项没做完，preload 不得上线。
     > **审计结果（两版口径，后一版为准）**：`process.exit(` 语句数 **265–267**（两个统计口径差 2，属 `process['exit']`/可选链计法差异，不影响结论）。
     > - ❌ **同「块」口径（错，已废弃）**：`has-following` 仅 1 处（`model-windows-parity.test.mjs:61` 的 `exit(1); return;`）——**这是假绿灯**：`exit` 在 `if` 块内、`if` 块是其所在数组最后一项，但 `if` 之后还有几十条语句会执行。现成反例 `tools-cwd.test.js:66`：`if (…) { …; process.exit(1); }` 之后仍有 6 段工具调用。
     > - ✅ **祖先链口径（对）**：任一祖先不是其所在数组最后一项 ⇒ **37 处**。其中 **35 处实参恒为字面 `1`**（条件式下同步退出、零额外执行）、**2 处可能为 0**（`plugin-bypass-hardening.test.js:20`、`sandbox-linux.test.mjs:290`，均已审：后续只是 `}` / `run().catch(…)`，良性）。
     > ⇒ 结论：**条件式延迟可在全仓铺，爆炸半径 2 处且良性**；但**审计脚本必须用祖先链口径**，否则永久漏 36 处 = 空门禁。审计脚本自带反向用例：`if (x) { process.exit(0); } sideEffect();` 必须报 `has-following`。
     > 反向用例（preload 侧）四条全过：同 tick 在途失败→1、无失败→0、`exit(1)`→1、`exit(pass===total?0:1)`+在途失败→1。
     > 落地前提（**必须做，否则是空门禁**）：带 preload 跑一次全量，与 `297/294/0/3` 对比；出现新红要逐个判「真缺陷 vs 良性」，不得直接调宽阈值。
   - 与 AST 的关系是**互补**：AST 禁写法，preload 管运行时被吞。
3. **辅助（不单独成门禁）**：以计分锚点定位，**锚点之后不得出现失败特征行**（`[FAIL]` / `❌ ` / `FAIL `）。**不能**写成「汇总行必须是输出最后一段」——合法情形实测存在：`modal-keyboard-guard.test.mjs` 在计分行后还有一行 `⚠ 真机待验：…`；抽样 19 个套件里 4 个（21%）在计分行后还有 `[agent] …` / `[localStore] …` 这类异步诊断日志。若照「不得有任何后续输出」写，立刻假红 21%。

## 4. 修复纪律（违反即回退）

1. **禁止改测试期望值让测试变绿**。若修复导致旧测试变红，先判「该测试是否把缺陷固化成预期」，判断依据写进报告，不得直接改。
2. **禁止改阈值**（`BASELINE`、`max-warnings`、ratchet 上限）。改阈值等于消灭证据。
3. 单条改动 ≤ 200 行；只改必要文件；不做顺手重构。
4. 每条必须两段实测：修复前（证明问题存在）与修复后（证明已好），命令可复制。
5. 编码与验证分离：实现由编码工程师做，判定由独立测试工程师做，主理人只汇编。
6. 不提交 git，由主理人统一提交。
7. **测量工具自身出错，一律先修工具再修产品**。批次 1 期间已发生三次「工具制造失败」：① 干净检出漏链 `desktop/renderer/node_modules` ⇒ 11 套件假红；② `render-smoke.mjs` 往 `renderer/src` 写 `__i18n_probe_*.jsx` 被并发进程删除 ⇒ `legacy-ledger` 19/20 与 `lint-gate` ENOENT 假红（S5，待修）；③ 同步版 `check()` 让 async reject 变成 unhandled rejection ⇒ 先打印「全通过」再崩（已修，批次 1 提交内含 `async check`）。
8. **全量测试必须单一 owner：同一时刻只允许一个 `npm test`**。`test/render-smoke.mjs:163` 会往 `renderer/src` 写 `__i18n_probe_*.jsx`，两个 run-all 并发时后启动者会删掉先启动者的探针文件 ⇒ `legacy-ledger` 现算与 `lint-gate` 枚举失真，报 `ENOENT`。这**不是**「变异撞扫描」——2026-10-24 曾把该假红错误归因为并行变异，后经验证方证据订正。根治项 S5（探针改 `os.tmpdir()` 或 esbuild `stdin` 零落盘）待做。
9. **变异还原必须早于任何 `git add`**。批次 1 曾出现提交时刻撞进变异窗口：虽然事后比对确认提交进去的是定稿版（无泄漏），但这是运气。纪律：变异 → 还原 → 校验 → 才允许提交。
10. **校验锚点要说清是哪一种哈希**：`shasum -a 1 <file>` 是文件内容明文 SHA-1；`git rev-parse HEAD:<path>` 是 blob SHA（含 `blob <len>\0` 头，与前者不同值）。两者不可混比——批次 1 收口时出现过把明文 shasum 称作「blob sha」的表述，若后人拿 `rev-parse` 去比对会误判为不一致。当前实测：`main.js` 明文 `2e3f39e1…` / blob `a60b1e49…`。
11. **`exit=1` 是必要但不充分条件**（2026-10-24 对照实验实证）：把 `async function check` 改回 `function check` 后，同一条必然 reject 的探针用例会先被记为 `[PASS]`、汇总打印 `11/11 通过`、**之后**才崩，退出码**同样是 1**。因此「async 断言是否真的 fail-loud」必须同时满足三条，缺一不可：
    - 汇总行是 `10/11`（含失败条数），**不是** `11/11 通过`；
    - 输出里出现该条的 `[FAIL]`，且出现在汇总行**之前**；
    - 不存在「先打印全通过再崩」的顺序。
    > 推广到一般：任何以退出码为唯一判据的验收，都无法区分「断言失败」与「断言被吞后进程崩溃」。
12. **判据不得建立在「刚刚被我们关掉可见性」的通道上**（2026-10-24 主理人自犯）：同一批里给探针加了 `.gitignore`，而 S5 的检测判据恰是 `git status --porcelain` ⇒ 判据当场退化为恒真（实测盘上 2 个残留仍判「0 行」）。规则：**「防泄露」与「检测残留」是两条互斥通道，改其中一条必须复核另一条是否失效**；检测优先走不经 git 的文件系统直查（`find` / `ls`），只有需要「是否入库」时才用 `git ls-files`。
13. **「失败必须从汇总里扣掉」要当验收判据用，不只是口径**：修测试假绿时，合格判据不是「打印了 FAIL」也不是「exit≠0」，而是**汇总计数少一条**（如 `12/13` 而非 `13/13`）——它抓的是「打印 FAIL 但计数仍 +1」这种仍会骗人的形态。配套两条实现陷阱：① `forEach` 里的 `await` **不串行**，须改 `for…of`；② 顶层 `import().then(m => {…})` 里调用 `await check()` 时，`.then` 回调必须声明 `async`，否则汇总可能在断言完成前打印。
14. **变异/探针的还原一律用内容快照，禁止在有未提交改动的文件上 `git checkout --`**（2026-10-24 险情）：`git checkout -- <file>` 恢复的是 **HEAD**，不是「变异前状态」。当工作区里有别人（或自己前一步）的未提交改动时，它等于把在途工作当垃圾清掉——本轮验证方对 RB-2 的三处未提交修复执行了 checkout，所幸编码者随后又写回，实际未丢（已核 `await check` 计数 13/11/17 齐全）。规则：变异前 `cp <file> /tmp/<x>.snap && shasum -a 1 <file> > /tmp/<x>.sha`，还原用 `cp` 回写 + `shasum -c` 校验；只有 `git status --porcelain -- <file>` 为空时才允许 `git checkout --`。
15. **汇总行前缀也要可信**：`console.log('\nPASS：${pass}/${total} 项通过')` 在失败时仍打印 `PASS：`——计数对但前缀撒谎（`message-schema.test.js:131` 实测）。须写成 `${fail === 0 ? 'PASS' : 'FAIL'}：…`。凡是「固定前缀 + 动态计数」的汇总行都在此列。
16. **交付指纹只在「最后一次编辑之后」取，且由提交方在提交前扫一遍**。实测教训：编码者给的三指纹里 `message-schema` 是 `1ac41b6c…`，但随后落了一笔前缀修正，磁盘已变 `9e80b126…`；若拿旧指纹当「交付锁」，会把正常编辑误判成「被外部篡改」，或把新修正漏掉。规则：提交前对目标文件跑 `git hash-object` 并写进提交说明/报告；验收方记录**自己实际跑的那份**哈希。
17. **「无 `assert.*` 增删」是成本接近零的「未弱化测试」判据**：`git diff <base> <head> -- <test file> | grep -cE '^[+-].*assert\.'` 应为 0。它专抓「把断言改软/删掉换取变绿」，一行命令即可，建议列为所有测试改动的必查项（本批三个文件实测均为 0）。
18. **`git add` 只用显式路径，禁止 `-A` / `.`；提交前 `git show --stat` 自查**（2026-10-24 主理人自犯）：新增模块 `main/tools/artifactProduct.js` 被一次 `git add -A` 带进了「只改文档」的提交 `fc8b3f4`，导致后一个产品提交 `a5fdb51` 的 `--stat` 里看不到它、排查时误以为漏提交。功能无影响（两者同处历史），但**提交语义被污染，二分定位失效**。
19. **窗口纪律包含主理人自己**：全量跑期间我不得改 `docs/`——`doc-fact-check` 会在跑中读取 `MJCode-技术设计文档-2026-10-17.md`，主理人写文档同样能制造假红。并发污染不是「别人」的问题。
20. **实验室少一个变量，结论就只能限定在那个形态**（2026-10-24 同一坑连踩三次）：① 只测「同步 `check()` + async 回调」就断言「`exit=1` 可作 fail-loud 判据」——漏了产品 handler；② 只测「单 `unhandledRejection` handler + `strict`」就断言 strict 有效——漏了 `main.js:476` 的 `uncaughtException` 吸收器；③ 只测 `tools-cwd`（恰是 2 个有 handler 的之一）就外推 10 个套件的行为。规则：**结论必须带「在什么形态下成立」的限定语**；跨形态外推前，先把真实形态的变量补齐（本仓库的真实形态 = UR + UE 双 handler）。
21. **判据表必须标「时序」**（2026-10-24 第四次同类）：同一断言在「失败已上报」与「失败仍在途」两种时序下结论相反——
    - `Promise.reject(x); setTimeout(()=>process.exit(0),5)` ⇒ 同步包装可得 `exit=1`；
    - `Promise.reject(x); process.exit(0)`（同一 tick）⇒ 同步包装只能得到 `exit=0`，必须**延迟一宏任务**再退出才拦得住。
    只写结果不写时序，下一个人会拿错形态反推，把「漏检」读成「通过」。

## 5. 批次 2/3 的前置裁定（主理人决定，实施方按此执行）

  4. 档位表若有第二份副本（renderer / 文档 / 审批表），必须同步，并加「两份表同值」断言。

### 5.2 P0-5 一成员失败整组 failed

- **裁定（语义）**：新增组级状态 `partially_delivered`——部分成员完成时，产出的东西必须保留并可交付，同时给出「失败成员清单 + 未覆盖任务清单」。组状态不得因为单个成员失败而整体置 `failed`。
- **裁定（重试）**：`maxRetry` **默认值维持 0，本轮不改**。理由：把默认重试从 0 提到 1 会改变成本模型（每个失败成员多一次全量模型调用），属于需要在实测分布上定的阈值，不能凭直觉调。本轮只做「编排组可显式传 `maxRetry`」，默认行为不变。
- **判据**：注入一个必失败成员 ⇒ 其余成员产物保留、组状态为 `partially_delivered`、清单完整；且整改后 `maxRetry` 缺省仍是 0（用断言钉住，防止后续被顺手改掉）。
