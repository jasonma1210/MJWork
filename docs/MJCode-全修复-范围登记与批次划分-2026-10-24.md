**S6 验收（方案已两次修正，最终版）**：
> **第一次修正**：原判据「声明条数 == 汇总总条数」是空过判据（`total++` 在 `check` 入口）。
> **第二次修正（2026-10-24 22:3x）**：原拟「在 `run-all` 里按汇总行做时序断言」**撤销**——覆盖率 = 你能枚举的方言数，漏一种那批套件就静默不设防。实测方言 **≥6 种**：`${pass}/${total} 通过`、`PASS：N/M 项通过`、`pass 通过 / fail 失败`、`${pass} passed, ${fail} failed`、`crash durability: ${pass}/8 checks passed`，以及各套件自定义措辞。
> 附带订正：「有 1 个套件完全无计分行」不成立——`test/crash-durability.test.mjs:154` 有 `console.log(... ${pass}/8 checks passed)`，属第 6 种方言。

合法判据为以下 1+2 必做、3 辅助：
1. **静态属性检查（主判据，与方言无关、零覆盖缺口）**：各套件里的 `check` 必须是 `async`，且**所有调用点都 `await`**。这正是本 bug 的直接形态——同步 `check()` 让 async reject 变成 unhandled rejection。
2. **进程级兜底**：`run-all` spawn 各套件时显式加 `--unhandled-rejections=strict`。Node 默认已 throw，钉住它挡的是「有人用 `NODE_OPTIONS` 改成 `warn`/`none`」——那是唯一会让 exit 变 0、真正骗过 CI 的路径。注意：handler 要挂在**套件进程内**的公共 check helper 上，挂 `run-all` 抓不到子进程内的 unhandled rejection。
3. **辅助（不单独成门禁）**：套件 stdout 出现失败特征行（`[FAIL]` / `❌ ` / `FAIL `）⇒ 该套件 exit 必须非 0。
> 门禁自身要有反向用例：把任一 `await` 删掉必须红；把 `--unhandled-rejections` 改成 `warn` 必须红。
> **反向用例的实现约束**：S5/S6 判定脚本必须接受 `--root <dir>` 参数，反向夹具建在 `os.tmpdir()`；**禁止「改真实套件 → 跑 → 还原」**——那样反向测试自己就成了违规者，与门禁要检测的东西冲突。
> **原「(A) 要求 2 个套件补标准汇总行」的决策随之作废**——既然不再按汇总行锚定，补汇总行既不解决覆盖率也不必要。

**批次 3 的 6 条 P1 为什么合并成一批**：全部是「改配置 / 补字段 / 加一次 rename」量级，单条改动 < 50 行，但每一条都能单独验证；合并派发只为减少往返，验收仍逐条。

1. **禁止改测试期望值让测试变绿**。若修复导致旧测试变红，先判「该测试是否把缺陷固化成预期」，判断依据写进报告，不得直接改。
2. **禁止改阈值**（`BASELINE`、`max-warnings`、ratchet 上限）。改阈值等于消灭证据。
3. 单条改动 ≤ 200 行；只改必要文件；不做顺手重构。
4. 每条必须两段实测：修复前（证明问题存在）与修复后（证明已好），命令可复制。
5. 编码与验证分离：实现由编码工程师做，判定由独立测试工程师做，主理人只汇编。
6. 不提交 git，由主理人统一提交。
7. **测量工具自身出错，一律先修工具再修产品**。批次 1 期间已发生三次「工具制造失败」：① 干净检出漏链 `desktop/renderer/node_modules` ⇒ 11 套件假红；② `render-smoke.mjs` 往 `renderer/src` 写 `__i18n_probe_*.jsx` 被并发进程删除 ⇒ `legacy-ledger` 19/20 与 `lint-gate` ENOENT 假红（S5，待修）；③ 同步版 `check()` 让 async reject 变成 unhandled rejection ⇒ 先打印「全通过」再崩（已修，批次 1 提交内含 `async check`）。
8. **全量测试必须单一 owner：同一时刻只允许一个 `npm test`**。`test/render-smoke.mjs:163` 会往 `renderer/src` 写 `__i18n_probe_*.jsx`，两个 run-all 并发时后启动者会删掉先启动者的探针文件 ⇒ `legacy-ledger` 现算与 `lint-gate` 枚举失真，报 `ENOENT`。这**不是**「变异撞扫描」——2026-10-24 曾把该假红错误归因为并行变异，后经验证方证据订正。根治项 S5（探针改 `os.tmpdir()` 或 esbuild `stdin` 零落盘）待做。
9. **变异还原必须早于任何 `git add`**。批次 1 曾出现提交时刻撞进变异窗口：虽然事后比对确认提交进去的是定稿版（无泄漏），但这是运气。纪律：变异 → 还原 → 校验 → 才允许提交。
10. **校验锚点要说清是哪一种哈希**：`shasum -a 1 <file>` 是文件内容明文 SHA-1；`git rev-parse HEAD:<path>` 是 blob SHA（含 `blob <len>\0` 头，与前者不同值）。两者不可混比——批次 1 收口时出现过把明文 shasum 称作「blob sha」的表述，若后人拿 `rev-parse` 去比对会误判为不一致。当前实测：`main.js` 明文 `2e3f39e1…` / blob `a60b1e49…`。
11. **`exit=1` 是必要但不充分条件**（2026-10-24 对照实验实证）：把 `async function check` 改回 `function check` 后，同一条必然 reject 的探针用例会先被记为 `[PASS]`、汇总打印 `11/11 通过`、**之后**才崩，退出码**同样是 1**。因此「async 断言是否真的 fail-loud」必须同时满足三条，缺一不可：
    - 汇总行是 `10/11`（含失败条数），**不是** `11/11 通过`；
    - 输出里出现该条的 `[FAIL]`，且出现在汇总行**之前**；
    - 不存在「先打印全通过再崩」的顺序。
    > 推广到一般：任何以退出码为唯一判据的验收，都无法区分「断言失败」与「断言被吞后进程崩溃」。
12. **判据不得建立在「刚刚被我们关掉可见性」的通道上**（2026-10-24 主理人自犯）：同一批里给探针加了 `.gitignore`，而 S5 的检测判据恰是 `git status --porcelain` ⇒ 判据当场退化为恒真（实测盘上 2 个残留仍判「0 行」）。规则：**「防泄露」与「检测残留」是两条互斥通道，改其中一条必须复核另一条是否失效**；检测优先走不经 git 的文件系统直查（`find` / `ls`），只有需要「是否入库」时才用 `git ls-files`。

## 5. 批次 2/3 的前置裁定（主理人决定，实施方按此执行）

### 5.1 P0-1 沙箱「可写 + 联网」中间档

- **裁定**：新增一个独立能力档 `workspace-write-net`（工作区可写 + 允许出网）。**默认档不变**，仍为现状的 `workspace-write`（禁网），fail-closed 方向不动。
- **理由**：审计指出的痛点是「没有中间档，只能二选一到 `full-access`（连文件隔离一起放弃）」。补中间档是增加一个更小的权限集合，不是放宽默认。
- **硬要求**：
  1. 该档必须**显式切换**才生效，不得由任何自动推断打开；
  2. 沙箱拒绝网络时，错误信息必须**明确标注是沙箱拦截**（不是裸 `Operation not permitted`），否则用户无法判断是网络问题还是策略问题；
  3. 不得与该档同时放弃文件隔离（这是它相对 `full-access` 的全部价值）；
  4. 档位表若有第二份副本（renderer / 文档 / 审批表），必须同步，并加「两份表同值」断言。

### 5.2 P0-5 一成员失败整组 failed

- **裁定（语义）**：新增组级状态 `partially_delivered`——部分成员完成时，产出的东西必须保留并可交付，同时给出「失败成员清单 + 未覆盖任务清单」。组状态不得因为单个成员失败而整体置 `failed`。
- **裁定（重试）**：`maxRetry` **默认值维持 0，本轮不改**。理由：把默认重试从 0 提到 1 会改变成本模型（每个失败成员多一次全量模型调用），属于需要在实测分布上定的阈值，不能凭直觉调。本轮只做「编排组可显式传 `maxRetry`」，默认行为不变。
- **判据**：注入一个必失败成员 ⇒ 其余成员产物保留、组状态为 `partially_delivered`、清单完整；且整改后 `maxRetry` 缺省仍是 0（用断言钉住，防止后续被顺手改掉）。
