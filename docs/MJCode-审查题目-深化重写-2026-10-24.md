## 2. 四问之二：从哪些最原始素材入手

核心判据：**已经整理好的素材是「已想到的集合」，它天然不含缺口。深度只能从原始素材里的反例长出来。**

| 你已经整理好的（仅作线索索引，不作证据） | 专家会去取的原始素材 | 原始素材能给出而整理稿给不出的东西 |
|---|---|---|
| 第二～第九轮审查报告、四维审计、技术设计文档 | `git log --numstat` / `git blame` / revert 历史 | 改动最频繁的文件（缺陷热点）、被反复回退的行、修复与回归的时间间隔 |
| 台账里的「已闭环」标注 | 当前 HEAD 上逐个复验该条是否真的闭环 | 闭环标注与代码现状的偏差（账实不符条数） |
| 设计文档里的窗口/能力位/通道数 | `~/.mjcode/models.json`、`desktop/main/modelWindows.js` 的 `HOST_RULES`、`TOOL_CHANNELS` 现算 | 配置真值与文档的差值。曾发生 `xiaomimimo.com` 不在 `HOST_RULES` ⇒ 1M 模型按 32K 用 |
| 测试报告里的「全绿」 | 286 个 `.test.*` 文件的源码本身（现算：`ls desktop/test/*.test.* \| wc -l` = 286） | 哪些断言读的是源码正则、哪些集合为空即通过、哪些把缺陷固化为预期 |
| 内部对上游 API 的理解 | provider 官方文档 + 实际 HTTP 响应体 | 硬约束（如思考模式多轮工具调用必须回传 `reasoning_content`，缺失可能 400）——内部理解不含这条 |
| 审计里的完成度评分 | 真实会话 trace、DB 表（runs / messages / tool_calls）、`session_usage` | 用户实际走了哪些路径、哪些功能从未被触发、token 花在哪 |
| 与 Codex / WorkBuddy 的功能对比表 | 竞品可观测行为（发布 changelog、实际交互、公开 spec） | 对比结论是否成立；功能表证明不了行为等价 |
| 审查结论的文字描述 | 变异实验与故障注入的实测输出 | 反事实。这是唯一能证明「修复真的修好了」的素材 |

**优先级规则：一级素材（git / 测试源码 / 真机日志 / DB / provider 响应 / 磁盘配置 / 门禁常量现算）必须构成结论的支撑；二级素材（各类报告与文档）只能用来提出线索，不能用来支撑结论。**

## 3. 四问之三：具体方法和工具

| 方法 | 具体工具/命令 | 解决的问题 | 判据 |
|---|---|---|---|
| 门禁变异 | 手工注入变异体（Script 层改常量/挪进注释/清空集合） | 空过型假闸 | 变异后仍绿 = 假闸，计入「假闸数」 |
| 反事实回归 | 修复前后各跑一次同一套件 | 修复是否真的生效 | 修复前红、修复后绿；只绿不红 = 未证明 |
| 干净检出 | `git worktree add /tmp/wt <sha>` + 软链 `node_modules` + `NODE_OPTIONS=--preserve-symlinks` | 未提交依赖、路径依赖 | 干净树全绿才算通过 |
| 故障注入 | 401/400 响应、缺 `reasoning_content`、超时、断网、并发写同工件 | 失败路径是否 fail-closed | 每条失败路径有明确文案与状态，不静默成功 |
| trace 回放 | 引擎的 `now()` / `autoTimer:false` / `probeOnce()` 注入，离线重放录制会话 | 只有长时序才能触发的逻辑 | 同一 trace 重放得到同一终态 |
| 契约读者全搜 | `git grep -n "<字段名>"`，逐处判定是否需同步 | 多处读取点漏改 | 读取点数 == 已覆盖数 |
| 覆盖率当搜索工具 | `c8` / `nyc`，只看未触达分支，不设覆盖率目标 | 找「没想到的分支」 | 未触达分支逐条给出「为何不需要」或「需要补」 |
| 静态结构 | `tsc --noEmit`、eslint `max-lines`、`madge --circular` | 类型回归、God File、环依赖 | 0 错误；新增环依赖视为缺陷 |
| 属性测试 | `fast-check` 打归一化/纯函数（`resolveDispatchPresetTasks`、payload 守卫） | 输入空间盲区 | 反例可复现即缺陷 |
| 数字现算 | `node scripts/doc-fact-check.mjs`、门禁常量脚本 | 文档数字漂移 | 文档与源码同值；口径写明 |
| 双盲发现合并 | 两人独立审同一模块，先各自出结论再合并，冲突交人裁决 | 单人盲区 | 合并后冲突条目数即分歧度量 |
| 热点排序 | `git log --numstat` 累加 × 文件行数 | 优先级 | 前 10 个文件占审查预算 60% |

## 4. 四问之四：除你我之外，什么能证明结果正确

从「最不可辩驳」到「最弱」排序。关键是：**外部证明必须能拒绝我们的说法。**

| 证据源 | 能证明什么 | 不能证明什么 | 本项目可用性 |
|---|---|---|---|
| 上游服务端真值（provider 返回码、官方规格、账单） | 我们的 API 契约理解是否成立。它会直接拒绝错误实现 | 内部逻辑正确性 | 可用：4xx 响应体、官方窗口/推理字段规格 |
| 变异实验的反事实输出 | 门禁是否真的能失败 | 门禁是否覆盖了正确的点 | 可用，且是本轮第一优先级 |
| 干净检出 / 第三台机器复跑 | 结论不依赖本机残留状态 | 结论是否完整 | 可用（worktree） |
| 录制会话 DB 回放 | 缺陷真实发生过，且与叙述无关 | 缺陷是否普遍 | 可用 |
| 编译器 / 类型检查 / 结构性门禁 | 一类确定性的错误 | 语义正确性 | 可用，但须先被证明会红 |
| 跨实现对照（Codex / Claude Code 同场景行为差异） | 我们的行为是否偏离同类 | 偏离是否等于错误 | 可用，需固定同一模型与同一任务 |
| 时间（7 天 soak、崩溃日志、回归复现） | 时序类与长稳类缺陷 | 短期正确性 | 需排期 |
| 真实用户日常路径（holdout） | 功能是否被真实触发 | 触发是否正确 | 可用：会话 trace 的实际入口分布 |
| 第三方独立审查者（新人 / 开源用户） | 结论可被无背景者复现 | 结论深度 | 需成本 |

**最弱的一环要写明：你和我都不构成证明。我们能提供的只是「有锚点的可复跑命令」，可信度来自命令本身，不来自语气。**

## 5. 重写后的题目（可直接使用）

> 以下为替换原题目的完整任务书。

### 题目 v2｜MJCode Harness 深度审查：证明判定链本身可信

**审查对象（必须写死，不接受「当前项目」这种表述）**
- 树：`git rev-parse HEAD` 的 SHA 全写（起草时 `08b874f`），并记录 `git status --short` 的未提交项数量。
- 口径：检查项数 / 断言数 / 套件数三者分列；套件数 = `desktop/test/*.test.*` 文件数（起草时 286）+ smoke。
- 时点：每条读数带读数时间与是否在并发写入期。

**目标**
把已上账的 8 条 P0、5 条 P1 逐条追到「门禁为什么放过了它」，并给出修复前红、修复后绿的反事实实验。**禁止用新增覆盖面替代追根。**

**硬性动作（缺一即不合格）**
1. **验证验证器**：对台账里每个「假闸候选」注入最小变异，报告红/绿与断言实际读了什么。已知：`memory-file-channel` 本轮已被杀死（附录 A，勿重复）；`worker-memory-layering`（`LAYER_QUOTA` 全改 50）、`tool-registration-matrix` A-08（两侧清单清空）**待验**。禁止引用任何未标「哪一轮 / 什么变异体」的假闸结论。
2. **反事实**：每条 P0/P1 配最小实验，格式 `变异 → 期望红 → 实测`，禁止只给因果叙述。
3. **干净检出**：`worktree @ HEAD` 跑完整套件，报告总数，并注明确认「非并发期」。
4. **前提审计**：列出所有依赖「模型能力/窗口/用量」假设的设计（工具裁剪、`activate_tools`、压缩阈值、能力位推断），逐条核对当前真值（`modelWindows.js` / `~/.mjcode/models.json` / provider 官方规格）。
5. **契约读者全搜**：任一处字段或 schema 结论，必须给出 `git grep` 的读取点总数与已覆盖数；同一能力有多个装配点时断言「计数 == N」。
6. **真实流量取证**：结论优先用真机 session trace、DB 表、provider 响应体支撑；设计文档与历轮报告只能作线索。
7. **冻结判定**：确认无活跃写入者后跑终局门禁；并发期读数一律标注「不作为结论」。

**原始素材优先级**
一级：git 历史与 diff、286 个测试源码、真机日志与 trace、DB 表、provider 原始响应与官方文档、磁盘配置（`models.json` / `HOST_RULES`）、门禁常量现算。
二级（只作索引）：第二～第九轮报告、四维审计、技术设计文档、存量收敛台账。

**深度判据（反「更大」）**
- 一处挖穿优先于十处点到：同一模块必须追到「哪一行让这个错误成为可能」。
- 每条结论五要素：现象 / 证据（命令 + 输出）/ 根因链（≥3 层）/ 反事实实验 / 复跑成本。
- 无锚点陈述作废：每条须带 commit、`文件:符号`、口径、日期。
- 「加测试」「补文档」不算修复，只能算防护。

**交付物**
1. 根因表：行 = 根因，列 = 现象 / 证据 / 根因链 / 反事实 / 状态（已证 / 已排除 / 未验证+到期日）。
2. 假闸清单：门禁名 / 变异体 / 变异后是否红 / 断言实际读了什么。
3. 失效前提清单：假设 / 原适用条件 / 当前真值 / 影响面。
4. 收敛读数：存量未闭环数（台账现算）、假闸数、新代码首审缺陷率（首审 P0+P1 / 新增代码行）、同一根因复发次数。

**边界**
不做：新功能、需求变更、文档美化、单处 >200 行重构。
单轮上限：深挖不超过 3 个模块；其余明确标注「本轮未审」，不得用「已覆盖」表述。

**裁决点（只停两处）**
① 根因清单 + 反事实实验设计确认；② 终审。
其余阶段只通报，不阻塞。
