## 二、脚本做了什么

### 2.1 跨平台统一抽象

不按 `.app` / `.exe` / `.AppImage` 分别写，而是统一抽象成 **`resources` 目录**：
- macOS：`X.app/Contents/Resources`
- Windows / Linux：`win-unpacked/resources`、`linux-unpacked/resources`

产物发现顺序：`--artifact` 指定 → `release/*/` 下的 unpacked → `release/*.dmg`（自动 `hdiutil attach`，并注册 `process.on('exit')` + 信号处理确保卸载，不泄漏挂载点）。

### 2.2 十条断言

| # | 断言 | 拦的是什么事故 |
|---|---|---|
| R0 | 产物可解析出 resources | dmg 挂载失败 / 目录结构变了 |
| R1 | 代码载体存在（`app.asar` **或** `app/`） | 打包漏了代码 |
| R2 | 4 个关键入口齐备（main / preload / renderer/dist / agent-core） | **preload 缺失 ⇒ `window.mjcode` 全 undefined，UI 彻底不可用** |
| R3 | `sql-wasm.wasm` 在 asarUnpack 位置且 > 10KB | **asarUnpack 未生效 ⇒ 打包版 SQLite 起不来，数据不落盘** |
| R4 | 包内 `package.json` 版本 == 仓库版本 | 用旧代码打的包（发布事故） |
| R5 | `Info.plist` 版本 == 仓库版本 | **更新器按 plist 判新旧**，与包内版本不一致会导致更新判断错乱 |
| R6 | `extraResources/ecosystem` 已随包 | 生态中心空白 |
| R7 | OCR：二进制**可执行** + traineddata 齐备 | CI 未跑 `bundle:ocr` ⇒ macOS 包无 OCR |
| R8 | `app-update.yml` 含 provider/owner/repo | 检查更新恒失败 |
| R9 | `verifyUpdateCodeSignature` 与 `publisherName` **一致** | 见第三节 —— 本项抓到的真缺陷 |

**R7 的两个细节值得记**：
- traineddata 实测在 `ocr/tessdata/` **子目录**，只在顶层找会假红（我第一次就写错，被这一项自己抓出来）
- 只查文件存在不够，还要查**可执行位** —— 没有 x 位时 `spawn` 报 EACCES，比"文件缺失"更难排查

### 2.3 fail-closed

- 找不到产物 → **exit 1**（不是跳过）
- 唯一例外是 `--allow-missing`，且它会打印「这只说明没检查，不代表产物健康」；CI 绝不使用
- 自证伪里专门有一条断言验证这个行为

## 三、冒烟抓到的真实缺陷（已修）

### 3.1 `verifyUpdateCodeSignature: true` 但无 `publisherName` —— 校验恒空转

**这是 B6 第一次真实运行就抓到的。**

`electron-updater` 的 `NsisUpdater.verifySignature()` 先读 `configOnDisk.value.publisherName`，**读不到就直接 `return null` 跳过校验**。所以：
```
verifyUpdateCodeSignature: true  +  无 publisherName  =  一行校验代码都不会执行
```
它比 `false` 更糟 —— `false` 至少是诚实的，`true` 给了假的满足感。

**为什么不能简单补 publisherName**：补了但包未签名 ⇒ `verifySignature` 会真的执行并失败 ⇒ **Windows 自动更新 100% 挂掉**。两个字段必须同时到位。

**修复**：
1. `package.json`：`verifyUpdateCodeSignature: true → false`（未签名阶段明确关闭）
2. `test/build-config.test.js`：原断言只查「开关值」，改为**条件断言** —— 想开就必须同时具备 publisherName
3. 冒烟 R9 做同样的条件断言，两处判据同源

修改后的门禁语义：
| 配置 | 结果 |
|---|---|
| `verify=off` | ✅ 通过（明确声明未签名阶段不校验） |
| `verify=on` + 有 publisherName | ✅ 通过 |
| `verify=on` + 无 publisherName | ❌ 红（空转） |

**⚠ 签名证书就位后的必做项**：把 `verifyUpdateCodeSignature` 改回 `true` 并补 `build.win.publisherName`（值须与证书 Subject CN 完全一致）。R9 会强制两者同时到位。

> 关于原断言的意图：它写的是「显式开启更新包签名校验，fail-closed」。意图是对的，但**只查开关不查前提**，导致"空转的 true"也能通过 —— 这正是「断言检查了代理指标，没检查结果」。

### 3.2 我的第一版 R7 断言写错了（自纠）

初始版本只在 `resources/ocr/` 顶层找 `*.traineddata`，而真实布局是 `ocr/tessdata/`。第一次跑就红，我以为是产物缺数据，查了才发现是**断言路径错**。已改为递归查找并打印命中的文件名 —— 这类"断言自己写错"必须当场上报，不能靠改产物迁就脚本。

## 四、连带修复 B4 / B5

### B4：CI 打包不跑 `bundle:ocr` ⇒ macOS 包必然缺 OCR

**成因**：`build/ocr` 被 `.gitignore` 排除（平台相关二进制不入库），而 CI 的 Package step 直接调 `npx electron-builder`，**不经过** `npm run build`（只有那条链才含 `bundle:ocr`）—— 双轨。

**修复**：在 Package 之前加 `Bundle OCR (macOS only)` step：
```yaml
brew install tesseract tesseract-lang
node scripts/bundle-ocr.mjs --force
test -x build/ocr/tesseract
ls build/ocr/tessdata/*.traineddata   # 就地自检，早失败好定位
```

### B5：非 macOS 上 `npm run build` 第一步必红

`bundle-ocr.mjs` 原本非 darwin 直接 `process.exit(1)`，导致 `dist:win` / `dist:linux` 在非 mac 机器上根本跑不起来（`npm run build` 默认串了 `bundle:ocr`）。

**修复**：改为 `exit 0` + 两条明确 warning（说清「本平台产物不含随包 OCR」+ 影响面是图片/PDF 识别退回系统 tesseract）。随包 OCR 是可选能力，不该阻断构建。

## 五、必须说清的局限

### 5.1 我**没能**在本机打出新包

`npx electron-builder --dir` 在我当前运行环境里失败：
```
⨯ Brokered file token refused: modify backup failed
[shim] broker denied delete: path=.../release/mac-arm64.tmp.lock
```
这是**我的工具沙盒**拦住了 electron-builder 的写操作，不是项目问题。

**后果**：本报告里的「10/10 通过」是针对仓库里**现有的 0.7.0-beta 产物**跑的（挂载 dmg 得到），不是针对新打的包。CI 上的首次真实运行才是对新包的第一份证据。

### 5.2 产物形态有个未解之谜

现有 0.7.0-beta 产物是**解包形态**（`Resources/app/`），但 `package.json` 未设 `asar: false`、`asarUnpack` 也只在 asar 启用时才有意义。**二者不一致**。

我无法在新包上验证这一点（打不了包）。脚本已兼容两种形态（R1 接受 `app.asar` 或 `app/`），并会把实际形态打印出来 —— CI 首次跑就能看到当前配置到底产哪种。

### 5.3 CI 里冒烟与发布的顺序陷阱

`--publish always` 在 **Package step 内**就完成了上传。所以发布流水线中，冒烟失败时坏包**已经挂在 Releases 上**，需人工下架。

- 非发布流程（PR / push）：完全有效，坏包不进制品
- 发布流程：有 CI 红灯兜底，但不够干净

彻底解法是把 publish 拆成独立 step 放在冒烟之后（`--prepackaged` 或 `gh release upload`）。我没做 —— 那改动会影响发布流程，而我**无法在本机验证 CI**，不能盲改。

### 5.4 Windows / Linux 的冒烟没有接

CI 里冒烟 step 带 `if: matrix.os == 'macos-latest'`。原因：win/linux 的 `*-unpacked` 目录是否被 electron-builder 保留，我无法真机确认。**不引入未验证的 CI 失败**，比"写上去看起来很完整"更负责。

补齐条件：需要一次真机（或 CI 试跑）确认 `release/win-unpacked/resources` 与 `release/linux-unpacked/resources` 的存在性。
