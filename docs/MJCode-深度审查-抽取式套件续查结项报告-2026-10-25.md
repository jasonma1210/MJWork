## 3. 方法论样板：compact-tail-budget 的 Type-2 区分

第 12 项套件是本轮方法论上最干净的一例，明确区分了「看起来红了」与「真闭环」：

- **朴素全行注释变异**（`// if (convo !== beforeConvo) { ... }`）会让它后面的 `break` 悬空 ⇒ 触发 `SyntaxError` ⇒ 套件崩溃红。这是 **Type-2（崩溃运气）**，不构成覆盖证明——换个布局（把注释写成 `if(false){ //... }` 包住）就不崩了，反而静默绿。
- 真正能证明覆盖的是：**去注释后断言该校验仍作为生效代码存在、且位于 `tokenWindowSpent = 0` 之前**。这条对两种注释写法都红（因为无论怎么注释，去注释后校验都消失），且红在「断言未命中」而非「语法崩溃」。

推论已写入项目纪律：`compact-tail-budget` 的判据证明了「偶然红不算覆盖」的第三条——必须报告「被哪条机制拦住」，崩溃红 ≠ 断言红。

## 6. 本轮提炼的新纪律

1. **URL 安全注释剥离器**：含 `https://` 的文件必须用 `(^|[^:])\/\/[^\n]*/g` + `$1`，否则会把协议里的 `//` 误删导致断言失准。已在 `compact-tail-budget` / `worker-memory-layering` / `compact-safety` 采用 `stripTsComments` 落实。
2. **Type-2 区分样板**：`compact-tail-budget` 证明「崩溃红 ≠ 断言红」，报覆盖时必须附机制类。
3. **双路径互证边界**：`scheduled-tools` / `team-lead-dispatch` 用「括号配对」与「缩进层级」两条独立路径算闭括号，不一致即红，挡住单路径启发式（如 `bodyOf` 的 `\n  }`）的错位。
