## 3. 关键决策：FTS5 不可用 → bigram 倒排（§8.5 的实施前验证）

§8.5 要求「先验证当前构建是否启用 FTS5，以及中文召回效果，再进入完整 UI 实施」。实施前探测结果：

```
sql.js 1.15.1 → CREATE VIRTUAL TABLE ... USING fts5  →  Error: no such module: fts5
```

重编 WASM 在本机不可行（sql.js 的发行产物不带 FTS5 编译开关）。§8.5 同时允许「bigram 或等效分词方案」，故改为**普通表上的 bigram 倒排索引**：

- 中文：按字符切 bigram（`中文索引` → `中文`/`文索`/`索引`）；
- 英文/数字：按词元小写；
- 排序：`tf · idf`（`idf = ln((N+1)/(df+1)) + 1`），**分数只用于排序**，界面不显示、更不折算成「可信度百分比」（§8.5 明确禁止）。

满足的不变量：**中文不是只能整串 LIKE 命中**。判据落在 T3b：查询「中文资料」在原文里**不是连续子串**（`中文检索` 与 `业务资料` 之间隔着别的字），bigram 倒排分别命中 `中文` / `资料` 而召回；把检索换成整串 `includes` 语义即红（见 §5.2 的 M6）。只写 T3 是不够的——它的查询词在原文里连续出现，LIKE 也会命中，属于「断言名比判据强」。

## 4. 安全与口径（逐条对应 §8 条款）

| 条款 | 落地方式 | 守护测试 |
|---|---|---|
| §8.4 不删用户原文件 | 导入 = 复制进 `userData/kb-storage`；删除只清 chunks/index/授权/副本登记，**不动源路径** | T11c：删除后源文件仍存在（T11a/T11b 顺带守幂等：二次删除返回 `NOT_FOUND`） |
| §8.3 授权即版本 | `kb_project_authz.revision` 每次授权/撤权 +1；`kb_actor_authz.epoch` 供 M4 角色变更 | T10：撤权后再授权，旧快照仍失效（revision 单调） |
| §8.6 跨项目隔离 | 搜索按 scope 先收窄 source 集合；`buildContextPlan` 对非授权 chunk 直接 `FORBIDDEN` | T7（项目 B 看不到 A）、T7b（workspace 作用域可见）、T8（撤权即时失效） |
| §8.6.4 快照不复活 | `validateContextPlanForRun` 重验 revision / epoch / chunk 版本 / chunk hash / chunk 是否存在 | T9a–T9d（chunk 删除后 `CONTEXT_PLAN_STALE`）、T10 |
| §8.7 渲染层不传路径 | `knowledge:import` 只接受 `projectId`，路径由主进程对话框产生 | 静态：`knowledge-ui-wiring` 的桥面断言 |
| §8.8 真实空态 | 无授权源返回 `NO_AUTHORIZED_SOURCES`、无命中返回 `NO_HIT`，两者都是 `items: []` + reason，界面分文案显示，不编造引用 | T5a/T5b |
| 注入防注入攻击 | 片段下发前 `escapeHtml`，界面 `dangerouslySetInnerHTML` 只渲染已转义文本 | T6：`<script>` 命中后片段里是 `&lt;script&gt;` |

**为什么 `knowledgeValidateContext` 不暴露给渲染层**：若渲染层能自己调用重验，它就等于能自己宣称「快照仍然有效」。§8.6.4 要求该判定发生在运行前的主进程检查里，故这条通道只留给主进程内部使用。

### 5.2 反向验证（接线门禁确实会红，且红在断言上）

接线类断言最容易变成「恒绿装饰」。逐条变异后观察**失败原因是否就是该断言**（不是崩溃、不是语法错）：

| 变异 | 实际输出的失败原因 |
|---|---|
| M1 去掉 `projectId ?` 条件保护，无条件挂载面板 | `KnowledgePanel 未被 projectId 条件保护（无项目时也会渲染 → 串项目风险）` |
| M2 `projectId={null}` | `projectId 应直接透传上层 projectId，实际是：null` |
| M3 `projectId={projectPath}`（两键混用） | `projectId 应为项目 id，实际：projectPath` |
| M4 删掉 preload 的 `knowledgeDelete` 桥 | `缺桥方法：knowledgeDelete` + `knowledgeDelete 未调用 knowledge:delete` |
| M5 面板把 `knowledgeSearch` 拼成 `mjCode.knowledgeSearch` | `面板只调用了 7/8 条桥方法：…（缺 knowledgeSearch）` |
| M6 检索改用整串 LIKE 语义（`chunk.text.includes(query)`） | **只有** `T3b 词不连续查询「中文资料」仍能召回` 变红，T3（连续子串查询）仍绿 |

M6 值得单独说明：原 T3 的查询「中文检索」在原文里是**连续子串**，`LIKE '%中文检索%'` 一样会命中，所以它证明不了「没退化成整串匹配」（断言名比判据强）。补了 T3b 用词不连续的查询「中文资料」（原文里 中文 与 资料 之间隔着别的字）后，M6 变异只让 T3b 红、T3 绿——这正是「两条断言各管一件事」的形态：T3 管「能召回」，T3b 管「不是整串匹配」。

每组变异后按「还原 → 复跑全绿」收尾，四个被改文件与备份 `cmp` 逐字节一致。

另：`doc-fact-check` 的套件判据本轮由「N 套件全绿」改为「N 套件」。原因是它**只能现算套件数**，「是否全绿」算不出来——把不可验证的词写进被校验的断言，只会让文档在门禁红着时继续声称全绿（本轮实测：11 项存量门禁红着，而该行已连续多轮写「297 套件全绿」）。改完做了变异验证：文档写 300（现算 299）→ 报 `数字漂移：suites`，还原即绿。

## 6. 未接线 / 已知缺口（不含糊）

1. **任务侧注入未接（M3 的「注入/引用」只完成了一半）**
   已具备：快照生成（`buildContextPlan`）、快照预览（界面「预览注入」）、失效判定（`validateContextPlanForRun`）。
   缺：`agent:run` 在开跑时不校验、不拼接；任务页无「选择知识范围」选择器。
   接缝已定位：`desktop/main/main.js:1239` 的 `appendSystemPrompt: rc.appendPrompt` 是唯一的系统提示追加点（语义是**追加**而非替换，见 `test/append-system-prompt.test.mjs` 的事故记录）。把快照片段渲染成文本块后在此追加即可，但需要同时：(a) `agent:run` 载荷增加 `knowledgePlan: { planId, planHash }`；(b) 在同一次运行内先 `validateContextPlanForRun`，失败即按 `CONTEXT_PLAN_STALE` 拒绝而不是静默丢弃；(c) Composer 侧选择器。三项必须一起做，只做 (a)(b) 会得到一个「永远没有 planId 传进来」的死分支。
2. **格式范围**：仅文本类（`.txt/.md/.markdown/.json/.csv/.log/.text`，≤5MB）。§8.2 提到的 PDF/DOCX 未实现，界面按 `capabilities()` 下发的能力位如实显示支持范围，不写死。
3. **导入是同步的**：§8.4 的 `queued → parsing → chunking → indexing → ready` 多阶段进度与「取消导入」未实现；当前 5MB 上限内同步完成，失败项逐个返回错误码。大文件与 PDF 解析落地时必须补后台任务与取消。
4. **`context_plans` 只增不删**：为了让旧快照能被判成 `CONTEXT_PLAN_STALE` 而不是被悄悄抹掉，删除文档时**保留**快照行（§8.4「删除不暗中改写历史」）。代价是这张表会随使用增长，需要一条按时间的清理策略——属尚未实现项。
5. **访客上传/下载**：§8.2 明确 M4 才做，此处不做，也没有用任何文本同步冒充文件传输。
