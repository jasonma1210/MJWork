# MJCode 业务逻辑与前端展现审查（用户视角）

审查日期：2026-10-22
代码基线：`main @ 93c6c5d`，`git status` 干净
测试基线：**总计 280 · 通过 277 · 失败 0 · 跳过 3**（跳过均为 Linux 沙箱真机项，本机 darwin；按口径不计入已验证）
审查方法：只读源码 + 实跑测试，不采信 README 与既有报告的自述。凡结论均附 `文件:行号`，可逐条复核。

---

## 0. 先说结论

**这个项目的"能力密度"已经超过大多数商业 Agent 产品，但它的"主线回路"没闭环。**

一个 Agent 产品的核心回路只有五步，用户心里就是这么走的：

> 说清任务 → 看着它做 → 中途能干预 → 做完能验收 → 不满意能退回

MJCode 在这五步上的真实状态：

| 环节 | 状态 | 用户实际感受到的 |
|---|---|---|
| 说清任务 | 好，但入口太密 | 首次打开要过 9 步向导；首屏约 30 个可点目标；同一个功能常有 2–4 个门 |
| **看着它做** | **弱** | 运行时工具轨迹默认折叠，只看到一行"3 次调用"；进度清单（TodoPanel）永远不显示；实时 token 恒为 0；看不到哪一步慢 |
| 中途能干预 | 半 | 审批能拦住危险操作，但卡片不说是哪个会话发起的；页面刷新后正在跑的任务变成孤儿，看得见库里在长，屏幕上看不见 |
| **做完能验收** | **断** | 改完文件界面没有任何"有改动待审查"的信号；打开 diff 面板会先误报"没有未提交的改动"；"接受"按钮其实是 `git add` |
| 不满意能退回 | 半 | "放弃修改"是直接销毁工作区内容，靠 5 秒撤销兜底；没有 hunk 级精确回退 |

第 2 步和第 4 步是产品级缺陷，不是打磨问题。理由是：Agent 产品的信任来自"我看得见它在干什么"和"我能确认它做对了"。这两件事现在都做不到，用户只能选择全信或不信——而全信会出事，不信就没法用。

**另外三件同样重要的事：**

1. **有 6 个"看起来有、其实没有"的功能**（下面 §3）。这类问题比"没做"更伤，因为作者和用户都以为它在工作。它们有共同根因：能力声明和宿主实现之间**没有机器可查的一致性约束**。
2. **知识层缺两层里的两成**：只有"项目级规范"，缺用户级全局指令和组织级规范；而且项目规范只对主对话生效，Agent 军团和定时任务读不到——同一个项目里，主 Agent 守规矩、团队成员不守。
3. **文档体系是资产加负债，负债在按天复利**。61 份根目录报告零索引、零入库；README 73 万字节里 96.5% 是内部流水账；中英 README 在产品事实上互相矛盾。

## 2. 业务逻辑：八个必须修的断点

按"用户会不会撞上 + 撞上后有多难受"排序。

### P0-1 同一个会话，什么时候刷新决定模型看到什么历史

**你会遇到**：让 Agent 改一个功能，它读了 5 个文件、跑了一次测试。你追问"那第二个文件里的 xxx 为什么没改？"——它答不上来，或者重新把所有文件再读一遍。你花的 token 翻倍，行为还不可预期。

**代码里发生了什么**：发消息时，历史取自渲染层内存 `messagesRef`（`renderer/src/hooks/useAgentRun.ts:371`），而这份内存里只有"你的消息 + 最终总结"。中间那些 `assistant(tool_calls)` 和 `tool` 结果虽然主进程已落库（`main/agentRunner.js:486-489`），但主进程模式明确不转发 `message` 事件（`renderer/src/lib/agent.js:55`、`:86-120` 的 switch 里没有 `message` 分支）。

于是：**不刷新 = 模型看不到自己刚才干了什么；刷新一次（从库里全量拉回，`ChatArea.jsx:257-261`）= 历史突然完整了**。同一个会话，刷新前后是两种行为，问题还不可复现。

**怎么改**：历史必须只有单一来源。最省事也最正确的做法是让主进程在 `agent:run` 时用自己的库拼历史（payload 只传本轮新消息），渲染层不再充当历史的真源。退一步的话，至少把 `message` 事件接回渲染层并合并进 `messagesRef`。第一种改法顺带解决 §3 里"run 状态没落盘"的问题。

---

### P0-2 点"停止"会写出两条回复，其中一条是假的

**你会遇到**：任务跑到一半你点停止。界面上出现"（已停止）"。下次进这个会话，发现有两条 assistant 回复，一条写着"（已停止）"，另一条是它其实已经生成的总结。再发下一句时，这两条都进了上下文。

**代码里发生了什么**：中止时渲染层先本地收尾，写一条占位消息（`useAgentRun.ts:496-506`，走 `mainMode=false` 分支，因为 `lib/agent.js:130-140` 的 abort 路径没传 meta）；与此同时主进程的引擎收到 abort 仍会正常走 `onDone`，把真实收尾文本落库（`agent-core/index.js:3314`、`main/agentRunner.js:472`）。两条路径各写各的。

**怎么改**：加一条规矩——**消息落库只能有一个写者**。既然主进程已经在落库，渲染层就只负责显示 pending 态，停止时不要伪造消息。这条和 P0-1 是同一个根因（双写者），建议一起改。

---

### P0-3 任何超过 30 分钟的任务，必然以"契约校验失败"告终

**你会遇到**：一个长任务（大重构、批量处理）跑过半小时，界面弹英文错误"IPC 契约校验失败：data.kind Invalid enum value"，然后就不再动了。但主进程其实还在跑、最后还写完了总结——只是你看不到。

**代码里发生了什么**：引擎墙钟超限时发 `kind: 'wallclock'`（`agent-core/index.js:3184`），而 IPC 契约只允许 `tokens | rounds | timeout`（`shared-ipc/contract.mjs:73`）。越界的枚举值被降级成 `type:'error'`（`contract.mjs:243-252`），渲染层收到 error 直接 reject 整轮（`lib/agent.js:116-117`）。

**这是个必现 bug，不是偶发。** 而且 `suspended` 事件在渲染层根本没有消费分支，所以即使合法挂起（token 用尽）也一样被丢掉。

**怎么改**：契约枚举补 `wallclock`；渲染层给 `suspended` 加显式分支（"已暂停，点继续"）。同时补一条"枚举值必须双向对齐"的测试——现在契约和引擎是两个文件各写一份枚举，谁改了另一边都不知道。

---

### P0-4 点一次"压缩上下文"，可能永久删掉大半历史

**你会遇到**：会话长了，你点"压缩上下文"。结果之后这个会话只剩下最近几轮和一个 400 字摘要，之前的全没了。而且如果你在任务运行中点它，还会覆盖掉正在写入的新消息。

**代码里发生了什么**：压缩用的是 `.model` 对象直接传进去（`useAgentRun.ts:776`），而 `context_window` 只在运行时的副本里补（`:564-573`），两者不是同一个对象——所以引擎读不到窗口大小，回落到默认 **4096**（`agent-core/index.js:1443-1445`）。4096 的窗口意味着超过约 3.3k token 就判"激进档"，只保留 15% 尾部。压完直接 `replaceMessages` 整体覆盖数据库（`useAgentRun.ts:782`、`main/localStore.js:303-321`），不可撤销。

更麻烦的是：这个函数只检查 `compacting / selectedModel / messages.length`（`:772`），**没有检查 `loading`**。运行中压缩 = 两处同时写同一个会话。

**怎么改**：压缩必须拿运行时那份补好窗口的 model；压缩前落快照（`checkpointStore` 已有）或至少在 UI 上给"可撤销"；加 `loading` 守卫。这类"不可逆 + 静默"的组合是产品里最该防的。

---

### P0-5 审批卡不知道来自哪个会话，而且状态会亮错人

**你会遇到**：你在会话 A 干活，会话 B 在后台跑（这个产品明确支持切走继续跑）。B 撞到需要审批的命令，一张卡弹在你面前，只写着工具名和 cwd。你不知道它是 B 的，可能顺手批了。同时侧栏亮的是 A 的"待审批"徽标，B 啥也没有。

**代码里发生了什么**：审批载荷只有 `{approvalId, tool, rememberable, cwd, summary}`（`main/main.js:107`），没有 threadId。而 `App.jsx:777-782` 的 `onPendingChange` 直接改 `activeThread` 的状态。

**怎么改**：载荷加 `threadId` + 会话标题，卡头显示"来自《会话名》"，点一下能跳过去；状态按 `pending.threadId` 写。另外注意：主进程内部其实知道 runId（`main.js:98` 传给了 `approvalChannel.wait`），只是没往 UI 送——所以这个改动很小。

---

### P1-6 diff 面板：先说"没有改动"，再让"接受"变成了暂存

**你会遇到**：Agent 说"已修改 3 个文件"。你打开右栏的变更面板，第一眼看到"工作区没有未提交的改动"（假的，只是还没加载完）。几百毫秒后文件冒出来。点"接受"，回到编辑器发现文件内容一点没变——因为它只是执行了 `git add`。

**代码里发生了什么**：`DiffReviewPanel.jsx:58-60` 的 `load` 只依赖 `projectPath / t / scope`，不依赖 `agentFiles`，所以 Agent 新改的文件不会自动刷新，运行中一直开着面板更糟——永远不更新。`accept()` 调的是 `window.mjcode.gitAdd`（`:62-70`）。而 `reject()` 是 `gitDiscardFiles`，真的销毁工作区内容（`:100-113`，靠快照 + 5 秒撤销补救）。

**怎么改**：加 loading 三态（"正在读取…"→"没有改动"）；`load` 挂到 `agentFiles` 变化；文案按真实语义改（"暂存"≠"接受"），或者把默认动作换成 hunk 级 revert（`rejectHunk` 已经实现了）。

---

### P1-7 工具超时只是"不等了"，副作用还在跑；run 结束也不杀子进程

**你会遇到**：一个浏览器操作或长命令超时了，模型看到"超时失败"，于是重试一次。结果同一个写操作执行了两遍。或者任务结束了，后台还有个进程活着。

**代码里发生了什么**：`withTimeout`（`agent-core/index.js:3560`、`:3844`）超时后只返回 `{error}`，底层 Promise 继续跑。`agentRunner.js:628-633` 的 finally 只释放大载荷，不调 `killChildrenForRun`——只有用户主动 abort 才调（`:649`）。

**怎么改**：超时即取消（把 `AbortSignal` 真正传下去），run 结束时无条件杀本 run 的子进程。这两件事的收益是"行为可预期"，比多一个功能重要。

---

### P1-8 Worker / 定时任务会看到 28 个用不了的工具

**你会遇到**：让 Agent 军团去做一件事，成员说"我来生成 PPT"或者"我来打开网页查一下"，然后连续报"未知工具: xxx"，白烧几轮 quota，最后交一个半成品。

**代码里发生了什么**：引擎默认下发全量 `BASE_TOOLS`（`agent-core/index.js:2774`，只有聊天天花板 `chatOnly` 才传 `tools: []`，见 `main/workerPool.js:425`）。而 Worker 的 handler 只有 `scheduledToolHandlers + teamTools + chat + webSearch + webFetch + artifact`（`main/main.js:1496-1530`）。按名字实算，Worker 缺 28 个：`browser_*×6`、`chrome_*×7`、`doc_*×4`、`code_exec`、`sandbox_code_run`、`http_request`、`sqlite`、`clipboard`、`notify`、`search_plugins`、`install_plugin`、`scheduled_create`、`orchestrate_task`、`latex_compile`。定时通道缺 27 个。

默认团队模板因为有 `rolePreset.toolNames` 白名单挡着，命中率低；但**普通 `orchestrate_task` 组、定时任务、没配工具的自定义成员都会撞上**。

**怎么改**：引擎装配工具表时和 handler 求交集（fail-closed）。现在 `tool-registration-matrix.test.mjs` 只检查"某个 handler 在源码里出现过"，检查不出"这个通道没有它"——所以门禁是绿的但不代表对。这条改完，28 个死工具会立刻消失，而不是继续伪装成能力。

## 3. 六个"看起来有、其实没有"

这一节单独拿出来，因为它们的共同特征是**作者以为做完了、用户以为在用它**，比明摆着的缺失更贵。

| # | 功能 | 真相 | 锚点 |
|---|---|---|---|
| 1 | 待办清单 / 长任务进度 | `TodoPanel` 首行 `if (!runId) return undefined`，而两处挂载都是 `<TodoPanel />` 不传参 → 组件恒返回 null。引擎正常发事件，UI 一个字都不显示 | `TodoPanel.jsx:29`、`ChatArea.jsx:669`、`WelcomePage.tsx:91` |
| 2 | 运行中实时 token | 唯一累加点在 `onMessage`，主进程模式已剥离该回调 → 圆角标签里的 token 永远是 0 | `useAgentRun.ts:616-623`、`MessageStream.tsx:119-121` |
| 3 | "向量记忆" | `cosineSim` 注释写着"预留"；后台 `embed` 处理器直接 `skipped`；`embedding` 列从来没人写。真实检索是中文单字/二元组重叠的词法匹配 | `memory/scorer.js:112-120`、`memory/bgScheduler.js:46`、`db/index.js:106` |
| 4 | 诊断包导出 / 审计链校验 | 主进程注册了 `diag:preview` / `diag:export`，preload 也暴露了，**渲染层零调用点**；项目自己的死桥台账把这两个登记为 dead | `diagExport.js:191-210`、`preload.js:271`、`test/bridge-dead-allowlist.json:18` |
| 5 | 团队"按能力认领" | 对模型宣称 select 是"成员按能力认领"，实际是 `task.seq % 成员数` 轮转，没有任何能力匹配 | `ipc/teams.js:234`、`teamDispatchPlan.js:136`、`workerSession.js:27-33` |
| 6 | V 层自检结果可视化 | 判定结果只追加到 finalText 尾部注解，UI 无任何"本轮结论是否可信"的呈现；"Agent 说改好了但其实没改"在主对话里仍显示成功 | `verifyRun.js:122`（emit `verify`）、`lib/agent.js:86-120`（无消费分支） |

**共同根因值得单独说**：这六个都不是"忘了写"，而是"写完了没接另一端"。项目里已经有很强的门禁文化（280 个用例、契约校验、死桥台账），但这些门禁检查的是"某段代码存在"，不是"某个事件有人消费"。建议补三张机器可查的表：

- 事件 → 消费方矩阵（每个 `emit` 的类型必须有 ≥1 个 renderer 分支）
- 通道 → 工具矩阵（每个通道声明可用工具，引擎装配时求交集）
- UI 状态 → 写入点矩阵（每个展示的状态必须有真实写入端）

这三张表落地后，上面 6 条会当场变红，不需要靠人肉审查发现。

## 4. 前端展现：一次完整的用户走查

### 4.1 进门这一步，门槛偏高

冷启动 2.4s 闪屏（可跳过）→ **9 步向导**（欢迎 / 模型 / 安全 / 数字员工 / 技能 / 连接器 / 项目 / 首任务 / 开始，`Onboarding.jsx:16`）。其中"数字员工 / 技能 / 连接器"三步是可选的生态配置，却排在"首任务"之前——**用户还没发过一句话，先被要求做三个生态决策**。

进主界面后，首屏可点目标约 30 个：侧栏 6 + 顶栏 5 + 建议卡最多 8 + 输入框工具行 6 + 发送 1，另有 9 项藏在"+"后面。

**建议**：向导压到 3 步（模型 → 安全 → 首任务），生态三步改成"稍后在生态中心完成"；欢迎页建议卡固定 4 张。**先让人干成一件事，再让他配置。**

### 4.2 同一个功能，常常有 2–4 个门

这是"入口过载"的真实形态——不是功能太多，是重复指向。

| 能力 | 门的数量 | 具体 |
|---|---|---|
| 生态中心 | 2 | 侧栏一级（全屏弹窗） + 设置页内嵌（还带双滚动条） |
| 团队 | 3 个同名/近名的界面 | 侧栏"团队编制"（管理页） / "+"菜单"团队编制"（会话内派活） / 设置"团队空间"（看板） |
| 右栏面板 | 7 个 tab + 另一个 7 项"+"菜单 | 两者是**同一集合**，"+"的作用就是切 tab |
| 项目 | 4 | ⌘O / 侧栏项目列表 / "+"菜单项目空间 / 欢迎页 |

**建议**：右栏删掉"+"菜单（它是纯重复）；生态中心只留侧栏一个门；团队三处重命名并明确层级——"团队（编制）"=管理、"派活"=会话内面板、"团队空间"=看板。名字相同的两个东西摆在两个地方，是最容易让人怀疑产品没做完的细节。

### 4.3 运行时，你几乎看不到它在干什么

- 工具轨迹组默认折叠（`ToolTrace.tsx:578` 的 `defaultOpen = false`，注释写着"运行态传 true"但两处调用都没传）。跑起来只看到一行"3 次调用 · 点击展开"。
- 待办清单完全不显示（§3-1）。
- 实时 token 恒 0（§3-2）。
- 逐工具耗时、首字节、每轮耗时只写进 `userData/traces/<runId>.jsonl`，而打开它的 UI 入口（诊断导出）是死的（§3-4）。所以"慢在哪"这个问题，产品内无法回答。

**建议**：运行态强制展开工具组并显示"当前正在执行：shell · 已 12s"；`RunFooter` 把 token / 工具数 / 耗时 / 当前步骤放一行。这一条改动量很小，对信任感提升最大。

### 4.4 做完之后，没有"验收"这个落点

这是 §0 里"第 4 步断"的具体形态：

1. Agent 改完文件，界面无任何"有 3 个改动待审查"的信号（`agentFiles` 只被当成 diff 面板的筛选器，从没显示数量）。
2. 打开 diff 面板先误报"没有未提交的改动"（§P1-6）。
3. 面板不会随 Agent 新改动自动刷新。
4. 收尾条只报"状态/耗时/token/模型"，**没有任何动作按钮**。
5. 想回滚得知道"放弃修改"藏在 diff 面板底部。

**建议**：右栏开关加改动数量角标；`RunFooter` 末尾加"查看 3 个改动"，点击直达 diff；审批通过后自动切到 diff 并高亮新变动的文件。这三件事做完，"做完能验收"这一步才算存在。

### 4.5 静默失败：116 处 console，其中 40 处是唯一反馈

全渲染层 116 处 `console.warn/error`，逐条核实后 **40 处既没有 toast、也没有内联错误、也没有错误态置位**——只有控制台一行。最伤的四处：

| 位置 | 用户看到 | 实际 |
|---|---|---|
| `ChatArea.jsx:269` | 有标题、没消息、输入框可用的"空会话" | 消息加载失败，只 warn |
| `App.jsx:553-578` | 点了确认删除，列表纹丝不动 | `deleteThread` 裸 await，无 try/catch，unhandled rejection |
| `App.jsx:361-371` | 侧栏、模型选择器安静变空 | `Promise.allSettled` 后只 warn |
| `MemorySection.tsx:119-143` | "0 条记忆、开关全关" | IPC 抛异常，`setUnavailable` 只覆盖 `ok:false` 不覆盖 throw |

**建议**：定一条规矩——**写操作的失败必须有 UI 出口**；把 `console.warn` 换成统一 `reportError(err, { silent })` 包装，`silent` 必须显式声明并写理由。这条比逐个补 toast 更能防止复发。

### 4.6 三处跨会话 / 跨项目数据泄漏

| 泄漏 | 现象 | 锚点 |
|---|---|---|
| 附件 chips | 项目 A 拖入 2 个文件，切到项目 B 新建会话，chip 还在 → 发出去变成 B 会话里的 `@A文件路径` | `ChatArea.jsx:245-271`（`setAttachments([])` 只在 `thread?.id` 为真的分支） |

### 4.7 一致性：底子好，尾巴没扫

## 5. 作为一个 Agent 产品，还缺什么

对照主流 Agent 产品（Codex / Claude Code / Cursor / TRAE）该有而这里没有的，以及有但只通一半的。

| 能力 | 通到什么程度 | 卡在哪 |

1. **shell 三平台隔离是真的**：macOS Seatbelt、Linux bwrap、Windows 受限用户 + ACL，不可用时降级到"命令守卫 + 单次审批"，且 `sandboxPolicy` 缺省 `read-only`。CI 里还有真实 bwrap 冒烟。

## 8. 最后一条建议：把"壳子"变成机器可查

上面 6 个壳子里，有 4 个是"事件发出去了没人收"。这类问题人肉审查抓不住——因为它看起来完全正常：函数在、事件在、注释写着"运行态传 true"。

建议补三张机器可查的表，接进 `npm test`：

1. **事件 → 消费方**：每个 `emit('xxx')` 的 type，必须在 renderer 的 switch 里有分支，否则 FAIL。
2. **通道 → 工具**：每个通道（交互 / Worker / 定时 / 团队 / 子代理）声明可用工具集，引擎装配时求交集，多出来的直接报错。
3. **UI 状态 → 写入点**：每个展示给用户的状态字段，必须有真实写入端（这个项目在 `awaiting_approval` 上已经吃过一次亏，注释里写着"此前全库无任何写入端"）。

这三张表比再写 10 份审查报告有用。审查报告解决"这一次发现了什么"，表解决"下一次不可能漏"。
