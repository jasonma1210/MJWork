## 0. 先说一件影响决策的事：**「回 0.7.0」回不到你以为的那棵树**

| 引用 | SHA | 说明 |
|---|---|---|
| tag `v0.7.0-beta` | `f38dd47` | 与 `origin/main` 同一提交，即**已发布的 0.7.0** |
| 本地 `main` | `c1ad76e` | 比 tag **领先 7 个提交** |
| 当前分支 HEAD | `38eebd6` | 比 tag **领先 13 个提交** |

也就是说：**已发布的 0.7.0 并不包含本地 `main` 上那 7 个提交**，而其中几个恰好是修复审计里同类问题的：

| 提交 | 内容 | 与本次审计的关系 |
|---|---|---|
| `3846705` | 修复 P0 运行链路七项缺陷（历史单一真源 / **中止双写** / 墙钟契约 / **压缩安全** / 审批归属 / 待办接线 / **运行可见性**） | 审计里「中止产生两条 assistant」「压缩丢信息」「刷新看不到在跑的 run」——**这些正是它修的** |
| `1531dbe` | P1 八项 + 工具面重构（分层激活 / run 基线 / 验收回路） | 审计里「工具面设计」「验收」相关 |
| `ac1d5ef` | 修工具选择偏差（描述信息不对称） | 审计里「模型挑错工具」 |
| `1478096` | 登记 MiMo V2.6 Flash 的 1M 窗口 | 审计里「窗口口径两套」 |
| `c1ad76e` | 能力位读取侧补按 ID 推断 | 审计里「能力位识别」 |

**结论：回 `v0.7.0-beta` 不是"更干净的基线"，而是把一批已修的 P0 重新打开。**

而且更关键的一条：**四组审计的 P0，没有一条是品牌改名引起的。** 改名只影响身份字符串与文档；这些 P0（沙箱禁网、工件无出口、团队不能无人值守、签名缺失）在 0.7.0 里同样存在。

> **所以「回 0.7.0」不能解决任何一条审计问题，只会多出几条。** 这一点我按事实说清，具体怎么处理由你定。

## 4. 「一层假闭环」——四组共同指向的同一个模式

四组各自独立审计，但指向了同一个结构性毛病，我认为这是最该记进备忘录的一条：

> **很多东西"看起来有"，是因为可见的那一半做完了，而承重的那一半没做。**

| 看起来有 | 实际 |
|---|---|
| 记忆仪表盘、四层作用域、晋升链、半衰期 | 召回不传 query ⇒ 注入的是"最近 7 条无关记忆"；模型连 `memory_*` 工具都没有 ⇒ **不能自己查、自己记** |
| 能截图看懂页面 | 截的是给**用户**看的；模型只拿到路径，`read_file` 读图是乱码 ⇒ **模型是盲的** |
| 工件库有版本、有 patch、有 diff、有回滚代码 | 回滚**零调用方**；工件**导不出成文件** ⇒ 交付不了 |
| 团队有看板、有消息总线、有等待 | 消息单向拉取、`question`/`handoff` 无应答保证、统筹拆完就消失 ⇒ **不商量、不返工、不自愈** |
| 有审计日志、有诊断导出 | 界面无入口 ⇒ **用户看不到** |
| 有沙箱、有审批四档 | 默认档禁网 ⇒ 干不了联网的活；`read_file` 全盘零审批 ⇒ 承诺的"写操作逐次询问"只覆盖了写 |

**判读**：这类问题最危险的地方在于——**它不能靠"再加功能"解决，也不能靠测试发现**。审计里那句「291 项全绿与本报告不矛盾：上述缺口没有一条能被单测覆盖，它们都在进程边界、真实 provider、真实工作负载上」就是这个意思。

## 5. 如果要发下一个版本：最小可发布集

**目标不是"做完"，而是让「能不能干活」和「第一次能不能用」两条通路先通。** 按性价比排序：

### 第一批（极低成本，1~2 天，直接改善"能不能用"）
1. docx 表格框线（改配置级）
2. 窗口口径统一（4096 → 与 modelWindows 同源）
3. `grep`/`glob` schema 补实现已有的能力
4. 记忆召回补传 query
5. `read_file` 纳入敏感路径拦截 + 可配置审批
6. 连接器 Key 从 localStorage 与明文 env 里挪走

### 第二批（P0 里成本最低的两条）
7. **沙箱加「可写 + 联网」档**（这是"能不能干活"的总开关）
8. **首次对话没模型**：给出可用的默认配置入口（哪怕只是"从已有 provider 列表里一键导入"）

### 留到下一版
- 工件 → 产物导出桥（P0-2）
- 模板填充 + 读回 Office（P0-3，**这是能不能卖 1 万块单子的分界线**）
- 团队无人值守唤起（P0-4）
- 成员失败自愈 / 部分交付（P0-5）
- 签名 + 公证 + 回滚（P0-6，需 Apple 账号，外部依赖）

## 6. 诚实边界

- 四组均为**只读静态审计 + 单元级验证**，**未启动 Electron GUI、未接真实 provider、未跑全量测试**（遵守"只审不改"纪律）。
- 已知的推断项（已在各组报告内逐条标注）：陌生 Mac 上 Gatekeeper 的具体弹窗文案（本机 `spctl` 显示 `override=security disabled`，不代表干净机器）、Windows 更新签名校验失败、启动耗时与内存占用、模板填充缺失对成交率的实际影响。
- **有一处反向证据值得记**：全仓 `find` 命中的 `.docx` / `.xlsx` / `.pptx` = **0 个**。这条 Office 产线在真实交付里从未跑出过一个文件——而它的单测是 40/40 全绿的（只校验 zip 头是 `PK`）。
- 「完成度百分比」是主观刻度，依据是「与同类产品该维度的功能面 + 闭环程度」加权，不是可复现的指标。它的用处是**排序**，不是**计量**。
