## 3. 三类假绿（本批核心产出）

「假绿」= 套件报绿但没有真正测到，或产品真坏却仍报绿。本批处理了三类，每一类的判据都是**实测**而非读代码推断。

| 类 | 现象 | 处理 | 判据 |
|---|---|---|---|
| ① | `check` 声明成 `async` 但调用处没 `await` ⇒ 断言抛的 rejection 在进程退出前没被观察 | 修 3 个套件（`diag-export` / `web-todo-tools` / `message-schema`） | 合格判据三条同时满足：汇总计数少一条、`[FAIL]` 早于汇总行、退出码 1。**只看 exit 码不够**——同步 `check()` 会先打印 `13/13` 再崩，exit 仍为 1 |
| ② | 套件无条件 `process.exit(0)` ⇒ 在途 rejection 被截断 | 新增 `desktop/test/helpers/unhandled-preload.cjs`，条件式延迟包装 | 同步 `process.exit(process.exitCode||0)` 实测**仍 exit=0**（`exit()` 同步截断）；必须延后一个宏任务 |
| ③ | 抽取式断言的替身风险：用 `new Function` 从源码抽片段求值，锚点变化后行为不可控 | 9 个套件普查 + 修 1 个 | 见下 |

### ③ 的普查结论（9 个套件逐个实测变异）

- **严格 silent-empty（抽空 → 空过）= 0 个**。
- **替身命中导致的「应红却绿」= 1 个**：`stop-thread-work`。
  - 变异 T14：把 `useAgentRun.ts` 的 `stop()` 掏成空壳、真逻辑改名下移 ⇒ **产品真坏了**（`stop()` 什么都不做），套件却 `11/11` 全绿 exit=0。

它覆盖的失效形态是此前**完全没被覆盖**的一类：**抽取窗口错位，但两边元素按位置碰巧长得一样** —— 终态「三组一致」照旧成立，所以只看最终结论的断言永远不会发现窗口已经取错了。

这条与第 6 节的纪律 1、2 是同一条链的延伸：

- 纪律 1：「只看是否变红」会被**冗余防御**蒙混；
- 纪律 2：「只看最终结论」会被**崩溃/异常**蒙混；
- A10：「只看最终结论」还会被**巧合同源**蒙混。

合起来一句话：**验证要断言机制，不是断言结果。** 当前套件读数 `总计 16 · 通过 16 · 失败 0 · 跳过 0`。

实现取舍：**没用 espree / AST**——实测 espree 与 typescript 都不在 `desktop/package.json`，只是 eslint 的传递依赖靠 npm hoist 露出；依赖它的套件在依赖树重排后 `MODULE_NOT_FOUND` 崩溃，而 `run-all` 记 crashed 会让整条基线红。改用纯括号配对状态机（跳字符串/注释）+ 运行时交叉验证（require 真值 vs 抽取值）。

## 5. S12：`--write` 后门加锁

### 问题

`scripts/audit-check-await.cjs` 的 `--write` 只需一个 flag 就整份重算基线，**不要求任何人工说明**。位置级指纹的代价是「改裸 async IIFE 内部也会红」（1 消失 + 1 新增、总数不变），这类合法轮换会越来越频繁 ⇒ `--write` 变肌肉记忆 ⇒ 真实新增的裸 promise 会被顺手吸收，门禁**静默削弱**且事后查不出是谁。

### 落地（commit `9190709` + `63a3545`）

- 新增 `--reason=<文本>`；**触发条件按文件判，不看总数**：存在文件满足 `新增 > 消失` ⇒ 必须带理由。
  - 键轮换（同文件 1 增 1 消）⇒ 免理由；
  - 真新增（某文件多出 1 个、消失 0 个）⇒ 要理由；
  - **「删 2 个旧的 + 新加 1 个」总数净减但真有新增** ⇒ 照样拦（总数口径会漏）。
- 缺理由 ⇒ **不写基线**、打印净增文件清单、退出码 **3**（未知参数仍为 2）。基线字节未变用 sha256 前后比对证明。
- 基线加 `history` 数组：`{ at, added, removed, net, files:[{file,added,removed,delta}], reason }`。记所有 `delta ≠ 0` 的文件（比只记净增更可追溯）。
- 基线夹具取证：`points` 仍 **46**，`tiers {bareIife:46, thenOnly:0}`、`version:3` 全等 ⇒ 判据本体未被改动。

### 验证（自测 18/18）

原有 8 条 + 新增 6 条（S1–S6）+ 4 条对照实验（M1–M4）：

| 用例 | 结果 |
|---|---|
| S1 净增无理由 ⇒ exit=3 且基线字节未变 | ✔ sha256 前后相等 |
| S2 带 `--reason` ⇒ history 存理由原文 | ✔ 逐字一致 |
| S3 净变化 ≤ 0 无理由 ⇒ 放行，记清理标记 | ✔ |
| S4 老基线缺 `history` ⇒ 读成空数组不崩 | ✔ |
| **S5 反向：新增裸 promise 不带 `--write` 纯检查 ⇒ 仍 exit=1** | ✔ 输出含「② ratchet 违规」= **正门没被锁死** |
| S6 总数净减但某文件净增 ⇒ 仍要理由 | ✔ |
| M1 短路理由校验 | S1 失守，形态 = **静默放行** |
| M2 按文件改按总数 | S6 失守，形态 = **静默放行** |
| M3 置空**检查路径**的 `added` | S5 失守，形态 = **静默变绿** |
| M4 去掉 history 容错 | S4 失守，形态 = **明确崩溃** |

> S5 是最关键的反向验证：`--write` 是后门，**后门加锁不能顺手把正门也锁死**。

## 6. 本轮沉淀的三条纪律（已写入长期记忆）

1. **冗余防御会让单点反向验证失真。** 括号配对器有两层注释跳过（`matchBrace` + `splitTopLevel`）；只禁用配对层时套件**照样绿**——另一层把脏文本洗掉了。推论：**随着防御层越加越多，单点反向验证的可信度反而下降**。必须把所有实现路径一并失效、亲眼看到红。

2. **反向验证自身也会假绿，必须同时断言「失守」和「失守的形态」。** 只断言前者会被崩溃/异常蒙混过关——实测两次复现：①变异体在 tmpdir 里 `require('espree')` 解析不到 ⇒ MODULE_NOT_FOUND，「全部失守」其实靠崩溃；②变异写成 `net > 0 ?` 但 `net` 在其后声明 ⇒ TDZ 崩溃，显示 status=1「看着像明确报错」。**变异后的表现「看起来合理」时最危险。**

3. **数字口径必须带单位。** `*.test.*` 292 / 套件 294 / 总计 299 / 通过 296 是四个不同单位；历史上文档里已因此漂移过一次（速查表写 291/296/293 与技术基线的 294/299/296 自相矛盾，而 `doc-fact-check` 的正则只匹配首个「N 套件全绿」，不会自己变红）。

**配套纪律（沿用）**：还原一律 `cp` 快照 + `shasum -a 256` 比对，**禁止 `git checkout --`**（上一轮有人用它回滚变异，把另一个人未提交的改动一起清掉了）；改「有无变化」只认 blob 哈希，不认 `git status` 的 `M`（stat 缓存假阳性用 `git update-index --refresh` 清除）。
