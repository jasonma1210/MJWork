## 2. 架构范式 P

| 子维度 | 决策 | 理由 |
|---|---|---|
| 扩展方式 | **插件化**（双入口是同一 Harness 的两种「策略入口」，共享同一套工具/记忆/执行池） | 现有 `teams:*` / `tasks:*` / `scheduled:*` 已是同一 `task_groups` 表、同一 `workerPool`、同一 `MemoryManager`。双入口若各造一套执行器＝双份真相源，违反项目既有「单一事实来源」纪律 |
| 配置方式 | **声明式**（入口差异用一份声明式 `entryPolicy` 配置表达，代码里只有一套分流逻辑） | 「新建任务 vs 助理」的差异本质是**策略参数**（是否允许自动 DAG、是否预挂军团、是否允许 AI 建团），不是代码分支。若写成 if/else，改一处要审两处 |
| 部署拓扑 | **单机** | 现有实现全在 Electron 主进程 + 本地 SQLite。无远程派发需求 |
| 编排模式 | **中心化**（编排器 `main/orchestrator/index.js` 统一建组，Worker 池统一执行） | 现有即是中心化。保持「编排器不认识团队」的零侵入约束——团队信息只经 `planWaves` 回调的 `dag.roster` 快照透传 |

**P 的非完备声明**：以上四子维度只是常见样例，本设计的真正区分度不在标签里，而在 §7 的「复杂度判定点设计」——即**判定权归谁**这一未被标签表达的深度决策。

## 4. 六层设计

### 4.1 E 执行循环

**设计决策**

- **终止条件**：不由模型自评。沿用现有三道保险——编排组由 `main/orchestrator/dag.js` `validateDag` 的任务数约束（`MIN_TASKS=2`/`MAX_TASKS=8`）+ `invoke.js` `waitGroupSettled` 的超时 + `workerPool` 的组预算闸（`main/groupBudget.js`）。**不新增自评式终止判定。**
- **墙钟预算**：交互式沿用 `tasks.max_concurrent`（默认 4，`main.js` `initWorkerPool`）+ 每任务超时 `TOOL_TIMEOUT_OVERRIDES`；定时通道沿用 `maxRounds: 40` / `tokenBudget: 400000`（`main.js` `runScheduledAgentTask`）。
- **并行度上限**：`tasks:config` 是唯一持久化入口，模型侧 `max_agents` 被显式忽略（`main.js` `toolOrchestrateTask` 内 warn）。**本设计维持该治理方向**：复杂度判定器只给「建议」，不改并发上限。
- **失败回喂**：编排拆解失败 → `planGoal` 带 `repairHint` 回喂重试 1 次（`orchestrator/index.js` `planGoal`）；`orchestrate_task` 侧同口径（`main.js` `toolOrchestrateTask`）。**不吞异常。**
- **打转检测**：**已存在**（本次复核修正了初判）。`agent-core/index.js` 有三道重复失败熔断：`REPEAT_FAIL_WARN=2`（同「工具名+参数」签名连续失败 → 旁路注入 `renewNotice`，不污染会话历史）、`REPEAT_FAIL_STOP=4`（同签名硬熔断，`budgetExhausted=true` + `budgetKind='repeat'` 强制收尾）、`TOOL_FAIL_STOP=6`（同工具换参数重试也拦）。签名由 `toolSignature(name, args)` 计算（**对象 key 排序后序列化**，防模型换 key 顺序绕过）。轮次硬顶 `AGENT_HARD_ROUND_CAP=120`。**这三道对双入口自动生效，无需新增。**
- **流式与可中断**：交互式走 `chatStreamOnce`（`main.js`），可中止；`stopThreadWork.ts` 按 thread 过滤中止编排组。

**落地规格**

- 双入口**共用**现有执行循环，不新增执行器。
- 新增的只有一个**前置分流点**（§7.3 `entryRouter`），它决定「把这一轮交给谁」，不决定「怎么跑」。

### 4.2 T 工具注册

**设计决策**

- 沿用三档工具面（`desktop/agent-core/toolTiers.js`：`core`/`catalog`/`ondemand`）。
- **关键约束（现算发现）**：`orchestrate_task` 属 `collab` 组且 `tier: TIER_ONDEMAND`。工具表 9852 token，窗口小于 16000 或占比超过 20% 时裁剪到 core 档（16 个常开），此时**编排工具不在通告列表内**。
  - 窗口 8192 → 占比 120%（必然裁）；32768 → 30%（裁）；65536 → 15%（不裁）。**默认 32768 窗口下必然裁剪。**
  - 裁剪后 `agent-core/index.js` 会注入「可申请的能力」段（`buildToolCatalogText`），`collab` 组在 `includeOndemand` 默认 true 时**会出现在目录里**（`toolTiers.js` `buildToolCatalogText` 默认含 ondemand 组）——即模型**知道有**编排能力，但需先 `activate_tools('collab')` 才能拿到 schema。
  - **这正是「模型自动决定是否启动 DAG」在默认窗口下的真实断点**：模型要先花一轮申请工具，才谈得上决定。§7.3 的设计必须正面处理这一点。
- 凭证不进执行环境：沿用 `resolveSecret`（`main/scheduledChannels.js`）在主进程解析，Worker 与渲染层拿不到 key。
- 注册 ≠ 披露 ≠ 授权：沿用三段裁剪（capability 门 / 角色子集 / planMode）+ `toolAvailability.js` 的「通告了但调不动」剔除。

**落地规格**

- 双入口**共用**同一 `TOOL_CHANNELS`（61 条）。新增工具必须同时登记三处（`TOOL_CHANNELS` / `TOOL_HANDLER_NAMES` / `createToolHandlers`），由 `test/tool-registration-matrix.test.mjs` 门禁看守。
- 助理入口若需新增「AI 建团」工具，**必须**同时进 `TOOL_CHANNELS` 与 `TOOL_HANDLER_NAMES`，并考虑 tier 归属（建议 `ondemand`，因为误用代价高、频率低）。

### 4.3 C 上下文管理

**设计决策**

- 窗口预算：沿用 `modelWindows.js`（宿主侧）与 `agent-core` 侧现状；**本阶段不统一两套兜底**（4096 vs 32768 的口径分歧属既有 P1，见 §15-4），但**双入口不得引入第三套口径**。
- 记忆注入格式：`agent-core/index.js` 的 `sysSections.memory`，逐条过 `detectInjection`（high 严重度丢弃）+ `wrapUntrusted` 结构性隔离。
- ⚠️ **模型没有任何记忆工具**（现算确认：`BASE_TOOLS` 52 个里 `memory_*` 为零，`agent-core/index.js` 中 `name: 'memory...'` 零命中）⇒ 模型既不能自己查记忆、也不能自己写记忆，一切靠渲染层注入。**这是既有事实，双入口不改变它**；但它意味着「保证记忆能力」完全押在渲染层召回链的正确性上 —— 修 §9 P1-1 的优先级因此提高。
- 前缀稳定：记忆块内容随每轮召回变化（`memories` 由渲染层 `useEffect` 注入），**必然导致前缀重写**。现有实现已把记忆放在 system 段尾部之后（`sysSections` 追加），但**不是纯追加**——这是既有事实，双入口不改变它，也不宣称解决它。

**落地规格**

- 记忆召回的**唯一入口**是渲染层 `ChatArea.jsx` 的 `useEffect` → `localListMemories` IPC → `MemoryManager.recallContents`。**双入口必须共用它**（否则就是第二份真相源）。
- ⚠️ **现算发现的既有缺陷（不是本设计引入，但会被双入口放大）**：`ChatArea.jsx` 调用 `localListMemories({ projectPath, limit: 7, conversationId: threadId })` **不传 `query`** ⇒ `recallContents` 的 `query` 为 `undefined` ⇒ `recall()` 里 `query` 默认 `''` ⇒ `scoreMemory` 的 `relevance` 因子（权重 0.40）被跳过（`scorer.js` `hasQuery` 为假时 relevance 贡献 0 且权重按比例分摊）⇒ **实际召回的是「最近 + 高 tier」而非「与当前问题相关」**。这与 `docs/MJWork-全项目审计…` P1 小节所记一致（该文档表述为「只取最近 7 条无关记忆」）。本设计在 §9 P1 清单中列为必修项。

### 4.4 S 状态存储

**设计决策**

- 结构：任务/团队同库 `task_groups`/`teams`/`team_members`/`team_messages`；记忆独立 `memories` 表（`memory/index.js`）。
- **军团归属层级（结论）**：军团是**全局资产**。依据：`teamStore.createTeam` 的 `project_path` **可选**，注释明写「军团是跨项目复用的编制，不强制绑定项目」；`teamStore.listTeams` **不按 `project_path` 过滤**。⇒ **双入口不需要为「助理建军团 → 新建任务选用」新增任何数据模型**，两个入口读同一张 `teams` 表即可。这是本次审查最重要的减法结论之一。
- 记忆 4 层的隔离键：`session`→`conversation_id`；`team`→`team_id`(+`agent_id`)；`project`→`space_id`(= project_path)；`global`→忽略 space。依据 `memory/recall.js` `_layerRows`。
- 记忆治理：`resolveScope` 的三条硬约束（`external_content` 强制 session；global 仅 `user_input` 可写；team 必带 `teamId`）+ `trustOf` 可信度乘子（`user_input` 1.0 / `model_conclusion` 0.6 / `external_content` 0.2）。
- 外部副作用幂等：沿用 `taskStore.markEffectUncertain` + `needsRetryReview`（`ipc/tasks.js` `tasks:retryTask`）。

**落地规格**

- 助理入口的「AI 建团草案」**不落库**（沿用 `teams:draftMember` 的既有语义：只出草稿、人审后由 `teams:addCustomMember` 落库）。**不新增草案表。**

### 4.5 L 生命周期钩子

**设计决策**

- 人在回路四档，沿用 `approval.js` 的 `L0/L1/L2/L3` + 用户四档 `never/auto-safe/on-request/always`。
- **AI 自动建团的审批门强度**：本设计建议「**执行前确认**」——草案生成后必须由用户逐项确认（可编辑工具/模型/审批档/沙箱档）才落库。理由见 §10 决策点 D3。
- 高危纵深：`scheduled_create` 恒 L3 且审批结果**不落规则库**（`main/scheduledTools.js` `scheduledCreate`）；`orchestrate_task` 钉 L2（`main/approval.js` `TOOL_LEVELS`）。

**落地规格**

- 双入口共用 `main/approvalPolicy.js` 的 `hostPolicySnapshot`（审批档 + 沙箱档），不各自实现。

### 4.6 V 评估接口

**设计决策**

- 定时任务已有 V 层：`main/scheduledVerify.js`（L1 全量对账 + L3 风险门/抽样，**无人值守 fail-closed**）+ `main/scheduledVerdict.js` + `scheduledGuard.js`（对外动作默认拦）。
- 交互式对话**无独立 V 层**（无产物对账）。这是既有事实，双入口不假装解决。
- 模型裁判：当前**无**独立模型裁判环节（grep 未见）。编排组的「完成」= 子任务状态 `done`，由 `workerPool` 状态机判定，非模型自评。**这符合「终止条件不落在模型自评」的纪律。**

**落地规格**

- 助理入口的「AI 建团草案」质量校验 = **确定性校验**（`normalizeMemberInput` 的 fail-closed 枚举归一 + `capabilitiesOf` 能力摘要），不引入模型自评。

## 5. 模型组合与任务分派

- **形态判定：形态 B（单智能体 + 循环内多档模型）为主，形态 C（多智能体）按需放行。**

  | 形态 | 结论 | 理由 |
  |---|---|---|
  | A 单智能体+单模型 | **否** | 现有 `model_overrides` 已支持 compact/decompose/worker 三档；且 DAG 场景确实需要多 Agent。纯 A 既浪费已建的分档能力，也满足不了用户的「自动 DAG」诉求 |
  | B 单智能体+循环内多档 | **是（主形态）** | 「新建任务」的默认路径是单智能体对话（形态 B），分档用于「要不要先拆解」「压缩摘要」两处 |
  | C 多智能体 | **条件放行** | 已过编排决策卡（§6），且**现有实现已存在**（`orchestrate_task` + `workerPool`）。本设计不新增编排形态，只加「何时进入」的判定点 |

  **显式质疑记录**：为何不是纯形态 A？因为「模型自动决定是否启动 DAG」这一需求本身就要求存在 B/C 两种执行路径，且判定必须发生在进入执行循环之前。为何不是纯形态 C？因为简单问句走 C 会把一个自然语言问答变成多 Agent 编排（既有真机事故：「每人报数」被拆成「实现命令行报数程序」，烧 2 分钟 + 数万 token —— `teamDispatchPlan.js` `CHAT_ONLY_RULES` 的注释记录了原委）。**结论：默认 B，按判定升级到 C。**

### 任务-模型分派表

| 步骤 | 档位 | 理由 | 成本/延迟预算 |
|---|---|---|---|
| 路由判定（L1 triage） | 决策型模型（主模型，短调用；**可降级到 `model_overrides` 的便宜槽**） | 需要语义理解但输出**离散路由类别**（不是难度分）；n4n 经验：triage 用小模型、temperature=0、strict JSON | 1 次短调用，≤ 1500 in / ≤ 200 out；预算 3%（若判为 `simple_chat`，本项是唯一开销） |
| 简单对话主推理 | 强力 LLM（主模型） | 开放推理 | 主体 |
| 任务拆分草案（`multi_step_single` 路由） | 快速低价 LLM（`model_overrides.decompose`） | 结构化转换，容错空间大 | ≤ 2k in / ≤ 1k out |
| 编排拆解（`parallel_team` 路由） | 决策型模型（主模型，`ORCHESTRATOR_SYSTEM`） | 封闭 JSON 输出，可校验（`validateDag`） | ≤ 4k in / ≤ 3k out；失败回喂重试 ≤ 1 次 |
| Worker 子任务执行 | 强力 LLM 或 `model_overrides.worker` | 真实执行 | 组预算闸 `max_tokens` 默认 256k（`teamStore.js` `BUDGET_DEFAULTS`）；**团队规模上限 5**（Anthropic 3-5 经验，对标修正新增） |
| 上下文压缩 | 快速低价 LLM（`model_overrides.compact`） | 摘要 | 现有 |
| AI 建团草案 | 决策型模型（主模型） | 角色设计需语义理解，但输出 schema 封闭 | ≤ 3k in / ≤ 2k out |
| 会话摘要（记忆沉淀） | 快速低价 LLM | 结构化摘要 | 现有 |

### token 预算按档位分配

- 总预算沿用现有分档机制（`model_overrides` 三槽各自独立），**本设计不设新的全局 token 池**——现有 `workerPool` 的组预算闸（`main/groupBudget.js`）已在组级封顶。
- **评估/验证步骤计入预算**：定时任务已有（`scheduledVerify` 的 L3 抽样成本记在同一次运行内）；交互式无独立评估步骤 ⇒ 无此项增量。

### 缓存与重算账

- 记忆块每轮重取 ⇒ **前缀重写**（`memories` 变 ⇒ system 段变）。这是既有事实。
- **重写失效预算**：本设计建议在「复杂度判定」这一步**不引入任何 system 段内容**——判定结果只作为**执行器选择参数**（不走模型），从而不新增前缀重写。
- 命中率观测口径：现有 `trace` 落盘（`main/runTrace.js` `appendTraceEvent`）已记录 token 与事件；缓存命中率**当前无观测**（无 prompt-cache 观测位）⇒ 标为未知区。

### 级联升级条件

- 复杂度判定：**不级联**。判定失败（模型超时/输出非法）⇒ **降级为「不启 DAG」**（保守方向，见 §7.3）。
- 编排拆解失败：回喂 `repairHint` 重试 1 次 ⇒ 仍失败则整体失败并如实报错（`orchestrator/index.js` `planGoal`）。

### 降级链

- 主模型不可用（限流/故障/涨价）⇒ 复杂度判定降级为「不启 DAG」（继续单智能体对话，不阻断）。
- `model_overrides.decompose` 不可用 ⇒ 回落主模型（`resolveTaskModel` 既有行为：解析不出即静默回落）。
- `orchestrate_task` 通道不可用 ⇒ `toolAvailability.js` 在通告阶段就剔除它，模型不会看到；用户可手动走「助理 → 派活」。

### 评估者档位与生成者档位关系

- 本设计**不引入模型裁判**。编排组的正确性判据是子任务状态机（`workerPool`）+（定时通道的）确定性对账（`scheduledVerify`）。生成者（Worker）与评估者（状态机/对账器）**完全分离**，且评估者不看 Worker 推理过程。**满足独立性要求，且成本为零。**

## 7. 双入口信息架构设计

### 7.1 两个一级入口的职责边界

| 维度 | A「新建任务」 | B「助理」 |
|---|---|---|
| 主用途 | 一句话问答 / 小任务 | 组团 / 编排 / 定时 / 复杂任务 |
| 主交互 | 输入框 + 发送 | 面板（团队编制 + 定时 + 复杂问题发起） |
| 执行形态 | 默认单智能体；判定命中则自动 DAG | 用户显式派活或 AI 建团后派活 |
| 军团 | **可选**：从已建军团中选一个作为「本次的编制」 | **主场**：建 / 改 / 派 |
| 数字员工 | 可从「+ 菜单」拉单个员工入本次会话（既有 `PlusMenu.jsx` `experts` 面板 → `sessionExtras.expert`） | 可批量招募进军团（既有 `teams:recruit`） |
| 定时任务 | **不出现**（避免误触） | 归属此入口（既有 `ScheduledTasks.jsx` 从侧栏迁入） |
| 复杂问题 | 由模型自动判定后升级 | 用户显式选择「按团队执行」 |
| 记忆 | 4 层全生效（共用 `ChatArea.jsx` 召回链） | 同上 + 团队层（`recallTeamMemories`） |

**共用（不重复实现）**：
- 会话列表与消息持久化（`localStore` `threads`/`messages`）
- 记忆召回与注入链（`ChatArea.jsx` → `localListMemories` → `recallContents` → `agent-core` `sysSections.memory`）
- 工具面与执行循环（`agent-core` `runAgent`）
- 编排器与 Worker 池（`orchestrator` / `workerPool` / `taskStore`）
- 审批与沙箱策略（`approvalPolicy.js` `hostPolicySnapshot`）
- 数字员工目录（`ecosystem:employees`）
- 军团表（`teams` / `team_members`）——**两入口读写同一份，无第二份**

> ⭐ **「记忆是资产，不是入口的属性」**（调研 §5.3 样板 A + §6.3-13）：Claude 的统一记忆层证明「同一份记忆在两个入口都可用」是主流做法，但其「**本地 Cowork 不使用记忆**」正是警示 —— MJCode 是**本地桌面端**，若照抄「记忆只在云端共享」，本地轻入口与本地重入口之间就会天然割裂。**MJCode 作为本地应用，两个入口必须共享同一份本地记忆存储** —— 这恰恰是 MJCode 相对 WorkBuddy/Claude 的结构性优势。
>
> ⇒ 本设计因此把「记忆注入」列为**共用**而非「入口差异」，并且 §9 P1-1（补 `query` + `teamId`）的修复**对两个入口同时生效**。

### 7.2 「新建任务」里的军团选择器

**位置**：Composer 的「+」菜单已有 `legion` 面板（`PlusMenu.jsx` → `TeamDispatchPanel.tsx`），**现状即可用**：`TeamDispatchPanel` 列出未归档团队、点选回填团队徽标、`ChatArea.jsx` 的 `sendOrDispatch` 在有 `activeTeam` 时改走 `teamsDispatch`。

**因此「新建任务里可选自己的军团」这一条，源码上已实现**（`ChatArea.jsx` `sendOrDispatch` + `ipc/teams.js` `teams:dispatch`）。缺口在**三处交互语义**：

| 现状 | 缺口 | 建议 |
|---|---|---|
| 选中军团 ⇒ **强制**走派活，`sendOrDispatch` 直接 `return` 不再走普通对话（`ChatArea.jsx`：`if (!activeTeam \|\| opts) { send(...); return; }`） | 用户选了军团就不能再普通问一句 | **改为「编制偏好」而非「模式开关」**：军团徽标表示「本次任务可被该军团承接」，普通对话仍可发起；仅当模型判定需编排时才把该军团注入为 roster |
| 选中的军团**立即生效为派活**，与用户「先聊两句再决定」冲突 | 缺少「暂不派活」的中间态 | 加一个「仅作为候选编制」的中间态（见 §9 P0-3） |
| 无「临时组队」入口 | 用户想临时拉 2~3 个数字员工组成一次性编制 | 临时编制 = 一次性 roster，**不落 `teams` 表**（复用 `dag.roster` 快照机制） |

**能否覆盖自动 DAG 判定**：**能，且必须能**。用户显式指定编制 ⇒ 判定结果从「自动选编制」降级为「用这个编制」。这是 §7.3 判据的第 2 优先级。

### 7.3 复杂度判定的决策点设计（本设计的核心）

#### 现状：三套并存的「是否分步」机制

| # | 机制 | 位置 | 判据 | 触发后 | 是否多 Agent |
|---|---|---|---|---|---|
| ① | `looksLargeTask` | `agent-core/index.js`（导出，渲染层 `useAgentRun.ts` 调） | **本地正则启发式**（多词命中/分隔符+目标词/长度门槛） | 调 `decomposeTask` 出拆分计划 → 渲染层出**拆分卡片** → 用户选步骤 → **串行**逐步跑 | ❌ 否，单 Agent 分步 |
| ② | `orchestrate_task` | `agent-core/index.js` 工具 schema + `main.js` `toolOrchestrateTask` | **模型自主决定**（工具描述 + 系统提示词 `agent-core/index.js`「多 Agent 并行编排（orchestrate_task）：当用户要求多角色/多任务并行…主动调用它」） | 建 DAG 组 → 并行 Worker → 聚合 | ✅ 是 |
| ③ | `isChatOnlyGoal` | `main/teamDispatchPlan.js` | **窄规则词典**（报数/轮流说/一人一句） | 旁路 LLM 拆解，每人一句话 | ✅ 是（但极简） |

**结论（回答用户提问）**：
- **「模型自动按能力决定是否启动 DAG」= 机制 ②，它确实是模型自主触发的**，不是用户指定。触发链完整：
  `agent-core` 系统提示词 → 模型调用 `orchestrate_task` 工具 → `main.js` `toolOrchestrateTask` → `orchestrator.autoOrchestrate` → `planGoal`（LLM 拆 DAG + `validateDag` 校验）→ `workerPool.runGroup` → `invoke.js` `waitGroupSettled` 聚合 → `humanizeGroupResult` 回主 Agent。
- **`teamDispatchPlan.js` 的 `mode`（`lead`/`select`）与复杂度判定无关**。它是**协作模式**：是否预置指派表。`mode` 的来源是 `team.defaultMode`（`teams:dispatch` 时 `store.updateTeam` 落库为团队默认值）或 payload 显式值 —— **由用户/团队配置决定，不由模型决定**。
- **机制 ① `looksLargeTask` 是唯一存在的「复杂度判定器」，但它判的是「要不要出拆分卡片」，不是「要不要启 DAG」，且产出是单 Agent 串行分步。** 二者当前**不连通**：命中 `looksLargeTask` 只会出卡片，卡片确认后走 `Composer.tsx` 的 `onSend(task.prompt, undefined, {skipDecompose:true, planStep:ps})` —— **`skipDecompose:true` 明确跳过了后续判定**，全程单 Agent。
- **因此「模型按复杂度自动启 DAG」这件事，目前是「模型自己决定要不要调这个工具」，而不是「系统按复杂度判定要不要给它这个工具」。** 差别很实际：工具在默认 32768 窗口下会被裁到 core 档（§4.2 现算），**模型得先 `activate_tools('collab')` 才拿得到 `orchestrate_task` 的 schema**；且系统提示词里那句引导是**软约束**。

#### 本设计的判定点设计

**决策点位置：main 进程（renderer 之上、agent-core 之下），在 `agent:run` 之前。**

```
renderer (新建任务) 
   → IPC: agent:run
      → main: entryRouter.run()   ← 判定点在这里
         ├─ 命中「需要编排」→ 走编排路径（带 roster）
         └─ 未命中         → 走普通单 Agent 对话（agent-core runAgent）
```

**为什么不放 renderer**：renderer 判定 = 用户界面层做语义决策，不可测、不可审计、无法在无人值守（定时）通道复用；且 renderer 拿不到模型能力信息。
**为什么不放 agent-core**：agent-core 是模型循环内部，塞判定器会让「模型自决」与「系统判定」两个决策源互相污染（模型可能绕过或重复触发）；且 `orchestrate_task` 已由模型自决，叠一层会让行为不可预测。
**为什么不放 worker/模型侧**：模型侧就是机制 ②，已存在；本设计要补的是**系统侧的前置闸**，两者职责不同——系统侧决定「是否把编排能力暴露给模型」，模型侧决定「拿到能力后用不用」。

#### 判据：结构化启发式 + 离散路由类别（两层）

> **对标修正（2026-10-24，依据 `docs/harness-review/01-research/对标调研简报` §4.3 / §4.6）**：本节初版写的是「复杂度判定 + `needDag` 布尔 + `scale` 数字」。调研给出的两条硬证据要求改口径：
> ① **Google DeepMind + MIT《Towards a Science of Scaling Agent Systems》**（arXiv:2512.08296，Nature MI）：可分解任务多 agent **+80.8%**，但**顺序规划任务 −70.0%**；且「architectures without centralized verification tend to propagate errors more」；官方建议「start with a single agent. Only switch to multi-agent systems when **the task splits into independent pieces** and single-agent success stays below 45 percent」。
> ② **OpenAI《A Practical Guide to Building Agents》** + n4n triage 经验：「**Don't ask the triage model to score 'difficulty 1-10'. Use discrete routing classes that map directly to model choices and system prompts. Discrete classes are easier to evaluate and harder for the model to hedge.**」
>
> ⇒ **判据从「复杂度」改为「任务结构」，输出从布尔改为离散路由类别。**

**L0 规则层（确定性代码，零成本）—— 判据是结构，不是长度**

| 结构信号 | 判据来源 | 动作 |
|---|---|---|
| 子任务是否**可真正并行**（互不改变对方依赖的状态） | arXiv 摘要「architecture-task alignment determines collaborative success」 | ✅ 允许升级 |
| 是否**强顺序依赖**（改 A 的状态会改变 B 所需状态） | arXiv 摘要：顺序规划 **−70.0%** | ❌ **禁止**升级 |
| 需要调用的**工具种类数** | 【社区】阈值 ~16 | ⚠️ ≥16 ⇒ 降级单 Agent |
| 是否需要**中心化验证**（汇总时要交叉核对） | arXiv 摘要第 3 条 | ✅ 优先 centralized/manager 拓扑 |
| 对话型目标（`isChatOnlyGoal`） | 现有 `teamDispatchPlan.js` | ❌ 直接判「不启」 |
| 用户显式选了编制/军团 | 用户意图 | ✅ 直接判「启」 |

**其中前三条可在运行时用启发式直接算**（并行度、工具数、依赖图深度），只有「基线正确率」需离线评测积累 ⇒ **本设计可先落地不依赖训练的结构化判据**。

**L1 模型层（决策型模型）—— 输出离散路由类别，不打分数**

| 路由类别 | 含义 | 执行路径 |
|---|---|---|
| `simple_chat` | 单 Agent 对话 | 现有 `agent-core.runAgent` 直连 |
| `multi_step_single` | 单 Agent 多步（要拆分但不需要并行） | 复用现有 `looksLargeTask` → `decomposeTask` → 拆分卡片 → 用户确认 → 串行分步（**这条路径已存在且已联通**） |
| `parallel_team` | 可并行分解 ⇒ 自动 DAG | `orchestrate_task` / `teams:dispatch` |
| `manual_team` | 适合组队但需人工编排 | 提示用户去助理页组装（**不自动建组**） |
| `scheduled` | 应做成定时任务 | 引导到助理页定时任务视图（**不自动创建**） |

**L1 只在 L0 判「不确定」时调用**，一次短调用（≤1500 in / ≤200 out），输出严格 JSON `{"route":"...","reason":"...","confidence":0.0-1.0}`。

**为什么兜底方向是「不启 DAG」**：arXiv 的量化结论显示多 agent 在**顺序任务上退化 39%–70%**，且无中心化验证时误差放大 **17.2×**（中心化协调压到 4.4×）⇒ **误启的代价显著高于漏启**。

**为什么必须做离散分类而不是让模型自由判断**（Claude Code 官方做法即如此：文档写「Claude decides whether to spawn teammates based on the task」但**不公开任何数值阈值**）：离散类别可被 eval 量化、可回归测试；打分（1-10）难评估且模型会「对冲」（hedge）。

**可见的升级/降级提示（必做）**：调研 §6.2-9 指出 Claude Code 官方承认 subagent 与 teammate 混在同一面板无法区分 ⇒ MJCode 不应重复。至少要有「**已升级为 N 人团队执行**」与「**已降级为单 Agent 执行**」的可点入口（走 UI 事件，**不进 system 段**，见 §4.3 前缀稳定约束）。

**团队规模硬上限 3–5**（Anthropic「3-5 个 subagent 并行」「3 个专注队友常胜过 5 个散的」）。现有 `dag.js` 的 `MAX_TASKS=8` 是**DAG 任务数**上限，与**团队规模**不是一回事；本设计另设 `teamSize` 上限 5（配置项 `entryPolicy.new.autoDag.maxTeamSize`）。

**成本护栏**：调研 §6.2-12（Anthropic 报 4×/15× token 倍数）⇒ UI 上明示「本次升级为团队执行，token 消耗约为单 Agent 的 N 倍」，并提供上限。现有组预算闸 `groupBudget.js`（`BUDGET_DEFAULTS.max_tokens=256000`）是执行侧硬闸，**UI 提示是缺失的一环**。

**中心化验证环节（预留）**：调研 §6.2-11（arXiv：无中心化验证的拓扑误差传播更严重）⇒ 现有 `invoke.js` `humanizeGroupResult` **直接聚合成员结论、无交叉核对**（本设计 §6 已列为既有缺口）。**本阶段不新增该环节**（会改 `orchestrate_task` 的返回语义，属独立议题），但落地清单中标注为「已识别、建议下一轮」。

#### ★ 用户确认点：判据不可完全自动化 ⇒ 必须保留人在回路

> **主理人硬约束（2026-10-24）**：「『模型自己判定复杂度 → 自动升级为团队执行』目前**没有可靠的公开硬判据**。主流做法是『模型内建判定 + 显式确认点』双轨（Claude Code 文档写明 Claude 自行决定是否 spawn teammates 但**不公开阈值**；Devin **先给方案给人批准再启动团队**；Codex 多数级别**只在用户明确要求时才派生 subagent**）→ 请按『**判据不可完全自动化 → 必须保留用户确认点**』的方向设计，给出**具体确认点的位置与形态（何时不问、何时问、问了给什么信息）**。」

**本设计的处置（与 D2 并列，不是替代）**：判定器**只决定「要不要问」与「问什么」**，**不代替用户按下执行**。凡判定为 `parallel_team` 且命中下表「需确认」条件 ⇒ **先出确认卡，用户点「执行」才真正建组**。

**确认点的三档形态（按代价分档，不是二选一）**：

| 档 | 触发条件 | 形态 | 用户看到什么 | 用户要做什么 |
|---|---|---|---|---|
| **C0 静默执行** | ① 用户**已显式选了编制/军团**（意图已表达）；或 ② 规则层高置信（可并行信号命中 + 无顺序依赖 + 工具种类 < 8 + 预计规模 ≤ 3）；或 ③ 用户在设置里开启「自动升级（不再询问）」且本次为高置信 | 直接执行，**事后**给一条可点提示 | 「已升级为 N 人团队执行 · 约 N 倍 token」（可点查看/中止） | 不做动作；事后可撤销 |
| **C1 确认卡**（**默认档**） | 判据为 `parallel_team` 但**置信度中档**（可并行信号命中但工具种类 8–16，或需中心化验证，或规模估计 4–5），且用户**未显式选编制** | **先出卡，不建组** | 三件事：① **拟并行拆分的子任务清单**（每条一行标题 + 依赖关系）；② **为什么建议用团队**（一句人话理由 + 判据来源：可并行/顺序依赖/工具数/需交叉核对）；③ **代价**（预计 N 人、token 约 N 倍、预计墙钟） | 点「**按这个执行**」/「**改成单 Agent**」/「**看细节**」 |
| **C2 阻断+引导** | 判据为 `manual_team`（适合组队但需人工编排）或 `scheduled`（应做成定时任务） | **不执行**，只给引导 | ① `manual_team` ⇒「建议去助理页组建团队」+ 跳转按钮（**不自动建组**，成员构成需人来定）；② `scheduled` ⇒「这条适合定时跑」+「创建定时任务」按钮 | 点引导或忽略 |

**何时不问 / 何时问（明确判据表）**：

| 情况 | 档 | 理由 |
|---|---|---|
| 用户显式点了「按团队执行」/ 选了编制 | **C0** | 意图已表达，再问是烦人（对应 Codex「只在用户明确要求时才派生」） |
| 规则层高置信（可并行 + 小规模 + 工具少） | **C0** | 误判代价低（多花点 token），打扰代价高 |
| `parallel_team` 且置信度中档 | **C1** | **主要收益区间**（真需要多 Agent），也是**误判代价最高**处 ⇒ 必须问 |
| `parallel_team` 但**强顺序依赖**命中 | **直接降级 C0（单 Agent），不问** | arXiv 量化：顺序任务多 agent **−70%** ⇒ 不该问、更不该自动做 |
| `parallel_team` 且**工具种类 ≥ 16** | **C1 偏保守**：卡片里建议「单 Agent 或只读子代理」 | 社区阈值：工具密度高时多 agent 开销更大 |
| `simple_chat` / `multi_step_single` | **不问** | 单 Agent 路径无额外代价（`multi_step_single` 已有既有的拆分卡片，本就是确认点） |
| `manual_team` / `scheduled` | **C2** | 不是「要不要用团队」，而是「这条该走别的路」⇒ 引导而非确认 |
| **判定失败 / 超时 / 输出非法** | **不问，走 C0 单 Agent** | 失败时追问用户等于把系统故障转嫁给用户 |

**确认卡的信息规格（最小但够决策）**：

```
┌ 建议用 3 人团队执行此任务 ──────────────────────┐
│ 原因：拆出的 3 项互不依赖，可并行（顺序依赖检查：通过）│
│                                                 │
│ ① 梳理现有鉴权代码的调用链          （无依赖）    │
│ ② 核对各接口的越权风险              （依赖 ①）    │
│ ③ 汇总成一份风险清单                （依赖 ①②）  │
│                                                 │
│ 代价：约 3 人 · token 约 3 倍 · 预计 2–4 分钟     │
│                                                 │
│ [ 按这个执行 ]   [ 改成单 Agent ]   [ 看细节 ]     │
└─────────────────────────────────────────────────┘
```

**关键纪律**：
- **确认卡里的子任务清单必须是「已经拆好的」**，不是「打算怎么拆」——否则用户确认的是一句话、执行的却是另一份计划（经典形态：用户以为确认了 A、实际执行了 B）。⇒ **拆分必须在确认卡之前完成**。
  - ⚠️ 这与「系统侧不建组」的纪律有张力：**拆 DAG ≠ 建组执行**。本设计允许判定器在出卡前**预拆 DAG**（需从 `orchestrator.planGoal` 拆出「只拆不建」的纯拆解路径），**建组与执行仍只在用户点「按这个执行」后发生**。
- **用户点「改成单 Agent」⇒ 本轮不升级**，且**不重复追问**（同一会话内对同一目标只问一次）。
- **确认卡是 UI 事件，不进 system 段**（保前缀稳定，见 §4.3）。
- **无人值守通道（定时任务）没有确认点** ⇒ 定时任务必须**预先声明**用哪支团队（`team_id`）与预算，走既有 `scheduledGuard` 的 fail-closed 闸，**不得在无人值守时静默升级**。

**这条与 D2 的关系**：D2 决定「**判定权归谁**」（系统侧前置闸 + 模型侧自决并存）；本节决定「**判定之后谁能按下执行**」（用户）。两者合起来才是完整答案：**系统负责「判断得准 + 说清为什么」，用户负责「授权执行」**。这也正好回应调研 §6.2-9「必须有可见的升级/降级提示」——确认卡就是那个提示的强形式。

#### 与模型自决（机制 ②）的关系：并存，不互斥

**关键设计点**：判定器**不否决**模型调用 `orchestrate_task` 的能力。
- 判定器命中「需要编排」⇒ **主动**把编排工具**提前放进工具面**（跳过裁剪），让模型不必先 `activate_tools` 就拿得到 schema；并可**预置编制**（若用户选了军团）。
- 判定器判「不需要」⇒ **不**移除 `orchestrate_task`（模型仍可自决），但**不预热**。
- 两者都命中（判定器说需要、模型也调了）⇒ 走同一条编排路径，**不重复建组**（判定器的预热只做「工具面 + 编制预置」，不做建组）。

**这样既满足了「模型自动决定」，又不把决策权从模型手里夺走。**

#### 与「两个门」的架构不变量（对标修正）

调研 §5.1（Octomind「One Product, Two Front Doors」团队自己的复盘）给出的四条不变量，本设计逐条落为**架构约束**：

| 不变量 | Octomind 原文要点 | 本设计的落点 |
|---|---|---|
| **一个 board 只改导航/落地页/词汇，别的一律不改** | 「A board changes navigation, landing screen, and vocabulary. Nothing else.」「If we ever need to build a screen twice, the split was wrong.」 | 本设计**零新增执行器**、零新增记忆链、零新增编排路径（§14「不需要改动的文件」清单即为证据） |
| **无不对称状态** | 「Chat 里创建的东西在 Studio 完全可见可编辑，反之亦然」 | 军团/任务/定时计划**同一张表、同一套 IPC**（§7.5）；⚠️ **现状已有一处违反**：`TeamDispatchPanel`/`TeamsPage` 不订阅 `teams:event` ⇒ 新建军团在另一视图不可即时见（§17 U3），**必须修** |
| **board 不是计划也不是权限（deep link 两边都能解析）** | 「every board-conditional in our code governs presentation only, and one that ever gates a capability is a bug」 | 本设计的入口分支**只允许影响呈现层**（§7.1 + §11）；⚠️ **现状有一处接近违反**：`ChatArea.jsx` `sendOrDispatch` 里「选中军团 ⇒ 强制派活、直接 return」——**这是一个入口分支在 gate 能力**（普通对话被阻断）。本设计的 P0-6 正是修这一条 |
| **一键切换、无确认弹窗** | 「A switch you can't undo in one click isn't a preference, it's a trap」 | 入口切换只改 `App.jsx` 的 view state，零弹窗（§14 P0-3） |

**并且必须预留「合并回单面板 + 底部 Advanced 行」的收敛路径**（调研 §5.1：Octomind 2026-09 已把两个 board 合并回一个、Studio-only 能力收进侧边栏底部一个 Advanced 行）。本设计的前置条件是：**只要两入口读写同一张表、同一条执行栈，合并就只是把 `AssistantPage` 的 Tab 降级为侧边栏底部的一个入口行**——不需要重写。因此 §14 的落地清单刻意**不引入任何「入口专属的数据结构」**，这就是为收敛留的余地。

**另有两个来自 Octomind 的具体踩坑，本设计已提前规避**：
- **「默认值在用户脚下翻转」**：MJCode 的「新建任务」会**自动创建工作空间**（`useAgentRun.ts` 的 `createProject` 调用）⇒ 若将来引入「入口偏好」，必须**一次性计算并持久化**，不能每次重新判定。
- **「unfetched means unknown」**：空状态渲染不得用「有把握的猜测」—— legion 面板在 `teamsList` 返回前应渲染空/骨架，而不是先画一个可能错的默认军团。

### 7.4 「助理」的两条路径

#### 路径 ①：自己组建（可视化编辑）

**现状已具备**：`TeamsPage.tsx`（军团编制页）—— 卡片列表（军团全局可见）、新建团队（`name`+`description` 必填，`projectPath` 可选=工作目录）、两个等效的成员入口（生态中心「招募」/ 自定义描述）、多成员后显示温和「缺统筹」标签、指定统筹（全局唯一）、团队预算编辑、消息总线时间轴、团队调试面板。

**缺口**：无。**该路径是纯 UI 重组**——把 `TeamsPage` 从侧栏一级导航**搬进「助理」入口内部**，成为助理的默认子页。

#### 路径 ②：AI 自动组建（输入需求 → 成员草案 → 用户确认 → 落库）

**现状已具备（部分）**：
| 环节 | 现状 | 位置 |
|---|---|---|
| 描述 → 成员草稿 | ✅ 有：`teams:draftMember`（`ipc/teams.js`），`DRAFT_SYSTEM` 提示词产出 `{name, systemPrompt, tools[], approvalPolicy, sandboxPolicy, skillNames}`，`normalizeMemberInput` fail-closed 归一 | `ipc/teams.js` `teams:draftMember` |
| 草稿 → 落库 | ✅ 有：`teams:addCustomMember` | `ipc/teams.js` |
| 渲染层接线 | ✅ 有：`TeamMemberModal.tsx` 调 `api.teamsDraftMember` | `renderer/src/components/TeamMemberModal.tsx` |
| AI 造**数字员工资产**（落 `ecosystem/employees/<id>.json`） | ✅ 有：`teams:draftEmployee`（`EMPLOYEE_DRAFT_SYSTEM`）+ `ecosystem:employeeCreate` | `ipc/teams.js` / `ipc/ecosystem.js` |

**缺口（这是「助理自动建团」的真实差距）**：

| # | 缺口 | 性质 |
|---|---|---|
| G1 | **一次只生成一个成员**。`teams:draftMember` 的入参是 `description`（单数），产出单个 draft。**没有「输入一句需求 → 产出整支团队（N 个成员 + 统筹）」的入口** | 需要新后端能力（一次生成 N 个成员的草案） |
| G2 | **成员来源单一**：AI 草案一律走 `source: 'custom'`（`ipc/teams.js` `teams:draftMember` 里 `normalizeMemberInput({...raw, source:'custom'})`），**不会从 51 个数字员工目录里挑**。用户要的「AI 帮我构建团队成员」通常应优先复用目录 | 需要新后端能力（目录匹配 + 混合来源） |
| G3 | **草案没有覆盖度校验**：不检查「这套成员能不能干这个活」（如需求要联网但无成员有 `web` 工具） | 需要新后端能力（确定性覆盖度检查） |
| G4 | **没有草稿的暂存/多轮迭代**：草案只在 IPC 返回里活一次，用户改了描述要重来 | 纯 UI 编排（可在渲染层 hold） |
| G5 | `rolePolicyData.json` 只含**审批/沙箱档位顺序与默认值**（`approval.order`/`sandbox.order`/`snapshot`），**不含任何角色定义或角色库** ⇒ 「AI 建团」时模型能给的工具集上限只有 `DRAFT_SYSTEM` 里写死的 8 个抽象别名（read/write/edit/bash/grep/glob/web/browser） | 需要新增数据（角色预设库）或明确接受该上限 |

**成员从哪来（结论）**：**混合，且目录优先**。
- 优先：`ecosystem:employees` 目录 51 条（已含 `system_prompt`/`tools`/`starter_skills`/`approval_policy`/`sandbox_policy`/`default_model_tier`）——经 `resolveEmployeeById` + `buildEmployeeRuntimePreset`（`main/ecosystem.js`）转换成 `rolePreset`。
- 次之：模型自由生成（`source:'custom'`），走既有 `teams:draftMember` 的 `DRAFT_SYSTEM`。
- 混合产出：一次草案里每个成员带 `source: 'template' | 'custom'` 与 `templateRef`。

**来源标记与优先级（对标补充）**：调研 §6.3-18 指出「预置数字员工目录 + 用户自建军团并存」需要明确的来源标记与优先级，WorkBuddy 的处理方式（「分享给成员的专家是副本，不影响你的配置」）可直接参考。
⇒ 本设计的落地口径：**预置目录项只读**（用户改了就是「派生副本」，不污染目录）；**用户自建的军团优先**（同名冲突时自建胜出）。落库字段上，成员的 `source`（`'template'`/`'custom'`）+ `templateRef` 已能承载来源标记，**无需新增列**；「派生副本」通过 `source:'custom'` + `templateRef` 指向原员工实现（快照语义：模板日后被改不影响已落库成员）。

#### AI 建团的交互形态：对标修正（表单 vs 对话）

调研 §6.3-17 指出：**「AI 自动构建团队」的交互形态已有生产验证 —— WorkBuddy 用「创建对话 + 内置管理工具引导」而非表单**。

**本设计的修正**：**主形态改为「对话式引导」，表单降级为「精细编辑」**。

| | 对话式引导（主形态） | 表单（辅助） |
|---|---|---|
| 形态 | 用户在助理页输入一句需求 ⇒ 模型在**对话中**逐步提议成员（3~5 人）⇒ 用户逐条「要/改/换」⇒ 确认后落库 | 已有 `TeamsPage.tsx` 的「加成员」弹窗（`TeamMemberModal.tsx`），供需要精确改工具/审批档/沙箱档时用 |
| 落点 | 复用 `teams:draftTeam`（新增，产出 N 个草案）⇒ 渲染层以**对话气泡 + 草案卡片**呈现 ⇒ 每条可「采纳/编辑/否决」 | `TeamMemberModal.tsx` 现有表单 |
| 为什么 | 用户的真实表述是「我要一个能查资料+写报告的小组」，不是「先填 8 个字段」；表单把用户的表达翻译工作推给了用户 | 表单适合**精确微调**，不适合**首次表达** |

⇒ 落地：`AiTeamBuilder.tsx` **不是一张大表单**，而是「一句话输入 + 草案卡片列表 + 逐条操作」；`TeamMemberModal.tsx` 的既有表单保留为「编辑单个成员」的下钻。

⇒ **与「工作台/工作区」的资产归属对齐**：调研 §6.3-14「军团是**任务的属性**，不是会话的不可逆状态」（WorkBuddy「切换专家需开启新对话」是反面教材）⇒ 本设计**不做**「切换军团 ⇒ 强制新会话」；军团选择是**会话级编制偏好**（随 thread 持久化，可随时改），不锁死会话。

#### 审批门在哪

**在 `ipc/teams.js` 与渲染层之间**：草案**只出草稿不落库**（现有语义），用户确认后由既有的 `teams:addCustomMember` / `teams:recruit` 落库。**不新增审批机制**，只把现有语义扩展到「N 个成员一次性确认」。

**这意味着「AI 自动建团」的落库路径 100% 复用既有 IPC，新增面只在「一次生成 N 个草案 + 目录匹配」。**

### 7.5 资产共享模型

**结论（直接回答用户提问）**：

> **军团是全局资产，不需要改数据模型。**

依据（三条源码事实）：
1. `teamStore.createTeam`：`project_path` **可选**，注释明写「军团是跨项目复用的编制，不强制绑定项目；留空 = 全局团队（任意项目/会话都能在 `+` → 军团里看到并派活）」。
2. `teamStore.listTeams`：**不按 `project_path` 过滤**，注释明写「军团是跨项目复用的编制…任意项目/会话看到的都是同一份列表」。
3. `ipc/teams.js` `teams:list` 与 `TeamDispatchPanel.tsx`：均不按项目过滤，注释标「军团全局可见（2026-10-20 用户反馈修正，原 D1『按项目归属过滤』已废弃）」。

**因此**：助理里建好的军团，在「新建任务」的 `+` 菜单 legion 面板里**立即可见**（同一张 `teams` 表、同一 `teams:list` IPC），**零改动**。

**唯一需要补的是「助理新建后，新建任务侧要立刻感知」**：已核实 `ipc/teams.js` `teams:create` 会调 `broadcastSystem(team.id, 'teamCreated', team.name)`（写一条 team_message 到总线并经 `emitTeamsEvent` 广播），**但那是一条消息事件，不是列表失效事件**；`TeamDispatchPanel.tsx` 只在挂载时 `teamsList` 拉一次、**不订阅 `teams:event`**，`TeamsPage.tsx` 同理 ⇒ 两个视图同时在场时新建的军团不会即时出现在 legion 面板（详见 §17 U3）。

### 7.6 「助理」与「定时任务」的关系

**结论：定时任务归属「助理」，且应支持复用军团。**

**现状**：
- 定时任务目前挂在**侧栏一级导航**（`Sidebar.jsx` `scheduled` 项 → `App.jsx` `showScheduled` → `ScheduledTasks.jsx` 组件）。
- 执行走 `scheduler.runTask` → `execCtx.runAgentTask` = `main.js` `runScheduledAgentTask` → `agent-core.runAgent`。
- **定时通道已经有 `orchestrate_task`**：`main.js` 里 `orchestrateTask: (a) => toolOrchestrateTask({...a, cwd: rc.dir}, {signal, conversationId: 'scheduled:${taskId}', projectPath: rc.dir})`。这是 2026-10-21 补的（`main/scheduledOutput.js` 注释：「定时通道此前只有 23 个工具、没有 orchestrate_task」）。

**关键限制（现算 + 读码确认）**：

| 限制 | 证据 | 后果 |
|---|---|---|
| **定时任务不能复用军团** | `scheduledTools.js` `scheduledToolHandlers` 的 `teamTools` 默认 `null`，`teamTools` 只在**成员任务**（workerPool 的 `createToolHandlers`，`main.js`）注入。`scheduler.js` 全文件 grep `team`/`teamId`/`roster` **零命中** | 定时任务里 `orchestrate_task` 建的是**匿名 Worker 组**，无 roster、无成员人格、无 team 记忆 |
| **定时任务无记忆注入** | `main.js` `runScheduledAgentTask` 的 `runAgent` 参数里**没有 `memories`**（grep 确认） | 定时任务不继承 4 层记忆 |
| **`scheduledChannels.js` 承载不了「定时跑团队」** | 该文件职责是**模型调用通道**（`scheduledChatOnce` 非流式纯文本 / `scheduledAgentChat` 非流式带工具），管凭证解析（`resolveSecret`）、超时（`createStreamGuard`）、配额（`quota.acquire('fg')`）、信号级联（`AbortSignal.any`）。**它不决定「这次跑哪些工具」** | 要「定时跑团队」，需改的是**工具面装配**（给定时通道注入 `teamTools` + 让编排走 `teams:dispatch` 语义带 roster），**不是**改 channels。**channels 层无需改动** |
| 定时任务的 V 层 fail-closed 会对团队模式生效 | `scheduledGuard.js` 对外动作默认 block；`scheduledVerify.js` 无人值守 fail-closed | 团队模式下同样适用（安全，不冲突） |

**「定时跑一个团队」的可编码路径（推荐方案）**：
1. 定时任务表加一列 `team_id`（可选）。`scheduler.createTask` 已有 `expects_file` 等可选字段的先例（`scheduler.js` `createTask`），加列是同型改动。
2. 执行时：若 `t.team_id` 存在 ⇒ 走 `teams:dispatch` 的编排路径（带 roster 快照、`team.defaultMode`、`team.budget`），而非 `orchestrate_task` 的匿名路径。
3. `runScheduledAgentTask` 的 `toolHandlers` 注入 `teamTools`（来自 `createTeamToolHandlers`）+ `memories`（走 `recallContents` 带 `teamId`）。
4. V 层不变（`scheduledVerify` 仍对账团队产出目录）。

#### 定时任务的形态：触发器属性 vs 独立产品域（对标修正）

调研 §5.3 给了两个正面样板与一个反面：

| 样板 | 做法 | 对 MJCode 的含义 |
|---|---|---|
| **Codex Thread automation**【官方文档】 | 「线程自动化可以在预定时间唤醒**同一个线程**，同时保留对话上下文」 | 定时任务**不新建会话**，而是唤醒既有线程 |
| **Devin Scheduled Sessions**【官方文档】 | 定时 session **继承原 session 的 prompt**；多次运行之间**携带状态**（读写真实笔记，每次在上次基础上继续） | 定时任务可绑定到**某条已有会话/任务** |
| **WorkBuddy 定时任务**（反面）【官方文档】 | 做成第 5 个一级入口 ⇒ 用户要理解「本地/项目/云端」三种来源和**两套权限模型**，且项目来源的任务在定时任务页**只能查看、不能编辑** | 「定时任务作为独立产品域」的代价是可枚举的 |

**本设计的修正结论**：
- **定时任务是「触发器」，不是独立产品域**。同一条任务可被 cron / 事件触发。
- **编辑权始终在任务本身**；助理页只提供**跨任务的定时列表与治理视图**（满足用户「助理统一查看与治理」的意图，同时避免「两个入口都能改同一份资产」的非对称状态 —— Octomind 不变量 2）。
- ⭐ **推荐新增「把当前这条会话/任务变成定时任务」**（对应 Codex 的 Thread automation）：与 MJCode 现状「定时任务是独立的 `prompt` 文本」不同，这条路径让定时任务**继承会话上下文**，且执行结果**回写原会话**而非落到别处。
  - 落地：`scheduledStore` 的 task 增可选 `thread_id`（会话 id），执行时把该会话的历史与记忆一并装入（`localStore` 取 messages + `recallContents` 带 `conversationId`），产出**回写该会话**。
  - 现状对照：`scheduler.createTask` 只有 `prompt` 字段、无 `thread_id`；`runScheduledAgentTask` 的 `runAgent` 参数里也没有 `messages`（只有 `[{role:'user', content: prompt}]`）⇒ **该能力完全缺失**。
- **「项目来源的任务在定时页只能看不能改」是反面教材** ⇒ 本设计的定时列表**必须可编辑**（编辑走既有 `scheduled:save` IPC）。

#### 「定时任务」与「助理」的归属（对标修正）

调研 §5.3 样板 C（WorkBuddy 反面）与 §6.3-15 一致：「定时任务 = 触发器 + 统一管理视图，不是独立产品域；任务编辑权归任务；助理页提供跨任务的定时列表与治理」。

⇒ **本设计的 D5 修正为**：
- 定时任务**从侧栏一级导航移入助理页**（Tab3）—— 满足用户「助理承担定时任务」的明确诉求；
- 但**它是助理页的一个「管理视图」，不是助理的专属资产** ⇒ 编辑权走既有 `scheduled:*` IPC，与普通任务同源，不引入「助理专属的定时任务表」；
- **预留**：若将来要让「新建任务」也能建定时任务（Codex 的 Thread automation 形态），两个入口操作的是**同一份 `scheduledStore` 数据** ⇒ 天然满足 Octomind 不变量 2「无不对称状态」。

## 11. 层间交叉检查

| 关系 | 说明 |
|---|---|
| E ↔ T | 判定器命中「需编排」时**必须**把 `orchestrate_task` 从 ondemand 提升为可见（否则模型拿不到 schema，判定形同虚设）。**这是 E/T 交叉上最容易被忽略的一环** |

## 13. 生产级必答项

| # | 必答项 | 结论 |
|---|---|---|
| 1 | 执行环境：工具在哪跑、凭证是否进执行环境 | 工具在主进程（`main/tools/exec.js` 等）或引擎子进程（`engineProcess/host.js` utilityProcess）。**凭证不进执行环境**：key 只在主进程经 `resolveSecret`（`main/scheduledChannels.js`）解析为 HTTP 头，Worker/渲染层拿不到。**双入口不改变此约束**——定时任务走 `scheduledAgentChat`（同一 `resolveSecret`），助理建团走 `chatOnce`（同一 `resolveSecret`） |
| 2 | 错误回喂：失败如何作为观察回到上下文、如何分类恢复 | 编排拆解失败 → 回喂 `repairHint` 重试 1 次（`orchestrator/index.js` `planGoal` / `main.js` `toolOrchestrateTask`）。**分类**：模型错误（带纠正重 prompt）/ 瞬时（`chatWithRetry` 退避）/ 永久（能力门 `NO_TOOL_CAPABILITY` 直接拒，不重试）/ 资源（超时 → 整组强停）。**判定器调用失败属「资源」类 ⇒ 不重试，直接降级为不启 DAG** |
| 3 | 打转检测与熔断：如何识别原地打转、如何打断 | **已存在，三道**（`agent-core/index.js`）：① `REPEAT_FAIL_WARN=2` —— 同「工具名+参数」签名连续失败 2 次 ⇒ 旁路注入 `renewNotice`（写 `renewNotice` 而非 `convo`，**不污染会话历史**）；② `REPEAT_FAIL_STOP=4` —— 同签名连续失败 4 次 ⇒ `budgetExhausted=true` + `budgetKind='repeat'` 强制收尾；③ `TOOL_FAIL_STOP=6` —— **同工具换参数**重试也拦（2026-10-21 真机事故：换命令重试 20 轮烧 257k token）。签名由 `toolSignature(name, args)` 计算（**key 排序后序列化**，防换 key 顺序绕过）。轮次硬顶 `AGENT_HARD_ROUND_CAP=120`。另有 `main/verifyPolicy.js` 的任务级熔断（连续失败自动暂停，针对定时任务）。**双入口自动继承，无需新增** |
| 4 | 记忆治理：可信度、归属、失效条件 | 可信度：`SOURCE_TRUST`（`user_input` 1.0 / `model_conclusion` 0.6 / `external_content` 0.2 / `compressor` 0.6），`trustOf` 为唯一口径；低于 `TRUST_THRESHOLD=0.6` 默认不进注入。归属：`scope` × `space_id`/`conversation_id`/`team_id`/`agent_id`。失效：`is_valid=0` + 物理删除宽限 7 天 + 半衰期（session 7 / team 30 / project 30 / global 90 天）+ `promoteToLongTerm` 人工固化 + `invalidate` 手动作废。**未验证的推测（会被丢弃）不得因「写进记忆」升级为事实** —— 现有 `promoteScope` 要求 `user_input` 来源才能升 global，方向正确 |
| 5 | 外部副作用幂等：幂等键 / 状态查询 / 恢复策略 | 既有：`taskStore.markEffectUncertain` + `needsRetryReview`（`ipc/tasks.js` `tasks:retryTask`）——有未确认副作用时必须用户显式确认才重试。定时任务另有 `scheduledGuard.js`（对外动作默认 block）+ `scheduledReplay.js`（待确认动作一键执行）。**双入口新增的外部副作用**：AI 建团落库（写 `team_members`）——幂等键建议用 `draftId`（草案 id）+ `teams:addCustomMember` 的 `templateRef` 去重；**状态查询**：落库后 `teams:get` 读回；**恢复**：草案未确认 = 无副作用，无需恢复 |
| 6 | 证据版本绑定：验证结论如何绑定版本、版本变更后如何失效 | 编排侧已有：run 级**名册快照**（`teamRoster.js` `snapshotRoster` 随 `dag_json` 落库，运行期只读快照 ⇒ 团队中途改配置不影响本次 run）——这是「事实绑定到版本」的既有实现，**双入口沿用**。定时任务侧：`scheduledVerify` 的对账绑定产出目录与本次 run 的 trace（`runTrace.js` `appendTraceEvent` 用 runId 落盘，不被同任务的多次运行覆盖）。**未覆盖**：AI 建团草案若引用了某个数字员工模板，模板被改后已落库成员**不会**跟着变（快照语义），需在 UI 明示 |
| 7 | 生成者与评估者分离：独立上下文、不看推理、显式评分标准、迭代预算 | 编排组：生成者=Worker（独立上下文 `memberSessionKey`），评估者=**子任务状态机**（`workerPool`），不看 Worker 推理，只看产物与执行记录 ⇒ 独立性满足且成本为零。定时任务：评估者=`scheduledVerify`（确定性对账 L1 + 风险门 L3 抽样，**无人值守 fail-closed**），显式标准、可复现。**不引入模型裁判** ⇒ 无「评估死循环」风险，无迭代预算需求（迭代预算恒为 0）。**AI 建团草案的质量判据 = 确定性校验**（`normalizeMemberInput` 枚举 fail-closed + `capabilitiesOf` 能力摘要），非模型自评 |
| 8 | 前缀稳定与缓存命中：稳定区/可变区划分、序列化确定性、重写触发点的失效代价、命中率观测 | **现状（现算 + 读码）**：工具表 9852 token 固定顺序（`BASE_TOOLS` 数组序）⇒ 工具段前缀稳定。**记忆段每轮变化**（`ChatArea.jsx` 召回注入）⇒ **前缀重写不可避免**，且 `memories` 内容随召回结果漂移 ⇒ 命中不稳定。**失效代价**：一次全量重写 ≈ 9852（工具）+ 系统提示 ≈ 其余部分 token。**命中率观测：当前无**（无 prompt-cache 观测位；`runTrace` 只记 token 与事件）。**本设计的处置**：① 判定结果**不进 system**（不新增重写源）；② 记忆召回**补 `query`** 后结果更稳定（同问题 → 同召回集）；③ 观测缺口列入 §15 |

## 15. 魔鬼代言人：反例清单

> 手段定义：每条反例给出「目标方案 → 反驳 → 后果」。

**反例 1 —— 「自动 DAG 就是让模型自己决定」**
反驳：现状确实是模型自决（机制 ②），但**默认 32768 窗口下工具表必然被裁到 core 档**（9852 token / 32768 = 30% > 20% 阈值，现算），`orchestrate_task` 属 `collab` 组且是 ondemand ⇒ **模型要先花一轮 `activate_tools('collab')` 才拿得到 schema**。系统提示词里那句引导是软约束，模型可以忽略、可以忘记、可以先花两轮试探。
后果：用户要的「自动」在默认配置下变成「偶尔自动」。**判定器命中时预热工具面**是本设计对该反例的直接处置。

**反例 2 —— 「4 层记忆已经支持了，普通对话必然生效」**
反驳：① 普通对话的召回 IPC **不传 `query`**（`ChatArea.jsx` → `local:memories/list`），`recall()` 的 `query` 缺省 `''` ⇒ `scoreMemory` 的 `relevance` 因子（权重 0.40，最高）被跳过 ⇒ 召回的是「最近 + 高 tier」而非「相关」。② **team 层在普通对话里永远取不到**：`recall.js` `_recallLayered` 中 `if (sc === 'team' && !teamId) continue;`，而 `local:memories/list` 的入参**根本没有 `teamId`**。③ 自动沉淀**默认关闭**（`memory.autoCapture`，设置页 `useState(false)`）⇒ 会话层记忆默认不写。④ **模型自己没有任何记忆工具**（`BASE_TOOLS` 里 `memory_*` 全为零，`agent-core/index.js` 的 `name: 'memory...'` 零命中）⇒ 模型既不能自查记忆也不能自行留存。
后果：「保证记忆能力（4 层）」在普通对话上目前只成立 3 层（session/project/global）且相关性失效、写入默认关、模型无自救手段。**必须先修 §9 P1-1 与 teamId 透传，否则新入口一上线就暴露这个洞。**

**反例 3 —— 「把定时任务挪进助理就行了」**
反驳：定时任务**不能复用军团**——`scheduler.js` 全文件 grep `team`/`teamId`/`roster` **零命中**；`scheduledTools.js` 的 `teamTools` 默认为 `null`，只在 workerPool 的成员任务路径注入 ⇒ 定时任务里 `orchestrate_task` 建的是**匿名 Worker 组**（无 roster、无成员人格、无 team 记忆）。且定时通道的 `runAgent` 参数里**没有 `memories`**。
后果：用户说「定时任务也能用我的军团跑」，如果只做 UI 挪位，会得到「界面能选、实际跑的还是匿名组」的假闭环——正是 `docs/MJWork-全项目审计…` 记录的「一层假闭环」形态。

**反例 4 —— 「AI 自动建团 = 调一次 `teams:draftMember`」**
反驳：① 一次只生成**一个**成员（入参 `description` 单数），没有「一句需求 → N 人 + 统筹」的入口；② 草案一律 `source:'custom'`，**不从 51 条数字员工目录里挑**，用户要的「AI 帮我构建团队」通常应优先复用目录；③ 无覆盖度校验（需求要联网但没成员有 `web` 工具，没人提示）。
后果：AI 建团变成「AI 写了个角色设定」，而不是「AI 组了一支能干活的车队」。这与用户「类 WorkBuddy 专家团」的期望不符。

**反例 5 —— 「双入口 = 两套导航壳子」**
反驳：若两个入口各自实现一遍记忆召回、各自建一套编排触发，则 `MemoryManager` 与 `orchestrator` 的「单一事实来源」纪律破掉；而项目历史上已有大量「可见的一半做完、承重的一半没做」的假闭环（`docs/MJWork-全项目审计…` §4）。
后果：两入口行为漂移（同一句话在两个入口行为不同），且修复要改两处。**本设计强制：两入口共用 `ChatArea` 的召回链、共用 `agent-core` 执行循环、共用 `orchestrator`/`workerPool`、共用 `teams` 表**；入口差异只允许落在「执行器选择」与「UI 编排」。

**反例 6 —— 「军团归属全局，那『助理建的军团』在新建任务里一定能选到」**
反驳：数据层确实全局（`listTeams` 不过滤），但**「建好立刻可见」并不成立**——已核实：`ipc/teams.js` `teams:create` 广播的是一条 team_message（`broadcastSystem`），**不是列表失效事件**；`TeamDispatchPanel.tsx` 与 `TeamsPage.tsx` 都只在挂载时拉一次列表、**不订阅 `teams:event`**。⇒ 两个视图同时在场时，助理里刚建好的军团不会即时出现在新建任务的 legion 面板。
后果：用户会读成「助理建的军团丢了」。**修法很轻**：补一个 `type:'team_created'` 事件 + 让 `TeamDispatchPanel` 订阅，或让 legion 面板每次打开都重拉（§17 U3）。

**反例 7 —— 「判定器放在 agent-core 里，让模型自己判断更自然」**
反驳：模型侧已有自决（机制 ②）。若系统侧再叠一层判定，等于两个决策源互相污染：模型可能绕过（直接调工具）、也可能重复触发（判定器预热 + 模型自决各建一次组）。
后果：重复建组 ⇒ 双倍烧 token + 两组产物打架。**本设计的处置**：判定器只做「工具面预热 + 编制预置」，**绝不建组**；建组仍只有 `orchestrate_task`/`teams:dispatch` 两条既有路径。

## 16. 风险与决策点（需管家节点裁决）

### D1. 军团归属层级：**全局资产**（已确认）

| 项 | 内容 |
|---|---|
| **推荐** | **全局资产**（现状即如此，不改数据模型） |
| 理由 | `teamStore.createTeam` 的 `project_path` 可选且注释明写「跨项目复用」；`listTeams` 不过滤；2026-10-20 用户反馈已推翻「按项目归属过滤」的 D1 设计 |
| 不选的后果 | 若改成项目级：① 需改 `teams` 表结构 + 迁移既有数据；② `listTeams` 加过滤条件 ⇒ 所有调用点（`ipc/teams.js` `teams:list`、`TeamDispatchPanel.tsx`、`TeamsPage.tsx`）三处同步；③ 「自己的军团」在跨项目场景下不可见 ⇒ 直接违反用户诉求「自己的军团」；④ 改动面与收益完全不成比例 |

### D2. 路由判定权归谁：**系统侧前置闸 + 模型侧自决并存**（推荐）

| 项 | 内容 |
|---|---|
| **推荐** | 系统侧在 main 进程做**前置路由判定**（L0 结构化规则 + L1 离散类别分类器），判定结果用于「**预热工具面 + 预置编制 + 发升级/降级提示**」，**不建组、不否决模型自决** |
| 理由 | ① **判据本身有硬证据**：arXiv:2512.08296（Nature MI）量化了「可分解 +80.8% / 顺序规划 −70.0%」与「无中心化验证时误差放大 17.2×」⇒ 「什么时候该上多 Agent」**不是玄学**，有可落成代码的结构信号（并行度、工具数、依赖深度）；② 系统侧可解释、可审计、可 eval 量化（离散类别）；③ 工具面裁剪（现算 30% > 20%）使纯模型自决在小/中窗口下不可靠；④ 不否决 ⇒ 保留模型自主性，避免重复建组 |
| 不选的后果 | **纯模型自决**：默认窗口下模型拿不到 schema，「自动」变「偶尔自动」，且**不可 eval**（说不清哪类任务被升级了）。**纯规则**：无法处理语义结构（「这五个文件要不要分别查证」），误判率高。**系统侧直接建组**：与模型自决重复建组 ⇒ 双倍烧 token |
| 需裁决的子项 | ① 判定失败降级方向（推荐 `simple_chat`，理由见上）；② 是否允许用户关掉判定器（推荐可关，配置项 `entryPolicy.new.autoDag.enabled`）；③ 升级/降级提示与成本倍数提示是否展示给用户（推荐展示，走 UI 事件不进 prompt）；④ 是否保留 `manual_team`/`scheduled` 两个「引导但不执行」的路由类别（推荐保留）；⑤ **确认卡的三档形态（C0 静默 / C1 确认卡 / C2 阻断引导）是否获准**（推荐按 §7.3 的表落地；C1 为默认档） |
| ⚠️ 配套约束 | **本决策不能单独成立** —— 必须与 §7.3「用户确认点」合读：**判定权归系统（判得准 + 说清为什么），执行权归用户（授权执行）**。若只做判定、不做确认点，则等于把「不可完全自动化的判据」当成可完全自动化 ⇒ 正是主理人指出的「没有可靠公开硬判据」的核心风险 |

### D3. AI 自动建团的审批门强度：**执行前确认，逐成员可编辑**（推荐）

| 项 | 内容 |
|---|---|
| **推荐** | 草案只出草稿不落库，用户逐项确认（可编辑名称/工具/审批档/沙箱档/技能）后才落库；落库走**既有** `teams:addCustomMember`/`teams:recruit` |
| 理由 | ① 沿用既有语义（`teams:draftMember` 已是「只出草稿」），**不新增审批机制、不新增草案表**；② `normalizeMemberInput` 已是 fail-closed 归一（枚举非法即回落），落库路径本身安全；③ 成员会拿到真实工具权限（`rolePreset.toolNames` 交集裁剪 + 沙箱档），自动落库等于让模型自行扩权 |

| 需裁决的子项 | ① 是否允许「一键全确认」（推荐允许，草案已逐项可见）；② 草案是否需要暂存以便多轮迭代（推荐渲染层 hold，不落库） |

### D4. 两个入口是否共享同一会话列表：**共享**（推荐）

### D9. 「助理」这个命名（⚠️ 与管家节点待办 #11 直接相关）

| 项 | 内容 |
|---|---|
| **推荐** | **避开「助理」**，改用按场景分的名字。推荐顺序：**「团队」** > 「编制」 > 「数字团队」 > 「工作室」 |
| 理由 | ① 调研 §2.2 已核实【官方文档】：**WorkBuddy 的「助理」= IM 远程控制**（微信/企微/QQ/钉钉/飞书发消息 → 电脑执行 → 结果回推，官方原文「就像一个遥控器」），与用户设想的「重编排/组建军团」**含义完全不同** ⇒ 目标用户在 WorkBuddy 语境下已有「助理=远程」的肌肉记忆，直接沿用会造成心智冲突。② Octomind 团队的命名原则【社区】：「a name should describe **what you do there** rather than **rank the person doing it**」「**never Simple and Advanced**」；「助理」在语义上更接近「难度分/身份分」，不如「团队」这类**场景分**名。③ 用户原话里「助理」还并列承担了「定时任务」，语义负担更重。 |
| **各候选名的对比** | **「团队」** ✅ 与 WorkBuddy 已有「专家团」概念不冲突（不同词）、语义直白（用户心智里「团队」就是一群角色）、且与内部既有对象名 `teams`/`team_members` **完全一致**（代码与文案同源，零翻译损耗）｜**「编制」** ✅ 更准（对应「编制表」语义，且内部 `TeamsPage.tsx` 的头部注释本就用「编制」一词），但对非技术用户略生僻｜**「数字团队」** ⚠️ 语义清楚但与「数字员工」易混（一个是编制、一个是成员）｜**「工作室」** ⚠️ 语义偏泛，不像一个能装下定时任务的地方 ｜**「助理」** ❌ 与 WorkBuddy 撞名且含义相反 |
| **「直接叫助理」的认知混淆成本（量化）** | ① **首次使用成本**：用户点「助理」期待「像遥控器一样远程派活」，实际得到「组团的编排台」⇒ 一次语义错位，纠正成本 = 一次误点 + 一次解释；② **文档/截图成本**：所有说明文档要反复澄清「我们的助理不是那个助理」，Octomind 的复盘原话正是「the docs fork, support has to ask which mode you're in before they can help」；③ **跨产品迁移成本**：WorkBuddy 用户（若与目标用户重叠）会把「助理」当远程控制入口，**心智无法迁移**；④ **若未来真要做 IM 远程控制**（MJCode 有 `miniprogram/` 与 `server/` 目录，说明这条线存在），「助理」这个名字会被**双重占用** ⇒ 届时改名成本更高（已有用户文档、快捷键、教程） |
| 不选的后果 | 若 MJCode 与 WorkBuddy 同处一个用户群（「助理」心智已被占用），用户点「助理」期待远程控制、得到的是编排面板 ⇒ 首轮认知错位；后续文档/截图要反复解释「我们的助理不是那个助理」 |
| 备选命名 | 「**团队**」/「**编制**」/「**数字团队**」/「**工作室**」——语义精确度递减、与 WorkBuddy 冲突概率递增。建议顺序：**团队** > 编制 > 数字团队 > 工作室 |
| 需裁决的子项 | ① 是否接受与 WorkBuddy 同名（若目标用户群不重叠则可接受）；② 若改名，navState 的 `NavKey`、i18n key、`sidebar.json` 文案要同步改（见 §14 P0-1/P0-2） |

### D11. ⭐ 入口数量：2 个一级入口 vs 1 入口 + 2 种模式（主理人硬约束）

> **主理人硬约束（2026-10-24）**：「『拆成两个一级导航』正在被成熟产品收回（Octomind 2026-09 合并回单面板）→ 请评估：MJCode 是否真的需要 2 个一级入口，还是『1 个入口 + 2 种模式』更稳（给出对比与推荐）。注意 MJCode 现状是 4 个一级入口（newChat / scheduled / ecosystem / teams），**从 4 → 2 合并与从 4 → 5 新增是完全不同的改造量级**，两条路径的代价差异请量化。」

**先量化现状与三条路径的改造量级（现算）**：

| 项 | 现状 | 路径 A：4 → 2（一级导航合并） | 路径 B：4 → 5（保留 4 项再加 1） | 路径 C：4 → 1（单入口 + 模式切换） |
|---|---|---|---|---|
| 一级导航项数 | 4（`newChat`/`scheduled`/`ecosystem`/`teams`） | 2 | 5 | 1（+ 模式切换器） |
| **一级导航渲染改动** | — | 删 2 项、加 1 项（`Sidebar.jsx`） | 加 1 项 | 删 3 项、加模式切换器 |
| **视图状态改动** | `showScheduled`/`showEcosystem`/`showTeams`/`showDashboard` 4 个布尔 | 收敛为 1 个 + 子 tab | 加 1 个布尔 | 全部收敛为「模式」枚举 |
| **`activeNavOf` 契约** | `NavKey` 5 值 | 改 5 值 → 3 值（**破坏性**，须同步 `test/sidebar-nav-active.test.js`） | 加 1 值（**非破坏性**） | 改 5 值 → 2 值（破坏性） |
| **组件搬迁** | `TeamsPage`/`ScheduledTasks` 各占一级 | **必须搬进助理页**（新建 `AssistantPage` 容器） | 无需搬 | 全部收进单页 |
| **「生态中心」归属** | 独立一级（实际是弹层 `EcosystemModal`） | 降级为弹层 | 保持 | 降级 |
| **不变量风险（Octomind 3）** | — | ⚠️ 搬迁若做成「两套页面」即违反 | ✅ 最低 | ⚠️ 模式切换若 gate 能力即违反 |
| **可合并性（Octomind）** | — | ✅ 已按「一个产品两个门」设计 | ❌ 5 项一级导航**离合并更远** | ✅ 天然可合并 |
| **净改造量级** | — | **中**（导航 + 状态 + 组件搬迁 + 测试改写） | **小**（只加 1 项） | **大**（全量收拢） |
| **与用户诉求的距离** | — | ✅ 命中「2 个入口」 | ❌ 变成 5 个 | ✅ 命中「2 种模式」但形态不同 |

**推荐：路径 A（4 → 2），且按「一个产品、两个门」实现。**

**理由**：

1. **用户诉求明确是 2 个**（「用户想把入口做成 2 个」），路径 B（4→5）直接违背诉求 ⇒ 排除。
2. **路径 C（1 入口 + 2 模式）看似最稳，但**：
   - 调研 §5.1 的 Octomind 合并案例，**合并后的形态恰恰是「单面板 + 底部 Advanced 行」** ⇒ **路径 C 其实是 Octomind 的终局形态**，不是「更稳的起点」。
   - 但 Octomind 之所以能合并，是因为他们**先做了双面板**（积累了双份状态的教训）⇒ **直接走 C 未必更省**：「模式」仍需承载两套语义（哪个模式、怎么切、偏好存哪），复杂度并未凭空消失。
   - 更关键：**用户要的是「两个入口」这个心智**，模式切换器（角落里的 toggle）**不提供这种心智**——用户看到的是「一个输入框 + 一个不知在哪的开关」，反而回到 Octomind 拆分前的症状（「That's a wall if you signed up to get something done」）。
3. **路径 A 满足 Octomind 的可合并性**：本设计刻意**不引入入口专属数据结构** ⇒ 将来若要收敛成路径 C（或 Octomind 的单面板 + Advanced 行），**只是把 `AssistantPage` 的 Tab 降级为侧栏底部一行，不需要数据迁移**。这正是「先双门、留合并路」的正解。

**但路径 A 有两个必须守住的约束（否则会退化成「两个产品」）**：

- ⚠️ **搬迁 ≠ 重写**：`TeamsPage`/`ScheduledTasks` **原样搬进助理页**，不改其内部逻辑（§14 落地清单已如此规定）——直接对应 Octomind 的「If we ever need to build a screen twice, the split was wrong」。
- ⚠️ **入口分支只许影响呈现层**：`ChatArea.jsx` 里「选中军团 ⇒ 强制派活」这条现状（P0-6 要修的）**正是「入口分支 gate 能力」的实例** ⇒ 修它不是洁癖，是路径 A 成立的前提。

**不选 A 的后果**：若因 A 的改造量级偏大而选 B，则一级导航变成 5 项（比现状更挤），且**离 Octomind 证明的收敛终局更远**；若选 C，则用户的「2 个入口」心智落空，且要额外设计「模式偏好持久化」（对应 Octomind 的「默认值在用户脚下翻转」坑；本项目新建任务会自动建工作空间，正属该场景）。

**需裁决的子项**：① 路径 A/B/C 的最终选择（推荐 A）；② 若选 A，是否**同时**在设置里留一个「合并为单入口」的开关（推荐**不留**——避免引入「模式偏好」这个已被证明易翻车的概念）；③ 生态中心降级为弹层是否获准（推荐获准，它是弹层不是页面）。

## 19. 拟入库知识条目（随设计回传主理人，由主理人经 wiki-creator 编译进底座）

> 按 `references/knowledge-policy.md` 的防污染标准整理：只收**跨项目可复用**的方法论，不含 MJCode 专有实现细节、不含未验证结论。

1. **「模型自主决策」与「系统前置判定」可以并存，关键是划分职责边界**——系统侧只做「能力预热 + 上下文预置」，**绝不建组**；建组仍由模型单点触发。判据：两个决策源同时能建组 ⇒ 双倍副作用；系统侧只预热 ⇒ 既保住模型自主性，又修掉「模型拿不到 schema」的物理断点。
2. **工具面裁剪会静默削弱「模型自主使用某能力」的设计**——当能力被放进 ondemand 档且工具表占窗口比例超阈值时，模型必须先花一轮申请工具才能拿到 schema，「模型会自己决定用 X」就退化为「模型偶尔会用 X」。审查任何「让模型自主决策」的设计时，必须同时检查该能力在默认窗口下的可见性。
3. **「分层召回」必须传 query，否则最高权重的相关性因子静默空转**——`relevance` 通常是六因子中权重最高的一个；缺 query 时它被跳过而其余因子按比例分摊，排序从「相关」退化为「最近 + 高 tier」，且**没有任何报错**。
4. **「四层作用域」在主对话路径上可能只有三层可达**——某层若依赖调用方透传归属键（如 team 层需 teamId），而该 IPC 的入参没这个键，则该层在主链路上**永远取不到**，且同样无报错。审查多作用域系统时，须逐层核对「归属键是否真的被传下去了」。
5. **「无人值守通道复用某资产」的能力缺口通常不在通道层，而在工具面装配层**——判定依据：若通道只负责模型调用（凭证/超时/配额），则「定时跑团队」需要改的是「这次跑哪些工具 + 名册从哪来 + 记忆带不带 teamId」，而不是改通道本身。

**因 T-01 / T-08 而新增的设计约束**：

1. **T-01 ⇒ 分层召回的 `topK` 必须真正生效**。现状：主对话 `local:memories/list` 传 `topK: limit||7`，而分层路径**忽略它** ⇒ 「limit=7 恰好等于 Σ配额(2+3+2)=7」是**巧合**，一旦 `team` 层可达（传 teamId）或配额调整，注入量会失控。
   - 修法：`_recallLayered` 必须接收并应用 `topK`（在合并去重后、`RECALL_TOP_K_MAX` 之前切片），使 `topK` 语义与旧单空间路径一致。
   - **对双入口的直接含义**：本设计 §9 P1-1 扩为「**补 `query` + 修 `topK` + 透传 `teamId`**」三件事。团队路径 `main.js` 的 `buildTaskPrompt` 注释写「Top-3 注入」但**实为最多 7 条**（`LAYER_QUOTA` 之和），注释与行为不一致 ⇒ 修 `topK` 后才真正是 3 条。
2. **T-08 ⇒ 记忆召回必须按轮次刷新**。现状：召回只在 `project?.path`/`thread?.id` 变化时发生 ⇒ 同会话内 `/mem` 写入的记忆**在后续轮次不生效**。
   - 修法：召回需在**每轮发送前**刷新（或把本轮 query 纳入依赖）。
   - **与本设计的一致性**：§7.3 的确认卡设计**依赖「本轮问的是什么」**才能给出准确的拆解与理由 ⇒ 若记忆不按轮次刷新，判定理由会基于过时上下文。
3. **T-09 ⇒ 两条入口的检索口径必须收敛到同一套**。现状：主对话不传 query、团队路径传 `goal+task.title` ⇒ 同一记忆体系两种口径。
   - **设计约束**：本设计的路由判定器（L1 triage）**必须拿到与执行侧同口径的召回结果**，否则「判定用的记忆」与「执行用的记忆」不同 ⇒ 判定理由会失真。⇒ 判定器与执行链**共用同一个召回函数与同一个 query 构造规则**（建议统一为「本轮用户输入 + 当前任务标题」）。
