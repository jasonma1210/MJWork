## 1. 一句话结论

一级导航从 4 项收敛为 2 项（新建任务 / 助理）；「助理」成为 Tab 工作台（军团 / AI 建团 / 定时任务 / 复杂问题）；
「选中军团 ⇒ 强制派活」这条**入口分支 gate 能力**的架构违规已消除——编制改为「偏好」，派活改为**显式动作**；
记忆召回补上本轮 `query` 并按轮次刷新；一次性编制（临时组队）不落 `teams` 表。

两条新门禁（导航语义 + 候选编制/派活分流）均为**行为断言**，并逐条做过**变异验证**（§4）。

## 11. 收尾补丁（第三轮）：「按这个执行」真派活 + 临时编制限制

### 11.1 修掉的假闭环

此前「按这个执行」只调 `entryChoice`（主进程 `noteUserChoice` **只记录选择、不启动团队**）⇒ **点了什么都不发生**，确认卡是假的。
现在：`entryChoice`（记录选择，防下一轮重复弹卡）→ 然后真的调**既有** `window.mjcode.teamsDispatch(...)`。

**派活调用位置**：`renderer/src/components/EntryRouteNotice.tsx` 的 `choose('confirm')` 分支；载荷由纯函数
`renderer/src/lib/entryRouteView.ts` 的 `dispatchPlanOf()` 组装（**可被门禁行为断言**，不埋在点击回调里）。

载荷（键集与主进程 `teams:dispatch` 契约一一对应）：

```js
{
  teamId: candidateRoster.teamId,   // 当前候选编制（lib/candidateRoster 单一事实源）
  goal: card.goal,                  // 本轮用户输入（主进程判空）
  threadId,                         // 当前会话
  presetTasks: card.subtasks.map(t => ({ id, title, prompt: title, dependsOn })),
  projectPath,                      // 可选：当前项目目录
}
```

### 11.2 ⚠ 一个必须登记的契约缺口（否则「按这个执行」会 100% 失败）

- 确认卡下发的 `subtasks` 只有 **`{ id, title, dependsOn }`**（`main/entryRouter.js` 的 `buildConfirmPoint` 明确只映射这三个字段）；
- 而 `main/teamDispatchPlan.js` 的 `normalizePresetTasks` 与 `main/orchestrator/index.js` 的 `planGoal` 都要求每条任务**同时有 `title` 与 `prompt`**（`if (!title || !prompt) continue;`），否则 `presetTasks` 全被丢弃、`planGoal` 直接返回 `'预设任务清单为空或缺少 prompt'`。

⇒ **原样回传 `card.subtasks` 会让「按这个执行」每次都失败**（可见报错，不是静默回落——这点比静默强，但仍不可用）。
处置：渲染层把 `prompt` **按 `title` 原样填充**——不加料、不扩范围，用户看到的标题就是执行指令；`id` / `title` / `dependsOn` 逐字保留（门禁 `F1`/`F2` 守着）。
建议（main 侧一处改动即可更优）：`buildConfirmPoint` 在 `subtasks` 里一并下发 `prompt`（拆解结果里本来就有），渲染层就不用推导。

| 动作 | 行为 |

### 11.4 临时编制（`kind === 'temp'`）的限制：禁用 + 解释，**不伪造、不静默降级**

- `dispatchPlanOf` 对 `kind==='temp'` 返回 `{ ok:false, reason:'roster-temp' }`，**拒绝时载荷对象里没有 `teamId` 字段**（门禁 `F3` 断言「拒绝时不得带载荷」）；
- UI：「按这个执行」**禁用**（`disabled={!card.ready || Boolean(blockedReason)}`）+ 卡片内就地一行解释「**临时编制需先保存为军团才能按团队执行**」（i18n 中英各一，门禁 `F10`）；
- 拒绝原因**分档**（`no-roster` / `roster-temp` / `no-team-id` / `no-thread` / `no-goal` / `not-ready`），每种都有自己的文案——不合并成一句「无法执行」，也不悄悄降级成单 Agent 而不告诉用户。
