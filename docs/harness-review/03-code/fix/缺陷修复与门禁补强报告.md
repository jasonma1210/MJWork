## 1. 逐条修复：改动前行为 → 改动后行为 → 验证方式与结果

### T-01（P1）分层召回 `topK` 被丢弃

| 项 | 内容 |
|---|---|
| 改动前 | `recall()` 的 scopes 分支调 `_recallLayered({space, query, scopes, …})`——**参数表里没有 topK**；`_recallLayered` 只用 `LAYER_QUOTA[sc]` + 末尾 `slice(0, RECALL_TOP_K_MAX=50)`，全程不看 topK。实测分层 `topK:1` 返回 5 条。 |
| 改动后 | `recall()` 透传 `topK`；`_recallLayered` 按「**全局 topK 与每层配额取更严格者**」执行：每层 `min(LAYER_QUOTA[sc], topK)`，合并后 `slice(0, topK)`。 |
| 语义细节（关键） | `topK` 缺省改为 `null` = **不额外截断**（只受每层配额约束）。理由：分层路径的既有契约是「总数 = Σ配额」，若把缺省当成 5，`memory-scope` 的「分层配额严格封顶」门禁会当场变红（已实测踩到并修正）。单空间旧路径缺省仍是 5 条，行为完全不变。 |
| 验证（探针 `/tmp/mjfix-a/probe-a1-a5.mjs`） | 分层（6 project + 3 global + 2 session，conv-a）：`topK=1 → 1 条`、`topK=3 → 3 条`、`topK=7 → 7 条`、`topK=50 → 7 条（不足则全给）`；单空间 `topK=1 → 1 条`（回归）；`conv-b → 5 条且不含会话层`（不跨会话泄漏）。 |
| 连带修复 | `main/main.js` 的 Worker 路径 `topK: 3` 现在**真的**是 3 条，「Top-3 注入」注释与行为一致（该文件不在本批范围，注释本身未改，但已不再与行为矛盾）。 |

### T-02（P1）SSRF 单一判据在 browser 通道被旁路

| 项 | 内容 |
|---|---|
| 改动前 | `childEntry.js` 的 `assertHttpUrl()` 只校验协议 http/https，不调 `isPrivateHost`。而更弱的 `web_fetch`（L2）走 `webTools.httpRequest` 的 `isPrivateHost + guardedLookup` 双防护 ⇒ **越强的通道越松**。可达 `127.0.0.1:47615`（本应用自身端口）/`169.254.169.254`/`[::1]`/私网段，随后 `browser_extract` 回读正文。 |
| 改动后（三层） | ① `assertHttpUrl` 追加 `isPrivateHost(parsed.hostname)`（**复用 `main/ssrfGuard.js`，无第二份判据**）；② `assertResolvedPublic` 做 **resolve-then-validate**（逐地址判，全部公网才放行，堵 DNS rebinding）；③ **落地复检** `assertLandedUrlPublic(page)`：`navigate`/`click`/`fill`/`select`/`extract`/`screenshot` 之后检查 `page.url()`，命中内网则**先 `goto('about:blank')` 清空页面**再报错——不让已加载的内网正文留在浏览器里被 `browser_extract` 读走。 |
| 为什么新增 `main/browserProcess/urlGuard.js` | `childEntry.js` 是**子进程入口脚本**，加载即 `attachChildSide()`，无 IPC 通道时直接抛错 ⇒ 单测无法 import 它，守卫若内嵌就只能靠「真起浏览器子进程」验证（慢、依赖本机 Chromium）。抽出无副作用的纯模块后：判据可被直接单测（含**注入式假 DNS**），入口只负责接线，接线另有 fork 行为断言看守。**该模块不含任何「什么算内网」的规则**，只调用 `ssrfGuard.isPrivateHost`。 |
| `ssrfGuard` 能否在子进程 require | **能**——它只依赖 `node:dns`，无主进程专有模块。故**未**向 `desktop/shared/` 抽取任何东西。 |
| 验证 | 新增门禁 `test/browser-ssrf-guard.test.mjs` **13/13 通过**：11 个私网目标（含 IPv6 `[::1]`、IPv4-mapped、`*.localhost`、CGNAT、`0.0.0.0`）全部拦截；3 个公网目标全部放行（不破坏正常导航）；`about:blank` 不被误判；假 DNS 注入验证「混入内网即拦」「解析失败不拦（交还浏览器报错）」「超时不下结论」；**fork 真子进程**验证 `navigate` 确实拒绝云元数据与本机端口，且业务错误不触发子进程重启。 |
| 遗留（诚实标注） | Chromium 自动跟随 30x，跳转目标由浏览器内部解析与建连——**入口处在请求发出前无法拦**。已在落地后复检（能覆盖「公网 URL 302 到 127.0.0.1」这条主路，并清空页面）；「跳转到**域名**且该域名解析到私网」这条仍需 Playwright `context.route` 逐请求拦截才能彻底覆盖，超出本批范围。 |

### T-07（P3）`recallForPrompt` 生产零调用 / 注入无长度预算

| 项 | 内容 |
|---|---|
| 路线选择 | **路线甲的变体：共用实现 + 生产路径承载预算**（报告中说明理由如下）。 |
| 改动前 | `recallForPrompt` 的 `budgetChars` 预算装配只活在这条**生产零调用**的分支里；真正进 system prompt 的 `recallContents` 路径**没有任何长度上界**（记忆正文 IPC 上限 5 万字符，一次召回能把上下文撑爆）。 |
| 改动后 | 抽出 `_assembleWithinBudget`（分层召回 → 可信度过滤 → 预算内逐条累积）作为**唯一**装配实现；`recallContents`（生产路径，`local:memories/list` 与 `main.js buildTaskPrompt` 都走它）**直接调用它**，新增 `budgetChars`（缺省 `RECALL_CONTENT_BUDGET_CHARS=4000`）⇒ 生产路径从此有硬上界；`recallForPrompt` 收敛为同一实现的文本出口（不再有第二份装配逻辑）。 |
| 为什么没选「纯路线乙（删除）」 | 路线乙必须同时改 `test/memory-scope.test.mjs`（该文件不在本批独占清单内，且另一成员正在改测试面）。删除会让一个现有套件当场变红、把红留给别人。收敛为「一份实现、两个出口」既消除了双实现分叉，也零破坏。 |
| 保底语义 | 累积到超预算即停；**若一条都装不下，装入第一条并按预算截断**——「召回为空」比「截断一条」更糟（主对话会彻底失去记忆上下文）。`recallContents` 的 `content` 取**装配后的文本**（已被截断的那份），否则「有上界」只是账面上的。 |

### 7.1 浏览器 30x 重定向：跳转到「解析为私网的域名」未覆盖

| 项 | 内容 |
|---|---|
| 残留形态 | Chromium **自动跟随 30x**，跳转目标由浏览器内部解析与建连。入口处（`assertHttpUrl` / `assertResolvedPublic`）看到的是**用户给的 URL**，看不到最终目标。 |
| 已覆盖的主路 | **「公网 URL 302 → IP 字面量」（如 `→ http://127.0.0.1:47615/`）已被拦住**：`navigate` 在 `page.goto` 之后调用 `assertLandedUrlPublic(page)` 检查 `page.url()`，命中内网则**先 `goto('about:blank')` 清空页面**再报错——已加载的内网正文不会留在浏览器里被 `browser_extract` 读走。`click` / `fill` / `select` 触发的导航同此路径复检。 |
| **未覆盖** | **「公网 URL 302 → 某域名，而该域名解析到私网」**。落地复检只做**字面量**判定（不做 DNS 解析——那会在每次导航后再加一次解析延迟，且此时内容已进页面）。 |
| 彻底修法 | 改用 Playwright `context.route('**/*', handler)` **逐请求拦截**：对每个即将发出的请求按其 URL 判私网并 `route.abort()`。属**独立议题**（会改变浏览器会话的请求管线，需单独评估对正常站点的影响与性能）。 |
| 影响面评估 | 需要「攻击者可控的公网域名 + 302 到自己的域名 + 该域名 A 记录指向内网」三件同时成立；比「模型直接 navigate 内网地址」的利用门槛高得多。**但不应据此宣称 SSRF 已完全闭环。** |
