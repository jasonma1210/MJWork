### 2.3 「新建任务」里的军团 = 候选编制（不是模式开关）

原实现是「选中军团 ⇒ 强制派活，直接 return，连普通问一句都不行」——设计判定这属于**入口分支在 gate 能力**（架构不变量违反）。

现改为**编制偏好**：徽标表示「本次任务可被该编制承接」，普通对话照常发起；仅当判定器命中需编排时才注入为 roster。中间态「暂不派活/取消编制」可清空，不影响对话。临时组队（temp）走 `lib/candidateRoster.ts`，不落 `teams` 表。

### 2.4 自动 DAG 判定（本轮核心）

新增 `main/entryRouter.js`（624 行，纯逻辑可单测）+ `main/entryRuntime.js`（199 行，宿主接线）+ `main/entryPolicy.json`（所有阈值/开关外置）。

**判据是「任务结构」，不是难度分**，输出 5 个离散路由类别：
`simple_chat` / `multi_step_single` / `parallel_team` / `manual_team` / `scheduled`

四条结构信号（运行时启发式，不依赖训练）：
1. 子任务**可真正并行** ⇒ 允许升级
2. **强顺序依赖** ⇒ **禁止**升级（依据：顺序规划任务上多 agent 退化约 70%）
3. 工具种类数 ≥ 阈值 ⇒ 提示降级
4. 需**中心化验证** ⇒ 优先 centralized 拓扑

两层判定：**L0 规则层**（零成本，命中即返回，**不调模型**）→ 只有 `unknown` 才走 **L1 模型层**（一次短调用，输出离散类别）。**L1 失败/超时/输出非法 ⇒ 降级 `simple_chat`**（误启多 agent 比漏启更伤）。

**确认点三档**（关键：判定器只决定「要不要问」，不代替用户按执行）：
- **C0 静默执行**：用户已选编制 / 规则层高置信 ⇒ 直接跑，事后给可点提示
- **C1 确认卡（默认）**：先出卡**不建组**。卡上三样：① **已拆好的子任务清单** ② 为什么建议用团队（人话 + 判据来源）③ 代价（N 人 / token 约 N 倍 / 预计墙钟）。三动作：按这个执行 / 改成单 Agent / 看细节
- **C2 阻断+引导**：不执行，只给跳转引导

三条纪律已落地：① 卡上子任务**必须是已拆好的**（预拆 DAG 但不建组）② 用户选「单 Agent」后**本轮不再追问** ③ **无人值守无确认点**（定时任务须预声明 team_id 与预算，不得静默升级）。

**不做的事（重要）**：判定器命中时**只预热工具面 + 预置编制，绝不建组**——建组仍由模型调 `orchestrate_task` 单点触发，否则会与模型自决重复建组、双倍烧 token。

### 2.5 「确认即派活」闭环（本轮补的一处真断点）

原实现里 `entryChoice` 的 `noteUserChoice` **只记录选择、不启动团队** ⇒ 点「按这个执行」什么都不发生（假闭环）。

已补：`teams:dispatch` 接受 `payload.presetTasks`（`main/teamDispatchPlan.js` 的 `normalizePresetTasks` 归一：去重 / 剔除不存在与自环依赖 / 8 条封顶 / 标题与正文长度封顶 / 全非法返回 null 回落 LLM 拆解）。渲染层点确认后调**既有** `teamsDispatch`，把卡上清单原样回传 ⇒ **编排器跳过 LLM 二次拆解，卡上显示的就是实际执行的**。

### 2.6 定时任务复用军团

- `scheduledStore.js`：task 增可选 `team_id` / `thread_id`（fail-closed 归一）
- `scheduler.js`：`createTask` 收参并在 `runTask` 透传
- `main/scheduledTeam.js`（223 行）：`prepareScheduledRun` 装配军团（roster 快照 / 默认模式 / 预算）+ 注入 `teamTools` + 注入记忆（带 teamId）+ 会话绑定（继承历史、产出回写原会话）
- `main/scheduledChannels.js` **未改**（它是模型调用通道，与军团无关——这条边界是对的）

### 2.7 界面上的可见性

- `renderer/src/components/EntryRouteNotice.tsx`（280 行）：订阅 `onEntryRoute` / `onEntryConfirm`，展示升级/降级提示（含理由 + token 倍数）与确认卡；`entryChoice` 回传选择
- 四个桥方法已从 `test/bridge-dead-allowlist.json` 移除（真接线，不是台账豁免）

## 四、已知限制（诚实清单，不粉饰）

1. **SSRF 的 30x 跳转**：Chromium 自动跟随重定向。已做「落地后 `page.url()` 复检 + 先 `about:blank` 清空页面」，覆盖「302 → IP 字面量」主路；**「302 → 解析为私网的域名」未覆盖**（需 Playwright `context.route` 逐请求拦截，属独立议题）。
2. **临时编制（temp）无法直接派活**：`teams:dispatch` 需要 `teamId`，而 temp 编制不落 `teams` 表。UI 上禁用「按这个执行」并给解释文案，**没有伪造 teamId、也没有静默降级**。
3. **工具面预热未实现**：设计要求「判定命中时把 `orchestrate_task` 提前放进工具面」，本轮**未做**。影响：小窗口模型仍需先 `activate_tools('collab')` 才拿得到编排工具 schema，此时靠确认卡「预拆 + 显式派活」这条更确定的路径兜底。
4. **`recallForPrompt` 无直接生产调用点**（T-07 残留）：预算语义已在生产路径上、双实现已消除，该函数保留为同一实现的文本出口。
5. **单 Agent 基线正确率无数据**：外部「>45% 才值得多 agent」的阈值无法直接套用（L0 规则层不依赖它，故不阻塞落地）。
6. **沙箱真机未验证**：Linux bwrap 与 macOS Seatbelt 在本机跑不了，3 条跳过项**不算通过**。
7. **Windows/Linux 未验证**：本轮全在 macOS darwin 上验。

## 五、设计决策（需用户知悉的 4 条）

| 决策 | 选择 | 理由 |
|---|---|---|
| 入口数量 | **4 → 2**（路径 A），按「一个产品、两个门」实现 | 刻意不引入任何入口专属数据结构 ⇒ 将来若像 Octomind 那样收回双面板，只需把助理 Tab 降级为侧栏底部一行，**不需数据迁移** |
| 「助理」命名 | **正文沿用「助理」**（未擅自改名） | 与 WorkBuddy 的「助理」（IM 远程控制）语义冲突，备选顺序 **团队 > 编制 > 数字团队 > 工作室**；改名牵动 `NavKey` / i18n / `sidebar.json`，**留给你裁决** |
| 军团归属 | **全局资产**（不改数据模型） | `teamStore` 的 `project_path` 可选、`listTeams` 不过滤 ⇒ 助理建好的军团在新建任务里立即可见，零改动 |
| 记忆预算 | `recallContents` 默认 4000 字符 | 是**上界**不是目标值；Worker 侧仍受 `topK=3` × 每条 `slice(0,200)` 约束 ≈600 字符，与「Top-3 注入」自洽 |
