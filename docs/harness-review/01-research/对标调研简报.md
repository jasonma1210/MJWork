## 一、简报概览

调研后的核心判断与用户设想**部分吻合、部分存在重要偏差**，需要在设计前先对齐：

**吻合的部分。** 「轻任务入口 + 重编排入口」是当前主流 Agent 产品的既定做法。Codex App 侧边栏就是 Chat + Project 两个一级入口；Claude 是 Chat + Cowork；Cursor 是编辑器/CLI/Cloud Agents 三面。WorkBuddy 桌面端侧边栏同样是一列一级入口：新建任务、助理、项目、专家·技能·连接器、定时任务、资料库、更多。【官方文档】

**三处必须先纠正的偏差。**

1. **「助理」这个名字在 WorkBuddy 里已被占用，且含义完全不同。** WorkBuddy 的「助理」= **IM 远程控制**（微信/企微/QQ/钉钉/飞书发消息 → 电脑执行 → 结果回推），不是「重编排 / 组建军团」入口。【官方文档】用户设想的「助理」在 WorkBuddy 语义里更接近「专家·技能·连接器」（专家团市场 + 我的专家创建）与「定时任务」的组合。
2. **「模型自己判断复杂度 → 自动升级为团队执行」目前没有可靠的公开硬判据。** 主流产品的做法是**模型内建判定 + 显式确认点**双轨：Codex 绝大多数智能水平下「只在用户明确要求时才派生 subagent」，只有 Ultra 级别才允许主动委派；Claude Code 文档明确写「Claude decides whether to spawn teammates based on the task」但**不公开任何数值阈值**；Devin 自动拆解任务但**先把方案给人批准**再启动团队。【官方文档】
3. **「拆成两个一级导航」本身正在被成熟产品收回。** Octomind 把侧边栏从 14 项拆成 Chat / Studio 两个面板后，**2026 年 9 月又合并回单个面板**，Studio 的能力收进侧边栏底部一个 Advanced 行。【社区】这是本简报中对架构设计最关键的一条反证。

**真正可迁移的资产共享机制**有两个正面样板：Claude 的 Chat ↔ Cowork 统一记忆层（但**本地运行的 Cowork 不使用记忆**），以及 Codex 的 **Thread automation**（定时任务唤醒的是同一条线程、保留对话上下文，而非另开会话）。【官方文档】

## 二、Q1：WorkBuddy 的产品形态（专家团 / 专家中心 / 定时任务 / 自动化分别是什么入口）

### 2.1 一级导航的真实结构

WorkBuddy 桌面端左侧导航栏分为四块：**顶部**（版本号、发现应用）、**一级入口**、**任务与空间**、**底部**（消息中心、多端协同、账号头像）。

一级入口共 7 个，官方导览原文如下【官方文档】：

| 入口 | 官方一句话说明 | 官方文档 |
|---|---|---|
| **新建任务** | 创建新任务，进入本地 AI 工作台 | [Task-Bar](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Task-Bar) |
| **助理** | **云端助理，可远程接任务、推送消息** | [Assistant](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Assistant) |
| **项目** | 按项目组织任务，支持团队协作 | [Project](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Project) |
| **专家·技能·连接器** | 调用专家、安装技能、连接外部服务 | [Expert-Center](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Expert-Center) |
| **定时任务** | 配置定时任务，让 WorkBuddy 按计划执行 | [Automation-Guide](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Automation-Guide) |
| **资料库** | 文档、表格、网页等资料的统一管理 | — |
| **更多** | 收纳低频入口（我的邮箱、腾讯文档、ima、乐享知识库、灵感、Genie BaaS） | — |

来源：[左侧导航栏 · WorkBuddy 官方文档](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Sidebar)

两个容易被忽略的官方约束：

- **「新建任务」是固定入口，不能拖动，也不能收进「更多」**。【官方文档】官方允许用户自定义一级菜单顺序（右键 → 自定义菜单栏），但新建任务被钉死。
- **自定义结果保存在当前设备上，暂不跨设备同步**。【官方文档】——即「入口偏好」被明确定义为**本地 UI 状态**，不是账号状态。这与 Octomind「偏好必须本地先存」的教训一致（见 §5.2）。

### 2.2 「助理」的真实定位 = IM 远程控制，不是重编排

官方原文：「助理是 WorkBuddy 的远程控制功能，让您可以通过手机上的即时通讯软件（微信、企业微信、QQ、钉钉、飞书）远程控制电脑上的 WorkBuddy 执行任务。」

官方对「助理」的本质描述是：**「助理就像一个遥控器」**——在手机上发一条消息 → 电脑上的 WorkBuddy 自动执行任务 → 结果回复到手机。【官方文档】

官方明确给出的**普通任务 vs 远程任务差异表**（这段是本次调研对 MJCode 最有价值的状态设计证据）：

| 对比项 | 普通任务 | 远程任务（助理） |
|---|---|---|
| 工作目录 | 自由指定 | **固定使用助理专属文件夹** |
| 新建对话 | 支持多个并行任务 | **仅一个会话，所有远程指令集中处理** |
| 上下文管理 | 可清空历史重新开始 | **保留完整对话历史，不可清空** |

来源：[助理(远程任务) · WorkBuddy 官方文档](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Assistant) ／ [腾讯云文档镜像](https://cloud.tencent.com/document/product/1831/134392)

官方还给出了**入口选择建议**：「本地操作优先使用主界面的普通任务；需要远程触发或统一查看记录时，再使用助理。」【官方文档】

> **【推断】对 MJCode 的意义**：用户设想的「助理 = 重编排 + 组建军团 + 类 bot 团队 + 定时任务」是一个**语义超载**的入口——它同时承载了「组织结构管理」「单次重任务执行」「常驻 bot」「周期调度」四类完全不同的用户心智。如果 MJCode 真的要把这四件事塞进一个一级导航「助理」，会直接踩 WorkBuddy 官方自己给出的那条警告（用普通任务还是助理，取决于你要做哪类事）。
>
> 更稳的拆法是让「助理」只承载**「组建与治理军团」**这一件事（对应 WorkBuddy 的「专家·技能·连接器」），把「定时任务」保留为独立一级入口（对应 WorkBuddy 的现状），把「类 bot 团队」作为军团的一种运行时形态而非独立入口。

### 2.3 专家中心 / 专家团：WorkBuddy 的「军团」实现

官方对两者做了明确的概念切分【官方文档】：

- **专家是「角色切换」机制** —— 以「人设 + 方法论 + 工具链」让 WorkBuddy 用特定领域专家身份执行任务。
- **专家团是「协作执行」机制** —— 专家团由多位专家分工协作，**由团长自动拆解、并行执行并整合交付**。

官方给的 Skill / 专家 / 专家团 三方对比表（原文）：

| 维度 | Skill | 专家（Agent 型） | 专家团（Team 型） |
|---|---|---|---|
| 组成关系 | 工具能力：让 AI 能做某件事 | AI 顾问：懂某个领域的 AI 角色 | AI 协作团队：自动拆解、并行执行、完整交付 |
| 怎么选 | 需要 AI 具备某种工具能力 | 有一个明确的单点问题 | 任务复杂，需要多角色配合 |

**入口路径**：左侧边栏「专家·技能·连接器」→ 默认进入「专家」页签 → 专家中心首页有推荐模块（按使用热度、新上架、编辑精选）→ 也可按行业分类浏览全部专家与专家团 → 点击卡片看详情 → 点「召唤专家/专家团」**进入对话界面**。

**专家团卡片展示的信息**：能力介绍、擅长领域、**团队成员**、任务示例，以及版本和使用量信息。（对比：专家卡片展示能力介绍、擅长领域、任务示例 + 使用量与开发者信息。）【官方文档】

**召唤后的机制**：专家团场景下「用自然语言描述任务后，专家团团长自动拆解、分配、执行并返回完整结果」——注意这与「新建任务」页的普通对话**是同一条对话流**，不是另一个专门的执行台。【官方文档】

**由 AI 帮用户构建团队成员（用户设想的「助理帮我建团」）在 WorkBuddy 里的对应实现**：
- 「我的专家」→ 右上角 → 「创建专家」/「创建专家团」→ **系统自动进入创建对话，由内置的专家管理工具引导您完成配置**；官方给出配置建议表（避免无指向名称、人设写「是谁+有什么背景」、擅长领域写清边界、提示词写工作流程与输出格式等）。【官方文档】
- 开放平台侧同构：「点击『我的专家』-『创建专家』/『创建专家团』→ 跳转进入对话，补全创建专家的提示词，开启创建。」【官方文档】[open.workbuddy.cn/docs/expert](https://open.workbuddy.cn/docs/expert)

> **【推断】** WorkBuddy 的做法是「**创建是对话中的一段流程，不是独立表单**」。这与用户设想中「助理页里用自然语言描述需求、AI 自动帮他构建团队成员」高度一致——可以判定该交互模式已有生产验证。

### 2.4 「切换专家会打断当前会话」——官方确认的状态割裂

官方原文：在**专家团会话**中通过搜索召唤其他专家时，会提示「**当前会话已使用专家团，切换其他专家需要开启新对话**」；确认后会先回到新对话态再完成召唤，**新专家不会回绑到当前专家团会话**。【官方文档】

同页还有两条相关设计：
- 对话中点击专家入口会展开「**最近使用**」下拉列表，支持**搜索**与**置顶**（置顶结果持久保存，下次打开排在列表前部）。
- 部分专家依赖 MCP / 连接器；服务未连接时，WorkBuddy 会在**输入框上方**展示连接引导卡片，点击连接后**自动继续当前任务**，无需重新发起对话。

> **【推断】** 「专家团会话 ↔ 普通专家会话」在 WorkBuddy 里是**互斥的会话绑定关系**，不是可叠加的。这是「轻入口 / 重入口共享资产」最具体的反面证据：编排形态一旦绑定到会话，会话就不能再自由换人。
>
> 对 MJCode 的直接含义：**「军团」应当是任务的一个可切换属性（类似 WorkBuddy 的「专家」选择器），而不是会话本身的不可逆状态**；如果 MJCode 把「军团」做成会话级绑定，用户每次换军团都要重开会话，4 层记忆的 session/project 连续性就会断裂。

### 2.5 定时任务：独立入口，且有三种来源 + 三种创建方式

**入口**：左侧导航栏「定时任务」→ 页面两个标签页：**定时任务**（查看管理全部，首次进入推荐模板）与**运行记录**（历次运行情况）。【官方文档】

**三种来源**【官方文档】：

| 来源 | 说明 | 差异 |
|---|---|---|
| 本地 | 电脑端创建，本机客户端执行 | 需电脑在线；可配工作空间与权限；可推企微 |
| 项目 | 项目中创建 | 需前往对应项目查看和管理；在定时任务页**只能查看**，编辑/暂停需回项目 |
| 云端 | 云端沙箱执行 | **无需电脑在线**；不需选工作空间和权限；不支持推企微；不能访问本机文件路径 |

**三种创建方式**【官方文档】：
- **手动新建** —— 需精确指定执行时间、权限和推送渠道。配置项：名称、提示词、**模型 / 专家 / 技能 / 连接器**（点 + 可添加）、工作空间、权限、重复（间隔/单次/每天/每周/每双周/每月/每年）、时间、有效期、消息推送到企业微信。
- **从任务新建** —— 「WorkBuddy 会回到首页，并在输入框中预填『帮我创建一个定时任务：』」，用户补一句需求即可。【官方文档】
- **从模版新建** —— 常见场景模板（每日 AI 新闻推送、每周工作周报、会议前准备等）自动填好名称、提示词和时间。

官方补充：**在普通对话中直接描述周期性需求（如「每天早上 8 点提醒我…」），WorkBuddy 同样会帮你创建定时任务。**【官方文档】

**关键 IA 设计——本地定时任务在侧边栏只占一个入口**（带定时任务图标），**历次运行不会各自生成一条任务**；未选工作空间时入口落在「任务」列表，选了则落在对应「空间」下。【官方文档】

**执行权限的两档**（官方标注「完全访问权限（推荐）」）：
- 完全访问权限：任务无人值守执行，工具调用无需逐次确认（开启时需再次确认）。
- 默认权限：敏感操作需要确认；**如果你不在电脑前，任务会停在等待确认状态**。

**失败原因诊断**：运行失败可查看原因和处理建议，例如连接器未授权、登录已失效、**电脑离线导致错过执行时间**。【官方文档】

### 2.6 定时任务与普通任务共享什么

- 定时任务配置里可以挂 **专家 / 技能 / 连接器 / 模型** —— 即定时任务复用与普通任务同一套资产目录。【官方文档】
- 推送渠道复用「助理」绑定的企业微信机器人（**仅支持 WebSocket 长连接，不支持 URL 回调**）。【官方文档】
- 运行页面可「点击某次运行进入对应会话，查看完整执行过程并继续对话」——**定时任务与普通会话是同一种对象**。【官方文档】

### 2.7 记忆：WorkBuddy 的形态与 MJCode 的「4 层记忆」对照

| 层级 | WorkBuddy 官方实现 | 证据 |
|---|---|---|
| 个人记忆 | 每晚整理当天会话，模型自动抽取事实信息/偏好习惯/人物关系/跟进事项，**仅本人可见**；可从「设置 - 记忆」查看、编辑、删除、一键关闭；注入系统提示词作为上下文 | [官方文档](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Memory) |
| 项目记忆 | 项目资料库以 **reference 形式**注入；项目指令拼入上下文；**个人记忆也拼入上下文** | [项目官方文档](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Project) |
| 团队记忆 | CLI 侧 `teamMemory.enabled`：项目记忆存在**项目目录**内供团队共享；`teamMemory.userId` 用 git user.name > 系统用户名自动识别 | [CLI Settings 官方文档](https://www.workbuddy.ai/docs/cli/settings) |
| 全局记忆 | CLI 侧存储路径 `~/.codebuddy/memories/global/`；另有个人模式 `~/.codebuddy/memories/{project-id}/`、团队模式 `{project}/.codebuddy/memories/@{user-id}/` | 同上 |
| 记忆类型分级 | Typed Memory 开启时使用 **4 种类型：user / feedback / project / reference** + YAML frontmatter | 同上 |
| 上下文检索 | 支持「上周做过什么」「之前聊过的 XX」这类会话历史检索 | 记忆官方文档 |

> **【推断】** WorkBuddy 的记忆分型（user / feedback / project / reference）+ 团队/个人/全局三种存储作用域，与 MJCode 设想的 session / project / global / team 四层记忆**结构上高度同构**。差别在于 WorkBuddy 把「session 层」做成了**会话历史检索**（可搜「上周做过什么」），而不是一个显式的 session memory 对象。MJCode 若要做显式 session 层，需要自己定义写入/淘汰规则——这是 WorkBuddy 没有公开的空白。
>
> 另外 WorkBuddy 的记忆是**每晚批量整理 + 手动可编辑**，不是实时抽取。这是隐私友好的取舍，但意味着「今天聊过但今晚没跑批」的上下文不会进记忆。

## 三、Q2：主流 Agent 产品的「新建任务」与「常驻团队/代理」如何分离

### 3.1 总览表

| 产品 | 轻任务入口 | 重编排 / 团队入口 | 是否显式「复杂度判定→自动升级」 | 自动派生的默认策略 |
|---|---|---|---|---|
| **Codex App** | 侧边栏 **Chat**（无需选项目文件夹即可启动的线程） | 侧边栏 **Project**（多线程 + worktree）+ **Automations** | ❌ 无显式升级机制；**Ultra 智能水平**才允许主动委派 | 绝大多数水平：**仅在用户明确要求时**派生 subagent |
| **Claude** | Chat（纯对话，不碰文件） | **Cowork**（可读写指定文件夹、完成多步任务）+ Claude Code | ❌ 无显式升级；Claude Code 内「Claude decides whether to spawn teammates」但**不公开阈值** | 由模型自行判断，且**以用户指令为默认** |
| **Cursor** | 编辑器 / CLI 内对话 | **Cloud Agents** + Subagents（可后台、可嵌套） | ⚠️ 「Agent 遇到复杂任务可自动启动 subagent」 | 内置 explore / browser 两个 subagent，**自动使用、无需配置** |
| **Devin** | 单个 session | **Managed Devins**（并行子 Devin）+ **Playbook** + **Automations/Schedule** | ⚠️ 有自动拆解，但**先给方案给人批准**再启动 | 自动拆解 + 人工确认点 |
| **WorkBuddy** | **新建任务**（Ask/Plan/Agent 三模式手动切换） | **专家团**（团长自动拆解）+ **定时任务** | ❌ **复杂度分流靠用户手动选模式** | 团长在专家团场景内自动拆解 |

### 3.3 Claude Code：Subagents 与 Agent Teams 是两套机制

**Subagents（官方文档）**：
- 通过 `/agents` 命令创建与管理；项目级 `.claude/agents/`、用户级 `~/.claude/agents/`，**项目级优先于用户级**；插件 agent 出现在同一 `/agents` 界面。
- frontmatter 字段：`name` / `description` / `tools` / `model`；**`description` 决定 Claude 何时该调用它**（社区惯例是写 "Use PROACTIVELY to…"、"MUST BE USED" 以触发自动委派）。
- 官方也支持 `--agents` CLI 参数做会话级临时定义（优先级：CLI < 用户级 < 项目级）。
- 官方内置三个 subagent：`explorer`（Haiku / 只读 / 探索）、`planner`（Sonnet / 只读+反思 / 规划）、`general-purpose`（Sonnet / 读写 / 复杂多步）。

**Agent Teams（官方文档，实验性）**：这是与 MJCode「军团」最接近的公开实现。

| 维度 | Subagents | Agent Teams |
|---|---|---|
| 上下文 | 独立 context window，结果返回调用方 | 每个队友独立 context window，完全独立 |
| 通信 | 结果返回主 agent | **队友之间直接互相发消息** |
| 协调 | 主 agent 管理全部工作 | **共享任务列表 + 自我认领** |
| 适用 | 聚焦、只要最终结果 | 需要讨论、互相挑战、自主协调 |
| Token | 较低 | 较高（每个队友是独立 Claude 实例） |

关键机制【官方文档】[Agent Teams](https://code.claude.com/docs/en/agent-teams)：
- **共享任务列表**三态：pending / in progress / completed；任务可依赖其他任务，依赖未完成的 pending 任务不可被认领；依赖在队友完成后**自动解除阻塞**；**文件锁**防止多个队友同时认领同一任务产生竞态。
- **两种分配**：lead 显式分配，或队友**自我认领**（完成后自动挑下一个未分配、未阻塞的任务）。
- **Plan approval**：在 lead 处于 plan mode 时创建的队友以只读 plan mode 工作，产计划后向 lead 发审批请求；**若未手动改过该队友的 permission mode，Claude Code 会在请求到达时自动批准**（无需 lead 审查），但队友的编辑与命令仍走权限提示。
- **显示模式**：in-process（默认，终端内 ↑↓ 选择队友）/ split panes（需 tmux 或 iTerm2 + `it2`）；`teammateMode` 可配 `auto` / `in-process` / `tmux` / `iterm2`。
- **规模建议**：「Start with 3-5 teammates for most workflows.」「If you have 15 independent tasks, 3 teammates is a good starting point.」「Three focused teammates often outperform five scattered ones.」
- **Token 成本**：「token usage scales with the number of active teammates」「Token costs scale linearly」；队友默认继承 lead 的 effort level。
- **硬限制**：一个 session 恰好一个 team；lead 终身固定不可转移；**不支持嵌套 team**（队友不能再派生队友）；in-process 队友不支持 `/resume` 恢复；任务状态可能滞后。

**「复杂度判定」在这份官方文档里的准确表述**（原文）：
> 「**Claude decides the number of teammates to spawn based on your task**, or you can specify exactly what you want.」
> 「Claude may sometimes use subagents instead of creating a team.」
> 「**Check that the task you gave Claude was complex enough to warrant a team. Claude decides whether to spawn teammates based on the task.**」
> 「Subagents appear in the same agent panel as teammates, so the panel alone doesn't confirm a team formed.」【官方文档】

> **【推断】** 官方确认「是否组队」是**模型判断**，但**没有公开任何数值阈值或评分算法**。同时官方承认 UI 侧不可观测（subagent 和 teammate 出现在同一个面板里）。这对 MJCode 是个明确的设计要求：**「自动升级为团队执行」必须配一个可见的状态提示**（例如「已升级为 3 人团队执行」+ 可一键降级回单 agent），否则用户既不知道发生了什么，也无法纠正误判。

### 3.4 Cursor：Subagents + Cloud Agents + 异步后台

官方文档要点【官方文档】[Subagents · Cursor](https://cursor.com/cn/docs/subagents)：
- 「**When Agent encounters a complex task, it can launch a subagent automatically.**」—— 自动派生是官方能力。

### 3.5 Devin：Managed Devins + Playbook + Automations

**Managed Devins（官方博客 + 官方文档）**：
- 「**Devin automatically breaks down large tasks and delegates to managed Devins when it makes sense.** You can also explicitly ask Devin to parallelize work.」【官方文档】
- 每个 managed Devin 是完整 Devin，跑在**独立 VM**、独立终端/浏览器/开发环境；各自有 session link，可单独检查或直接发消息。
- **主 session 充当 coordinator**：界定范围、分配、监控进度、解决冲突、汇编结果。
- 隔离理由（官方原话）：「when one agent tries to handle too many things in a single session, context accumulates, focus degrades, and the quality of each subtask suffers.」
- **协调器会学习**：Devin 可读取 managed Devin 的完整轨迹，理解什么有效/无效/卡在哪，用于改进下次拆解。「Over time, each managed Devin makes the next one more effective.」
- **★ 人工确认点（对 MJCode 极有参考价值）**：「**Devin analyzes your request and proposes the sessions for your approval before launching them.**」【官方文档】[Advanced Capabilities](https://docs.devin.ai/work-with-devin/advanced-capabilities)

**Playbook（可复用工作流）**：从成功的 session 生成可复用 playbook，或用反馈改进已有 playbook；playbook 可挂在定时 session 上，保证每次执行行为一致。【官方文档】

**Scheduled Sessions → Automations（官方文档）**：
- **旧的 Scheduled Sessions 是 legacy**，新的定时工作一律建成 **Automations + Schedule trigger**；支持 event-driven triggers（Slack / GitHub / Linear / webhooks）、条件、调用次数限制。
- 两种创建入口：从 Automations 页面新建（Schedule trigger：Every hour / Every day / Every week / Run once / Custom schedule），或从已有 session 选 Schedule Devin（prompt 预填）。
- 配置项含 **Agent 类型**（`devin` / `data_analyst` / `advanced`）、**Playbook**、Repositories、频率（可视化或自定义 cron）、一次性时间、邮件通知（Always / On failure only（默认）/ Never）、Slack 通知。
- **归属与状态**：默认归属创建者，可改为由他人承担以便通知正确；状态三态 Active / Paused / Error（连续失败）；一次性执行后自动禁用但保留历史以便审计。
- **跨运行记忆**：官方博客明确「Devin carries state between runs. It reads and writes its own notes across sessions」——每次运行在上一次基础上继续。【官方博客】[Devin can now Schedule Devins](http://www.cognition.ai/blog/devin-can-now-schedule-devins)

## 四、Q3：自动 DAG / 动态团队编排的主流做法，以及「复杂度判定」的公开判据

### 4.1 Anthropic 的 orchestrator-worker 与最直接可用的「复杂度 → 规模」映射

**架构（官方博客原文）**【官方博客】[How we built our multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system)：
- 模式为 **orchestrator-worker**：lead agent 协调，subagent 并行。
- lead agent 分析请求、制定策略、创建 subagent；**先把计划存进 Memory**（因为「if the context window exceeds 200,000 tokens it will be truncated and it is important to retain the plan」）。
- 每个 subagent 用**独立 context window** 独立检索，用 interleaved thinking 评估工具结果、精炼下一次搜索。
- 研究充分后单独交给 **CitationAgent** 处理引用定位——职责分离。

**★ 「Scale effort to query complexity」——本次调研找到的最直接可用的复杂度映射规则（原文）**：

> 「**Simple fact-finding requires just 1 agent with 3-10 tool calls, direct comparisons might need 2-4 subagents with 10-15 calls each, and complex research might use more than 10 subagents with clearly divided responsibilities.**」
> 「These explicit guidelines help the lead agent allocate resources efficiently and prevent overinvestment in simple queries, which was a common failure mode in our early versions.」

| 查询类型 | Agent 数 | 工具调用量 |
|---|---|---|
| 简单事实查询 | 1 个 agent | 3–10 次 |
| 直接比较 | 2–4 个 subagent | 每个 10–15 次 |
| 复杂研究 | >10 个 subagent，职责清晰划分 | — |

**并行化（原文）**：「the lead agent spins up **3-5 subagents** in parallel rather than serially; (2) the subagents use **3+ tools** in parallel.」→ 「These changes cut research time by **up to 90%** for complex queries.」

**成本（原文）**：「agents typically use about **4×** more tokens than chat interactions, and multi-agent systems use about **15×** more tokens than chats.」「token usage by itself explains **80%** of the variance」（BrowseComp）；多智能体（Opus 4 lead + Sonnet 4 subagent）比单智能体 Opus 4 高 **90.2%**。

**失败模式（原文）**：早期 agent 会「spawning 50 subagents for simple queries, scouring the web endlessly, and distracting each other with excessive updates」。

**明确的负面结论（原文，对 MJCode 尤其重要）**：
> 「most coding tasks involve fewer truly parallelizable tasks than research, and LLM agents are not yet great at coordinating and delegating to other agents in real time.」
> 「multi-agent systems excel at valuable tasks that involve heavy parallelization, information that exceeds single context windows, and interfacing with numerous complex tools.」

> **【推断】** 这条负面结论直接冲击用户设想中的「复杂分步任务自动启动自动 DAG」——**代码类任务恰恰是 Anthropic 明确说「多智能体通常不划算」的领域**。MJCode 是本地桌面 Agent + 代码开发为主，如果把「复杂分步」默认升级为多 agent DAG，很可能落入「-39% ~ -70%」的区间。**建议 MJCode 的自动升级条件不要用「任务是否复杂」，而用「子任务是否可真正并行、是否需要共享同一份可变状态」**（见 §4.3）。

### 4.2 Anthropic《Building Effective Agents》：workflow vs agents 的分野

【官方博客】[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) ／ [研究页](https://www.anthropic.com/research/building-effective-agents)

- 核心二分：**Workflows** = LLM 与工具按**预定义代码路径**编排；**Agents** = LLM **动态主导**自己的流程与工具使用。
- 五种 workflow pattern：**Prompt chaining / Routing / Parallelization / Orchestrator-workers / Evaluator-optimizer**。
- 官方忠告（原文）：「**you should consider adding complexity only when it demonstrably improves outcomes**」「Start with simple prompts, optimize them with comprehensive evaluation, and add multi-step agentic systems only when simpler solutions fall short.」
- 官方对框架的怀疑：「the most successful implementations weren't using complex frameworks or specialized libraries. Instead, they were building with simple, composable patterns.」
- Evaluator-optimizer 的适用前提：需要「LLM responses can be demonstrably improved when a human articulates their feedback」**且**「the LLM can provide such feedback」。

> **【推断】** 「evaluator-optimizer 需要两个条件同时成立」这个双条件，是 MJCode 判断「要不要上自动 DAG」的现成检验表：**模型能否自我批判 + 批判能否被证明有效**。两个都不成立时，多 agent 只是把错误并行放大。

### 4.3 ★ Google DeepMind + MIT《Towards a Science of Scaling Agent Systems》：目前最硬的量化判据

【官方博客（arXiv 摘要）】[arXiv:2512.08296](https://arxiv.org/abs/2512.08296) — Yubin Kim, Ken Gu, Chanwoo Park, Chunjong Park, Samuel Schmidgall, A. Ali Heydari, Yao Yan, Zhihan Zhang, Yuchen Zhuang, Yun Liu, Mark Malhotra, **Paul Pu Liang**, **Hae Won Park**, Yuzhe Yang, Xuhai Xu, **Yilun Du**, **Shwetak Patel**, **Tim Althoff**, **Daniel McDuff**, Xin Liu。v1 2025-12-09，v3 2026-04-08。**发表于 Nature Machine Intelligence**（社区转述，见 [Pebblous Blog](https://blog.pebblous.ai/blog/multi-agent-single-agent-threshold/en)）。

摘要原文要点：
- **260 configurations**，跨 **6 个 agentic benchmark**、**5 种架构**（Single-Agent + Independent / Centralized / Decentralized / Hybrid）、**3 个 LLM 家族**；工具、prompt、算力全部标准化以隔离架构效应。
- 量化模型跨验证 **R² = 0.373**（换成 task-grounded capability metric 为 **R² = 0.413**）。
- 相对单 agent 基线的性能变化区间：**可分解金融推理 +80.8%**；**顺序规划 -70.0%**。
- 三个稳定模式：
  1. **capability saturation effect** —— 「a coordination yields diminishing returns once single-agent baselines exceed certain performance」（单 agent 基线超过某阈值后，加 agent 收益递减甚至为负）。
  2. **tool-heavy tasks appear to incur multi-agent overhead**。
  3. **architectures without centralized verification tend to propagate errors more than those with centralized coordination**。
- 该框架在 **87% 的 held-out 配置**上能选出最优架构。

社区解读给出的具体阈值（**【社区】**，非论文原文，谨慎采用）：
- **45% 能力饱和阈值**：单 agent 正确率 > 45% 时，多 agent 通常不划算。【社区】[the-decoder](https://the-decoder.com/more-ai-agents-isnt-always-better-new-google-and-mit-study-finds)／[brainbyteslab](https://brainbyteslab.org/articles/when-multi-agent-helps-hurts)
- **工具密度阈值 ~16**：任务需要 16+ 个不同工具时，单 agent 或去中心化更优。【社区】
- **误差放大倍数**：独立 agent（无协调）放大 **17.2×**；中心化协调把放大压到 **4.4×**。【社区】
- **token 效率（每千 token 成功任务数）**：单 agent **67.7** > independent **42.4** > decentralized **23.9** > centralized **21.5** > hybrid **13.6**；hybrid 需要约 **6×** 的推理轮次；协调开销占 58%–515%。【社区】
- **顺序任务的精确退化**：PlanCraft 上单 agent 0.568 → independent 0.170（-70.0%）、centralized -50.4%、decentralized -41.4%、hybrid -39.0%。【社区】
- **可分解任务**：Finance-Agent 上单 agent 0.349 → centralized 0.631（**+80.9%**），decentralized +74.5%、hybrid +73.2%。【社区】
- 官方口径的建议：「**start with a single agent. Only switch to multi-agent systems when the task splits into independent pieces and single-agent success stays below 45 percent.**」【社区】

> ⚠️ **版本冲突说明**：[the-decoder](https://the-decoder.com/more-ai-agents-isnt-always-better-new-google-and-mit-study-finds) 写的是「180 controlled experiments」，而 arXiv v3 摘要写的是「**260 configurations**」。以 arXiv 摘要（v3）为准。

> **【推断】给 MJCode 的判据设计（可直接落成代码规则）**：
>
> | 触发条件 | 来源 | 建议动作 |
> |---|---|---|
> | 任务可拆成**互不依赖的子任务**（每步不改变后续步骤依赖的状态） | arXiv 摘要「relative performance ... architecture-task alignment determines collaborative success」 | ✅ 允许自动升级 |
> | 任务有**强顺序依赖**（改 A 的状态会改变 B 所需状态） | 同上（顺序规划 -70.0%） | ❌ **禁止**自动升级 |
> | 需要调用的**工具种类 ≥ 16** | 【社区】 | ⚠️ 降级为单 agent 或仅用 subagent 读多写少 |
> | 单 agent 自身在该类任务上的**基线正确率 > ~45%** | 【社区】 | ❌ 不升级（capability saturation） |
> | 需要**中心化验证**（汇总时需要交叉核对） | arXiv 摘要第 3 条 | ✅ 优先用 centralized/manager 拓扑 |
>
> 这四条里有三条是**可以在运行时用启发式直接算的**（并行度、工具数、依赖图深度），只有「基线正确率」需要离线评测积累。这意味着 MJCode 可以先落地一个**不依赖训练的结构化判据**，再逐步用自家 eval 数据校准。

### 4.4 AgentConductor：把「难度 → DAG 拓扑密度」做成显式建模

【官方博客（arXiv 摘要）】[AgentConductor: Topology Evolution for Multi-Agent Competition-Level Code Generation, arXiv:2602.17100](https://arxiv.org/abs/2602.17100) — 上海交通大学 i-WiN 团队 + 美团，ICML 投稿。

摘要原文要点：
- 现有 MAS 通过**预定义交互拓扑**协调专门 agent，**既不按任务难度调整拓扑密度，也不在单实例内用执行反馈迭代精修**，导致冗余通信与性能瓶颈。
- AgentConductor：以 **LLM-based orchestrator agent** 为核心，**端到端反馈驱动的动态交互拓扑生成**。
- 流程：对每个 query，orchestrator **推断 agent roles 与 task difficulty**，然后构建 **task-adapted, density-aware 的分层 DAG 拓扑**。
- 两个关键创新：**① 拓扑密度函数**（topological density function，刻画多 agent 交互的通信感知数学特征）；**② difficulty interval partitioning**（难度区间划分，避免过度剪枝，使每个难度级别都能精确测出拓扑密度上界，实现更细粒度控制）。
- 结果：3 个竞赛级 + 2 个基础代码数据集上 **pass@1 最高 +14.6%**，**密度降低 13%**，**token 成本降低 68%**。
- 实现细节（社区综述）：基座 Qwen-2.5-Instruct-3B；用 GPT-4o 生成 4,500 张交互图语料（分三个难度层）；拓扑用**人可读 YAML** 表示（每 step 一层，`ref` 表示依赖）；GRPO 多目标奖励 + 多轮轨迹（每轮生成拓扑 → 环境执行 → 反馈条件化下一轮生成）；支持**层内并行**（同 step 的 agent 并发）与**跨层连接**（可引用任意前序层输出）。

> **【推断】** 这条对本项目的价值不在算法本身（3B RL 训练的 orchestrator 成本过高），而在**它把「难度 → 团队规模」显式建模为「难度 → DAG 密度」**。MJCode 若要落自动 DAG，可以用**更轻的方式逼近同一目标**：
> - 难度分级不用 RL 训，用**结构化启发式**（§4.3 的四条）先分 3 档；
> - 密度上限用**难度区间划分**的方式预定义（例如入门级 ≤4 agent、面试级 ≤7、竞赛级 ≤10 —— 这是社区转述的具体数值，**【社区】**，来自 [搜狐报道](https://news.sohu.com/a/992577040_121718165)）；
> - 拓扑用**声明式 YAML/JSON** 表达，便于落盘、复盘和 eval。
>
> 同时，**「执行反馈驱动的拓扑再生成」**这一条是自动 DAG 相对于「一次性拆解」的真正增量，MJCode 若要做「自动 DAG」，建议至少支持**失败后重规划**，而不是只在开工前拆一次。

### 4.5 编排框架的能力边界（对比与教训）

| 框架 | 编排范式 | 状态管理 | 生产就绪度 | 关键教训 |
|---|---|---|---|---|
| **LangGraph** | 图状态机；`add_conditional_edges(source, path, path_map)`；conditional edges 即「由函数（通常 LLM 驱动）决定下一个节点」 | 内置 StateGraph + Checkpoint | ★★★★★ | 图节点数膨胀后不可调试（社区案例：14 节点 / 23 state field）；建议控制在 ~10 节点以内【社区】 |
| **CrewAI** | 角色流程；可开 hierarchical（manager agent 运行时决定委派） | 任务上下文 + 消息传递 | ★★★ | **hierarchical 模式产生非确定性 handoff**，同样输入不同运行路径不同 → 回归测试难做【社区】 |
| **AutoGen** | 对话驱动（GroupChat / 多轮辩论 / 沙箱执行） | 有限状态 | ★★★ | 学术与研究场景强，生产模式标准化不足【社区】 |
| **OpenAI Swarm** | 路由 + handoff（agent 之间交接） | 无状态 + 消息传递 | ★（实验性） | 官方明说 experimental、educational，**缺错误处理、持久化、可观测性，不应承载生产**【社区】 |
| **OpenAI Agents SDK**（Swarm 后继） | **Agents as tools**（manager 保持对最终回复的所有权）vs **Handoffs**（控制权转移给 specialist） | Runner + tracing | ★★★★ | 官方判据清晰，见下 |

**OpenAI Agents SDK 的官方选型判据（可直接照抄成 MJCode 的模式选择规则）**【官方文档】[Orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration)：

| 模式 | 用它的时机 | 发生什么 |
|---|---|---|
| **Handoffs** | specialist 应当**接管**对话的某一段工作 | 控制权转移给 specialist agent |
| **Agents as tools** | manager 应**始终掌控**，把 specialist 当作受限能力调用 | manager 保留对回复的所有权 |

官方还给了两条护栏：
- 「**Keep the routing surface legible**: Give each specialist a narrow job. Keep handoffDescription short and concrete. Split only when the next branch truly needs different instructions, tools, or policy.」
- 「**Start with one agent whenever you can. Add specialists only when they materially improve capability isolation, policy isolation, prompt clarity, or trace legibility. Splitting too early creates more prompts, more traces, and more approval surfaces without necessarily making the workflow better.**」

Python SDK 文档补充了 LLM 编排 vs code 编排的权衡【官方文档】[Agent Orchestration](https://openai.github.io/openai-agents-python/zh/multi_agent/)：code 编排可用 structured outputs 做分类后**用代码选下一个 agent**；LLM 编排适合开放式任务。

### 4.6 ★ 「复杂度判定」在工程上的可落地形态：triage / router

以上是「模型自己判断」的路线。工程上还有一条更可控的路线：**先用一个廉价的 triage 分类器做前置判定，再决定用哪条执行路径**。

**OpenAI 官方指南**【官方指南】[A Practical Guide to Building Agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf) ／ [网页版](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents)：
- 「**Our general recommendation is to maximize a single agent's capabilities first. More agents can provide intuitive separation of concepts, but can introduce additional complexity and overhead, so often a single agent with tools is sufficient.**」
- 两条具体的拆分参考标准（原文）：
  - **Complex logic** —— 「When prompts contain many conditional statements (multiple if-then-else branches), and prompt templates get difficult to scale, consider dividing each logical segment across separate agents.」
  - **Tool overload** —— 「**The issue isn't solely the number of tools, but their similarity or overlap. Some implementations successfully manage more than 15 well-defined, distinct tools while others struggle with fewer than 10 overlapping tools.**」
- 两种多 agent 形态：**Manager（agents as tools）** 与 **Decentralized（agents handing off to agents）**。

**triage 的具体 schema 设计（社区，实用价值高）**【社区】[n4n blog](https://n4n.ai/blog/using-a-cheap-model-to-triage-and-a-strong-model-to-answer)：
- 「**Don't ask the triage model to score 'difficulty 1-10'. Use discrete routing classes that map directly to model choices and system prompts. Discrete classes are easier to evaluate and harder for the model to hedge.**」
- 示例 schema：`{"route": "cheap" | "strong" | "escalate", "reason": "...", "confidence": 0.0-1.0}`
- triage 用**小模型**（分类不需要复杂推理），temperature=0.0，strict JSON 输出。

**路由可靠性的四种失败模式与缓解**【社区】[Taskade](https://www.taskade.com/blog/ai-agent-routing-patterns)：
- Misrouting → 置信度阈值 + 澄清问题
- Router bottleneck / SPOF → 冗余 router / 规则兜底
- Infinite handoff loop → **hop limit**
- Low-confidence dispatch → 视为 ambiguous，问一个问题；human handoff 是**合法路由目标**而非失败

> **【推断】** 给 MJCode 的建议是把「模型自己判断复杂度 → 自动启动 DAG」拆成**两层**：
>
> **第 1 层（确定性、可解释、零训练成本）**：triage 分类器用**离散类别**输出，直接对应「走哪条执行路径」：
> `simple_chat`（单 agent 对话）/ `multi_step_single`（单 agent 多步 + Plan 模式）/ `parallel_team`（自动 DAG）/ `manual_team`（提示用户去助理页组装）/ `scheduled`（引导到定时任务）。
> 判据用 §4.3 的结构化启发式（并行度、工具数、依赖深度），而不是让 LLM 打分。
>
> **第 2 层（模型内建）**：进入 `parallel_team` 后，由 orchestrator 像 Anthropic lead agent 那样做**运行时分解**（可参考 AgentConductor 的「失败后重规划」）。
>
> 这样既满足「模型自行判断」的产品直觉，又把**不可解释的部分压缩到最小**，并且每次升级都能在 eval 上量化。

## 五、Q4：产品 IA 双入口的踩坑案例与「共享同一套资产」的做法

### 5.1 ★ 最完整的正反两面复盘：Octomind「One Product, Two Front Doors」

【社区，但作者是产品团队自己的复盘，数据与 bug 描述具体】[octomind.run/blog/simple-mode-chat-studio](https://octomind.run/blog/simple-mode-chat-studio)（2026-08-12，2026-09 更新）

**拆分前的症状**：侧边栏 14 个入口、机器卡片 6 个 tab、新账号要先过 4 步 onboarding wizard 才能看到 agent 干活。原文：「That's the right panel if you signed up for a cloud machine. It's a wall if you signed up to get something done.」

**拆分依据来自用户自述数据**：注册时问用户来干什么，选项是 build software / research and write / automate routine work / just exploring —— **四分之三不是开发者，但四个人都被塞进了 machines dashboard**。

**★ 最重要的反直觉结论 —— 一年后他们把两个面板合并回去了**：
> 「**Update, September 2026: the two boards have since merged into one panel shaped like Chat. The Studio-only machinery now sits behind a single Advanced row at the foot of the sidebar; there is no board switch any more.**」

**命名原则（对 MJCode 直接可用）**：
> 「**A beginner mode is a setting that admits the product is too hard and offers to hide some of it. It ages badly: nobody self-identifies as a beginner, the docs fork, support has to ask which mode you're in before they can help, and every screenshot is wrong for half the userbase.**」
> 「The model that works is the one exchanges have used for years. **Coinbase has Coinbase and Coinbase Advanced. Binance has Convert, Spot and Futures.** Those aren't difficulty levels — they're **different front doors to the same exchange, with the same account and the same balance behind each.**」
> 「We call them Chat and Studio, **never Simple and Advanced**, because a name should describe **what you do there** rather than **rank the person doing it**."

**★ 四条不变量（保持「一个产品」而非「两个产品」的全部关键）**：
1. **「A board changes navigation, landing screen, and vocabulary. Nothing else.」** —— 同一批路由、同一批组件、同一份底层数据；代码里只是一个 layout 分支，不是 fork，不是第二套页面。「If we ever need to build a screen twice, the split was wrong.」
2. **「No asymmetric state.」** —— Chat 里创建的东西在 Studio 完全可见可编辑，反之亦然。「A conversation in Chat *is* a session in Studio — the same row in the same table. The moment one door can create something the other can't see, you own two products and twice the support load.」
3. **「A board is not a plan and not a permission.」** —— 免费账号可以进 Studio，高阶账号可以待在 Chat；**每个 deep link 在两边都能解析**。「Chat leaves things out of the *menu*; it never blocks a *route*. In practice this means every board-conditional in our code governs presentation only, and **one that ever gates a capability is a bug, not a feature**.」
4. **「One switch, always visible, no confirmation.」** —— 侧边栏底部，两个方向都能一键切换，无弹窗。「A switch you can't undo in one click isn't a preference, it's a trap — and a trap is exactly what makes people avoid trying the other door at all.」

**他们犯的两个 bug（都发生在新旧接缝处）**：
- **默认值在用户脚下翻转**：新账号默认进 Chat、老账号留在 Studio，判定规则是「已拥有 machine 就算老用户」。但 Chat 用户的**第一条消息就会创建一个 machine** —— 一句话之后他就被判定成老用户并被弹到 Studio。修法：「the derivation is computed once, the first time we see the account, and then stored. **A default that keeps re-deciding isn't a default.**」
- **偏好扛不过一次刷新**：偏好存在账号上（跨设备同步用），但部署窗口期 API 还不认这个字段，写入被拒，F5 后全被弹回原处。修法：本地先存，账号副本只做跨设备同步。「**A view preference that needs a server round-trip to survive F5 is broken by construction.**」

**第三个 bug（空状态 UX）**：「**unfetched means unknown, and 'unknown' should render nothing rather than a confident guess you take back a moment later.**」—— 未取回的列表不是空列表。

**Chat 里被移除的四样东西**（值得抄的减法）：machine（首条消息自动创建并按需唤醒/休眠）、model picker（`auto` 已按用途路由）、dashboard（Chat 落地页就是一行输入框）、wizard（Chat 里没有向导；引导延后到首次对话之后的「Next」区块）。

> **【推断】** 这条复盘对 MJCode 的意义可能超过其他所有材料：
> 1. **「两个一级导航」不是终局**。成熟团队试过一次、发现双份状态和不一致成本太高后合并了。MJCode 若做双入口，应从一开始就按「**一个产品、两个门**」而非「两个产品」设计，并预留**合并为一个面板 + 底部 Advanced 行**的收敛路径。
> 2. **命名必须是「按场景分的门」而非「按难度分的门」**。用户拟的「新建任务 / 助理」在语义上接近场景分（chat / orchestration），比「简易 / 高级」好；但「助理」在 WorkBuddy 语义里已被占用，建议另择名（例如「团队」「编制」「工作室」）。
> 3. **四条不变量应当直接变成 MJCode 的架构约束**（尤其第 2、3 条：两个入口必须读写**同一张任务表**，且任何「按入口分支」的代码只允许影响**呈现层**，绝不允许影响**能力可达性**）。
> 4. **首条消息即产生资产的场景**（MJCode 的「新建任务」会自动创建工作空间）会重演「默认项在用户脚下翻转」——需要把入口偏好**一次性计算并持久化**。

### 5.2 其他公开的踩坑证据

| 证据 | 具体症状 | 来源 |
|---|---|---|
| **WorkBuddy 官方**：专家团会话中召唤其他专家 → 提示「当前会话已使用专家团，切换其他专家需要开启新对话」，新专家不回绑 | 编排形态与会话强绑定，轻/重入口在会话层互斥 | 【官方文档】[Expert-Center](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Expert-Center) |

| **独立通道不能共享单一全局状态**：两个线程一个在等用户选方案、另一个已就绪，如果共用一个全局 busy/waiting/done，第二个请求会被饿死或第一个的需求消失 | 多入口共享状态时的**状态串扰** | 【社区】同上 |
| **空白对话框的认知过载**：blank chat box「无限能力、零引导」，把「从哪开始」的界定工作全丢回给用户 | 轻入口必须有 scaffolding | 【社区】[Generative Labs](https://www.generativelabs.com/insights/why-your-users-freeze)（建议：suggested prompts、context line、starter templates、guided first step） |

> **【推断】** 这批证据指向一个共同结论：**双入口的风险不在「导航分叉」，而在「状态分叉」**。Octomind 的四条不变量里，最难做到的是第 2 条（no asymmetric state）。MJCode 的 4 层记忆 + 军团 + 定时任务三套资产，恰恰是最容易在两个入口之间产生不对称的地方（轻入口看不到军团的运行态、重入口的任务不在轻入口的记忆里等）。

### 5.3 ★ 成熟产品怎么做「两个入口共享同一套资产」——两个正面样板

**样板 A：Claude 的统一记忆层（Chat ↔ Cowork）**【官方帮助中心】

官方帮助中心的现状表述：
- 「**When Cowork runs in the cloud, memory is shared between Chat and Claude Cowork**; Cowork sessions running locally on your computer do not use memory.」

- 但**记忆设置在任务开始时确定，之后无法更改**；可在单个聊天/任务上关闭记忆而不影响其他会话。

来源：[How does Claude's memory work? · Anthropic Help Center](https://support.anthropic.com/articles/11817273-how-does-claude-s-memory-work) ／ [中文版](https://support.claude.com/zh-CN/articles/11817273-使用-claude-的聊天搜索和记忆功能来建立之前的上下文:F使用Claude) ／ [Claude's memory works everywhere](https://claude.com/resources/articles/claudes-memory-works-everywhere-and-you-decide-whats-in-it)

> **【推断】** Claude 的做法是**单一记忆实体 + 按执行环境决定是否挂载**。这给 MJCode 一个更精确的模型：**记忆是资产，不是入口的属性**。两个入口读写同一个记忆库；差别只在「本地会话是否注入记忆」这种执行环境开关，而不是「这个入口有没有记忆」。
>
> 而「**本地 Cowork 不用记忆**」正是一个警示：MJCode 是**本地桌面端**，如果照抄「记忆只在云端共享」，MJCode 的本地轻入口与本地重入口之间就会天然割裂。**MJCode 作为本地应用，两个入口必须共享同一份本地记忆存储**——这恰恰是 MJCode 相对 WorkBuddy/Claude 的结构性优势。

**样板 B：Codex 的 Thread automation**【官方文档】

「**线程自动化 (Thread automations) 可以在预定时间唤醒同一个线程，同时保留对话上下文**」——定时任务不新建会话，而是**唤醒既有线程**，保留全部对话上下文。

来源：[Codex 更新日志（中文镜像）](https://developers.openai.ac.cn/codex/changelog?type=general) ／ [Automations 文档](https://developers.openai.ac.cn/codex/app/automations)

对照 Devin 的做法也是同一思路：**定时 session 继承原 session 的 prompt**（选 Session → Schedule Devin，prompt 预填）；而且 **Devin 在多次运行之间携带状态**（读写真实笔记，每次运行在上次基础上继续）。【官方文档】[Scheduled Sessions](https://docs.devin.ai/product-guides/scheduled-sessions) ／【官方博客】[Devin can now Schedule Devins](http://www.cognition.ai/blog/devin-can-now-schedule-devins)

> **【推断】** MJCode 的「定时任务」如果做成「新建一个任务并按 cron 重复执行」，就会丢掉全部历史上下文；应做成**「把当前这条任务变成可被唤醒的定时任务」**——这与用户设想里「助理承担定时任务」是一致的，但**资产归属应落在任务上、入口只在助理页做统一管理视图**。

**样板 C（反面但有价值）：WorkBuddy 的定时任务是独立入口**【官方文档】。它把定时任务做成第 5 个一级入口，代价是用户要理解「本地 / 项目 / 云端」三种来源和两套权限模型，且项目来源的任务在定时任务页**只能查看、不能编辑**。相比之下 Codex / Devin 的做法都是**「定时是任务的一个属性 / 一种触发器」**，不是独立产品域。

> **【推断】** MJCode 应把「定时任务」做成**触发器**而非**入口**：同一条任务可被 `@daily` 之类的方式触发；助理页提供一个**跨任务的定时视图**用于管理，但**任务的编辑权始终在任务本身**。这样既满足「助理统一查看与治理」的产品意图，又避免「两个入口都能改同一份资产」的非对称状态。

## 六、给 MJCode 架构设计的可迁移结论（【推断】汇总）

> 以下全部是本简报的分析结论，非外部事实。请架构师逐条判断后再采纳。

### 6.1 关于「两个入口」

1. **先决定是不是两个一级导航。** Octomind 试过并合并了回来。MJCode 的两个入口如果**读写同一张任务表**、且用户可一键来回，规模不大时可以考虑先做「同一页面内的两个 tab / 两个落地态」，成熟后再升为一级导航。WorkBuddy 把 7 个入口全平铺在一列也说明**一级导航不是稀缺资源，语义清晰才是**。
2. **命名按场景分，不按难度分。** 「新建任务 / 助理」中的「助理」与 WorkBuddy 的 IM 远程控制同名，会在用户心智里造成冲突（WorkBuddy 用户可能已有肌肉记忆）。建议避开「助理」，或至少在文案里明确区分「助理（远程）」与新入口。
3. **四条不变量直接写进架构约束**：
   - 两个入口共享**同一批路由、组件、底层数据**；
   - **无非对称状态**：任一入口创建的军团/任务/定时计划，在另一入口完全可见可编辑；
   - **入口分支只允许影响呈现层**，绝不影响能力可达性（deep link 在两边都能解析）；
   - 入口切换**一键、可逆、无确认弹窗**。
4. **首条消息会创建资产的场景要防「默认项翻转」**：入口偏好**一次性计算并持久化**到本地，账号副本只做跨设备同步；本地存储必须能扛住 API 失败（F5 不丢）。
5. **「未取回 = 未知」**：空列表渲染不得用「有把握的猜测」，未加载时渲染空而不是先画一个错的东西。

### 6.2 关于「自动 DAG」

6. **判定不要用「任务复杂度」，要用「任务结构」。** Anthropic 明确说多数编码任务不适合多 agent；Google/MIT 说顺序依赖任务会退化 39%–70%。**建议判定项**：子任务是否可真正并行 / 是否共享可变状态 / 工具种类数 / 是否需要中心化验证汇总。
7. **先离散分级、再连续打分。** 用 triage 分类器输出离散路由类别（`simple_chat` / `multi_step_single` / `parallel_team` / `manual_team` / `scheduled`），不要让模型打「难度 1-10」分。
8. **分层判定**：结构化启发式（第 1 层）→ orchestrator 运行时分解（第 2 层）→ 失败后重规划（AgentConductor 的增量）。
9. **必须有可见的升级/降级提示。** Claude Code 官方承认 subagent 和 teammate 混在同一面板里无法区分 —— MJCode 不应重复这个错误。至少要有「已升级为 N 人团队执行」+「降级为单 agent 执行」的可点入口。
10. **团队规模参考值**：Anthropic「3-5 个 subagent 并行」/「多数工作流从 3-5 个队友起步」/「3 个专注队友常胜过 5 个散的」；AgentConductor 社区转述的难度上限 4/7/10。**先取 3-5 作为硬上限**。
11. **预留中心化验证环节**（Google/MIT：无中心化验证的拓扑误差传播更严重）。汇总阶段应有交叉核对角色，而不是直接拼接。
12. **成本护栏**：Anthropic 的 4×/15× token 倍数、Codex 的 max_threads=6 / max_depth=1、Claude 的线性增长。MJCode 应在 UI 上明示「本次升级为团队执行，token 消耗约为单 agent 的 N 倍」，并提供上限。

### 6.3 关于「资产共享（记忆 / 军团 / 定时任务）」

13. **记忆是资产，不是入口的属性。** 学 Claude 的统一记忆层，但要修正它「本地 Cowork 不用记忆」的缺陷 —— **MJCode 是本地应用，两个入口必须共享同一份本地记忆存储**。
14. **军团是任务的属性，不是会话的不可逆状态。** WorkBuddy 的「切换专家需开启新对话」是反面教材。
15. **定时任务 = 触发器 + 统一管理视图**，不是独立产品域。任务编辑权归任务；助理页提供跨任务的定时列表与治理。这与 Codex Thread automation、Devin Schedule trigger 一致。
16. **军团资产必须能被轻入口引用。** 用户设想中「助理产出的军团沉淀下来，可直接被新建任务当作自己的军团使用」——这要求**军团是可持久化、可枚举、可被任务引用的独立实体**，而不是「助理会话里的临时状态」。建议数据结构上：军团（id、成员列表、角色、模型、提示词、工具权限、来源：预置/AI生成/用户手搭）+ 任务引用（task_id → legion_id），并保留**引用而非拷贝**，避免资产漂移。
17. **AI 自动构建团队的交互形态已有生产验证**：WorkBuddy 用「创建对话 + 内置管理工具引导」而非表单。建议 MJCode 的「助理」沿用这个形态。
18. **预置「数字员工」目录 + 用户自建军团并存**，需要明确的**来源标记与优先级**（预置的只读、自建的优先），WorkBuddy 的「分享给成员的专家是副本，不影响你的配置」是可直接参考的处理方式。
