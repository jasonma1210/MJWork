**缺陷**：

- **T-01（P1）｜分层召回模式下 `topK` 被完全丢弃**
  - 根因链：`main/memory/recall.js:32-34` 的 `recall()` 在 `scopes` 分支调用 `_recallLayered({space, query, scopes, conversationId, teamId, agentId, domains, minScore, scan})` —— **参数表里没有 `topK`**；而 `_recallLayered` 内部只用 `LAYER_QUOTA[sc]` 配额 + 末尾 `slice(0, RECALL_TOP_K_MAX=50)`，**全程不看 `topK`**。
  - 复现（实测，见 §4.1 探针 A/B/C/F）：`recallContents({spaceId, scopes:['session','project','global'], topK:1})` 返回 **5 条**（项目层配额 3 + 全局层配额 2），而非 1 条；同一 space 走**旧单空间路径** `topK:1` 则正确返回 1 条 → 差异定位在分层分支。
  - 影响面：
    - **Worker 注入路径**（`main.js:1578-1586`）：注释明写「Top-3 注入」，`topK: 3` **实际无效**；实取上限 = session 2 + project 3 + global 2 = **7 条**，每条再 `slice(0, 200)` → 注入体积上限 ≈ 1400 字符，是声明预算（600）的 **2.3 倍**。
    - `main/ipc/localData.js:496` `topK: limit || 7` 同样无效；当前渲染层恰好传 `limit:7` ≡ 分层配额之和 7，**巧合相等**，故主对话路径**暂时没暴雷**——但 `limit` 语义已失真（传 3 仍回 7）。
  - 修法方向：`_recallLayered` 接收 `topK` 并在收集阶段做全局截断（或把每层配额与全局 topK 取 `min`）；同时修正 `main.js:1559` 的「Top-3」注释与实际口径。
- **T-07（P3）｜`recallForPrompt` 生产代码零调用**
  - `main/memory/recall.js:121` 定义了「预算内记忆文本块 + 可信度过滤」的装配函数，但**全仓 `main/` `renderer/` `agent-core/` 内无任何调用点**，仅 `test/memory-scope.test.mjs:117` 调用。
  - 影响：这条「预算装配」路径在生产中不存在；实际生产路径（`recallContents` + 前缀 + `wrapUntrusted`）**没有 `budgetChars` 预算约束**（Worker 路径靠每条 `slice(0,200)` 兜，主对话路径**无任何长度上限**）。建议：要么接入，要么删除并把其语义合并到 `recallContents`，避免「有测试就以为有功能」。
- **T-06（P2）｜记忆写入队列的 flush 触发点过窄**
  - `main/ipc/localData.js` 的 `flushMemoryQueue()` 只在 `local:memories/add`(L481) 与 `local:memories/list`(L494) 内被调用。若用户「记忆子系统未就绪时」写入一条记忆，此后**再未触发任何记忆类 IPC**，该条**永远不落库**且进程退出即丢（模块注释承认「队列只在进程存活期有效」）。
  - 影响面：启动早期（DB 初始化慢于首次渲染）的记忆写入，存在静默丢失窗口。修法方向：把 flush 挂到 `memoryManager` 就绪回调 / 定时 tick / 任一 IPC 入口的统一前置。

**缺陷**：

- **T-02（P1）｜SSRF 单一判据在 browser 通道被旁路**
  - 根因链：项目纪律（`main/webTools.js:38` 注释原文）是「**所有出网都经过这里的协议/私网检查，不允许旁路**」；`main/ssrfGuard.js` 的 `isPrivateHost` + `guardedLookup`（resolve-then-validate，堵 DNS rebinding）是唯一判据。
  - 但：`main/browserTools.js:147` 的 `browser_navigate` 把 `args.url` **原样透传**给浏览器子进程；子进程 `main/browserProcess/childEntry.js:79-87` 的 `assertHttpUrl` **只校验协议是 http/https**，**不做私网判定**。
  - 可达面：`http://127.0.0.1:<port>/`（含本应用自身监听端口，如 `scheduledEventServer` 的 47615）、`http://169.254.169.254/latest/meta-data/`（云实例元数据）、`http://[::1]/`、以及 `10.x / 172.16-31.x / 192.168.x` 私网段；随后 `browser_extract` 可把页面正文读回模型。
  - **不对称性**：更危险的通道无防护，**更弱的通道有防护** —— `web_fetch`（L2，auto-safe 档即自动放行）走 `isPrivateHost`；`browser_navigate`（L3）反而没有。
  - 复现路径：`browser_navigate({url:'http://169.254.169.254/latest/meta-data/iam/security-credentials/'})` → `assertHttpUrl` 通过 → `page.goto` 发出 → `browser_extract` 回读。
  - 影响面：L3 档 + 可规则豁免（规则粒度为完整 URL 前缀，模型换一个前缀即需重新授权，但用户对「浏览器」类工具容易形成习惯性放行）。
  - 修法方向：在 `assertHttpUrl` 之后追加 `isPrivateHost(parsed.hostname)` 判定（复用 `main/ssrfGuard.js`，不新建第二份实现）；重定向亦需复检（`page.goto` 的 30x 由 Chromium 自动跟随）。
  - 未验证项：Chromium 在本项目 sandbox profile 下对 `169.254.169.254` 的实际可达性**未做真机验证**（需真实云/元数据环境或本地 mock metadata server 才能证）。本条的**代码路径缺口本身已由源码坐实**；「实际可取到什么内容」依赖运行环境。

### 2.6 工具面 / 模型能力 —— 数字自洽，一处「机器可读事实」残缺

- `modelWindows.js` 的 `HOST_RULES` 覆盖了 `PROVIDER_KINDS` 的**全部 8 种 kind**（ollama / anthropic-api / bedrock / deepseek / qwen / gemini / mimo / openai），**无遗漏**；`KIND_ALIASES` 额外覆盖 `azure / anthropic / aws / dashscope / aliyun / google / xiaomi` 等 providerId 形态。
- 窗口表的四态语义正确：精确命中（`table`）/ 同族推断（`family`，**标 confirmed:false**，避免前缀匹配把未见过版本高估）/ 默认 32768（`default`）/ Ollama 探测（`ollama-probe`，表内禁写死窗口）。
- 渲染层有同表 TS 版 `renderer/src/lib/modelWindows.ts`，由 `test/model-windows-parity.test.mjs` 深度比对防漂移 → 跨层契约有门禁。

**缺陷**：

- **T-04（P2）｜`ENGINE_BUILTIN_TOOL_NAMES` / `ENGINE_BUILTIN_TOOLS` 清单残缺，且其一致性门禁在清单清空时仍绿**
  - 事实：`agent-core/index.js:2525` `export const ENGINE_BUILTIN_TOOL_NAMES = ['todo_write'];`；`main/engineProcess/registry.js:69` `const ENGINE_BUILTIN_TOOLS = ['todo_write'];`。
  - 但同为「引擎内部、无宿主通道」的工具还有 **`spawn_subagent`** 与 **`deep_research`**（实测：这两个在 `TOOL_HANDLER_NAMES` 中映射为 `undefined`，即无宿主通道；见探针输出「缺通道 = [ 'deep_research→undefined', 'spawn_subagent→undefined' ]」）。
  - 根因链：`test/tool-registration-matrix.test.mjs:80-92` 的三条 A-08 断言：
    - 「引擎内置工具标注与引擎导出完全一致」→ 比的是 `[] === []`，**空集自洽**；
    - 「不得同时登记宿主通道」→ `[].every(...)` **恒真**；
    - 「矩阵的引擎内部清单必须包含全部引擎内置工具」→ `fromEngine.every(n => ENGINE_INTERNAL_TOOLS.includes(n))`，**只查 engine ⊆ matrix，不查 matrix ⊆ engine**（矩阵自己的 `ENGINE_INTERNAL_TOOLS` 是硬编码的 3 条，恰好比 registry 全）。
  - **变异验证 M5（实测）**：把两侧清单**双双清空** ⇒ `tool-registration-matrix.test.mjs` 仍 **162/162 通过，EXIT=0**，三条 A-08 全部 PASS。→ **确证的空过假闸**。
  - 影响面：这条门禁宣称「引擎内置工具必须是**机器可读事实**」，但事实本身已残缺（漏 2 个）且门禁对残缺/清空**完全无感**。当前 `ENGINE_BUILTIN_TOOLS` 仅被该测试消费（未进生产逻辑），故运行时暂无直接故障；但它是「声明式事实表」，一旦将来被用于路由/审批判据，残缺会直接变成漏判。
  - 修法方向：① 把 `spawn_subagent` / `deep_research` 补进两侧清单；② A-08 改为**双向相等**（`engine ⊆ registry` 且 `registry ⊆ engine`），并加一条「清单非空」下界断言；③ ③ 环节对引擎内部工具的判据 `new RegExp("['\"`]tool['\"`]").test(indexSrc)` 应收紧为「引擎内确有 `case`/分支处理」，避免名字出现在数组或注释里即算通过。

### 2.7 跨层契约 —— 同改机制存在，但接线断言有「文本化」倾向

- 有门禁保障的跨层契约：`shared/roleClamp.mjs` ↔ `main/approvalPolicy.js`（`test/role-clamp-parity.test.mjs`）、`main/modelWindows.js` ↔ `renderer/src/lib/modelWindows.ts`（`test/model-windows-parity.test.mjs`）、`agent-core` ↔ `main/engineProcess/registry.js`（工具登记矩阵）、i18n 双语键集（`i18n-modcheck` 43 模块）。
- **缺陷**：
  - **T-03（P1）｜`local:memories/list` 的「走分层模式」只有源码文本门禁，行为断了门禁仍报绿**
    - 变异验证 M3（实测）：把 `main/ipc/localData.js` 里的 `scopes: [...SCOPES],` **整行挪进注释**（实际调用不再传 scopes，仅在注释里保留字面量）⇒ `test/memory-file-channel.test.mjs` **52/52 通过，EXIT=0**，其中「✅ D1 local:memories/list 走分层模式（scopes + conversationId）」照样判绿。
    - 根因链：`test/memory-file-channel.test.mjs:232-234` 的判据是 `/local:memories\/list/.test(localData) && /scopes:\s*\[\.\.\.SCOPES\]/.test(localData) && /conversationId:\s*conversationId \|\| null/.test(localData)` —— **纯源码文本正则**，不执行被测行为、也不限定这三段必须出现在 `local:memories/list` 处理器体内。
    - 行为后果（若真发生）：主对话的 3 层召回退化为单空间全量 → 每层配额失效、跨层去重失效、**别的会话的 session 记忆会漏进当前对话**（正是 B-11 缺陷在主对话路径上的形态）。
    - 修法方向：改为**行为断言**——直接调用 `ipcHandlers['local:memories/list']`（`test/memory.test.js:256` 已有这种调用范式），写入「A 会话 session + B 会话 session + project + global」四条，用不同 `conversationId` 各调一次，断言「返回条数 ≤ 分层配额之和」且「不含 B 会话记忆」。源码正则可保留为补充，但不能作为唯一判据。
  - **T-05（P2）｜`worker-memory-layering.test.mjs` 不覆盖「每层配额」——尽管其文件头明确声称要锁这个缺陷**
    - 该套件头部（`test/worker-memory-layering.test.mjs:9`）写明：「① **每层配额（session 2 / project 3 / global 2）不生效**，Top-3 被 tier 高的项目条目占满」是它要锁的缺陷之一。
    - **变异验证 M4（实测）**：把 `main/memory/index.js` 的 `LAYER_QUOTA` 全部放大到 50（等价「每层配额完全失效」）⇒ `worker-memory-layering.test.mjs` **10/10 通过，EXIT=0**。
    - 对照：同一次变异下 `memory-scope.test.mjs` **红**（`AssertionError: 会话层配额=50`）、`memory-team.test.mjs` **红**（`团队层召回配额 3 / 50 !== 3`）⇒ 配额本身有别的门禁覆盖，**唯独这个号称锁它的套件是空的**。
    - 根因：该套件的 10 条断言里没有一条检查「每层取几条」；`③` 段全是**源码正则**（`/scopes[,:]/`、`/conversationId:\s*groupThreadId/`），能抓住「scopes 没传」（M2 已证），抓不住「配额数值被改」。
    - 修法方向：加行为断言——向 project 层写入 ≥5 条、global 层写入 ≥3 条，断言 `recallContents({scopes:['project','global']})` 返回 **恰好 3+2=5 条**（配额封顶），且分层路径返回条数 ≤ `Σ LAYER_QUOTA`。
  - **T-10（P3）｜工具链陷阱：macOS `grep` 是 BRE，`\|` 不生效**
    - 现象：本轮多次用 `grep -rn "a\|b" ...` 检索**恒返回空**，而用 `grep -E "a|b"` 或 Grep 工具则正常。
    - 根因：BSD grep（macOS 默认）不支持 `\|` 交替，需 `-E`（ERE）或 `grep -e a -e b`。
    - 影响面：所有**用 `\|` 写检索条件的核查脚本**都会得到「无匹配」的假阴性结论 —— 本轮若只用 Bash grep，会误判「SSRF/writeGuard 无调用点」「renderer 无记忆相关代码」等。本项目 `desktop/test/` 下的门禁脚本未见使用 `\|`（已抽查涉及文件），故**不影响现有门禁**；但对后续核查者与文档是必须写明的陷阱。
