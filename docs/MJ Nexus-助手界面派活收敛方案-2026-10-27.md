# 助手界面派活收敛方案（2026-10-27）

> 状态：**已执行**（方案 A + 落点统一，S1–S3 全部落地，见 §9 执行记录）
> 触发：用户实测反馈 ——「发布任务」进去发布任务，没有任何和助手有关的事情；助手目录与 AI 建团又各自为战，都有发布。

---

## 1. 结论（先看这三句）

1. **病根不是哪个 Tab 做得不好，是「派活」这个动作被拆成了三条互不相认的路径。** 三个 Tab 按「功能」切，而用户是带着「我要让谁干什么」这一个意图进来的。
2. **「发布任务」名不副实**：它只能选军团或"交给系统"，**从头到尾没有助手这个主体**。名字承诺的是「发起一切任务」，能力只覆盖「团队/自动」。
3. 建议：**把派活收敛成一个面板**（主体 × 运行方式 × 目标 × 落点），三个 Tab 降级为「资源面」（目录 / 建团），**「发布任务」这个 Tab 取消**。

---

## 2. 现状：三条并行路径（如实记录）

| 入口 | 能选的主体 | 走哪条通道 | 任务落到哪 | 额外副作用 |
|---|---|---|---|---|
| 助手目录 → 提交任务 | 单个助手 | `mjcode:recruit-expert` | **新会话**（`setActiveThread(null)` 强制） | 会新建会话、注入 `sessionExtras.expert` |
| 发布任务 → 确认 | 军团 / 空=自动 | `teams:dispatch` / `onAutoRun` | **当前会话**（无会话则新建） | 自动分支会再建会话，与目录不一致 |
| AI 建团 → 确认 | 无 | `teams:recruit` / `teams:addCustomMember` | **只写编制表**（工作室里才能看到） | 不产生任何任务 |

### 2.1 四个具体缺陷

| # | 缺陷 | 用户会怎么撞上 |
|---|---|---|
| D1 | 「发布任务」没有助手主体 | 想派给"技术文档工程师"，进发布任务后只能选军团 → 只能退出去目录重来 |
| D2 | 落点不一致 | 目录派活凭空多一个会话；发布任务挂在当前会话。同一个"派活"，行为不同 |
| D3 | 三处都有「提交/确认/采纳」 | 不知道哪个才是"真正发出去"的那一下；建团那个甚至不发任务 |
| D4 | 建团完成后无去处 | 确认落库后只在工作室的军团编制里能看到，用户不知道下一步该干嘛 |

### 2.2 根因

- **按功能分 Tab，而不是按意图分**：目录=浏览、发布=发起、建团=编排。用户的心智里只有一个动作：**派活**。
- **"谁来干"被拆在三个地方**：助手在 Tab1、团队在 Tab2、新建团队在 Tab3，三者互不知道对方存在。
- **"怎么跑"混进了"派给谁"**：定时任务这一维（什么时候跑）塞进了发布任务，助手路径完全没有这一维 —— 于是两条路径的能力集天然不同，无法合并。

---

## 3. 统一模型

一次派活 = **执行主体** × **运行方式** × **目标** × **落点**

| 维度 | 取值 | 现状归属 |
|---|---|---|
| 执行主体 | ① 指定助手 ② 指定团队 ③ 交给系统判定 | 被拆在 Tab1 / Tab2 / 判定器 |
| 运行方式 | ① 立即 ② 定时（repeat + 有效期 + 时间） | 只在 Tab2 有 |
| 目标 | 一段文字 | 三处各有一个输入框 |
| 落点 | 当前会话 / 新会话 | 两条路径规则冲突（D2） |

> 判定器**不新增实现**：主体的第 ③ 态沿用设计文档 §12 的现有判定器（按任务结构判、由确认点问），
> 只是把它的入口从"发布任务里不选军团"提升为派活面板的正规选项。

## 5. 推荐方案 A 的详细设计

### 5.1 Tab 结构

```
助手
├─ 派活（默认）    ← 唯一提交出口
│   ├─ 主体：[助手 ▾] [团队 ▾] [交给系统]     三态分段，默认「交给系统」
│   ├─ 目标：单行/多行输入（Ctrl/⌘+Enter 提交）
│   ├─ 运行：立即 / 定时（定时才展开 repeat/有效期/时间 与执行计划预览）
│   ├─ 提交 → 一个通道，按主体分派
│   └─ 看板：本会话已发起的编排与进度（从发布任务搬来）
├─ 目录            ← 浏览/发现，无提交按钮
│   └─ 点卡片 → 选中详情 + 「以此派活」→ 切到派活并预选该助手
└─ 建团            ← 只产出编制，不派活
    └─ 确认落库 → 「用这个团队派活」→ 切到派活并预选该团队
```

### 5.2 主体三态的语义（必须写清，否则又会变成三套实现）

| 主体 | 提交后发生什么 | 通道 |
|---|---|---|
| 指定助手 | 目标 + 该助手的 rolePreset 一起进会话；主进程取「助手声明 vs 用户设置」中更严格的安全策略 | 现有 `recruit-expert` / `enable-expert` |
| 指定团队 | 确定性派活给该团队，挂着当前会话 | 现有 `teams:dispatch` |
| 交给系统 | 目标交回主链路，由判定器决定单助手/团队 | 现有 `onAutoRun` |

三者**共用同一个提交函数**，只有"分派"这一步按主体分支 —— 这是把 D1/D3 一起解决的关键。

### 5.3 落点统一规则（解决 D2）

**一律落当前会话；没有会话才新建。** 三种主体同一条规则。

- 影响：目录派活不再强制开新会话。
- 需要打通一件事：**在当前会话换/设助手**。现在 `recruit-expert` 的第一句是 `setActiveThread(null)`，
  这是"必须新会话"的硬编码来源。改为：有当前会话时直接注入 `enable-expert`（覆盖该会话的 expert），
  并在面板上提示「本会话的助手将从 X 换成 Y」；无会话时保持现有开新会话行为。
- 这是本方案唯一的实现风险点，见 §7。

### 5.4 「发布任务」的能力如何安置（一个都不能丢）

| 原能力 | 去处 |
|---|---|
| 目标输入 | 派活面板的输入框 |
| 军团下拉 | 派活面板「主体：团队」 |
| 不选军团 = 自动构建 | 派活面板「主体：交给系统」（从"不选"变成**显式选项**，语义更清楚） |
| 复杂任务 / 定时任务 | 派活面板「运行：立即 / 定时」 |
| 定时三控件 + 计划预览 | 定时分支内联展开（代码原样搬，`schedulePresets` 复用） |
| 运行看板 | 派活面板下方常驻 |

### 5.5 空态与错误（按仓库既有纪律）

- 没有助手/团队可选 ⇒ 主体选择器禁用该项并给一句「去目录挑一个 / 去建团建一个」的引导，**不显示空下拉**。
- 目标为空 ⇒ 提交禁用（不是点了才报错）。
- 主体是"指定助手"但该助手 runtime 不可用 ⇒ 提交禁用 + 原因（沿用目录页的 runtime 判定，不猜 ready）。
- 定时任务缺必填 ⇒ 就地标注，不弹窗。

### 9.3 与方案的三处偏差（都是有意的）

| 位置 | 方案原写 | 实际做法 | 理由 |
|---|---|---|---|
| R1 当前会话注入 | 「S3 前先写一条探针」 | 派活面板在**提交前**再查一次 `ecosystemEmployeeRuntime` | 目录给出的 runtime 裁决可能已经过期（用户先在目录看过、几分钟后才提交）；探针是一次性验证，二次校验是每次提交都生效 |
| R3 定时 × 助手 | 「明确分工，不做第二套列表」 | **直接禁掉这个组合**，并在面板里给出带边框的原因文案 | 定时通道没有确认点，也带不上 `rolePreset` —— 放行等于造出一条「点了没反应」的路径。禁掉比假装支持诚实 |
| D4 建团无去处 | 「加回填」 | 同上，且回填后**自动切回派活 Tab** | 回填若不切 Tab，用户会以为没生效 |
