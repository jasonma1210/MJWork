## 1. Token 流水（`quota_consumptions`）— 支撑 M2

### 1.1 完整表结构

来源：`desktop/main/db/index.js:452-465`

```sql
CREATE TABLE IF NOT EXISTS quota_consumptions (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  project_id TEXT NOT NULL,
  run_id     TEXT,
  task_id    TEXT,
  member_id  TEXT,
  tokens     INTEGER NOT NULL,
  source     TEXT NOT NULL DEFAULT 'round',
  created_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_quota_consumptions_window
  ON quota_consumptions(project_id, created_at);
CREATE INDEX IF NOT EXISTS idx_quota_consumptions_member
  ON quota_consumptions(project_id, member_id, created_at);
```

### 1.2 逐字段语义核验

| 字段 | 结论 | 证据 |
|---|---|---|
| `id` | ✅ **单调递增唯一主键（AUTOINCREMENT）** | `db/index.js:453`。文档 §7.3 要求「若没有稳定唯一且单调递增的 consumption id，先迁移补齐」——**无需迁移**，可直接用作 asOf 高水位与 keyset 分页末位键 |
| `project_id` | ✅ NOT NULL，写入前 `String().trim()` 且空串拒绝 | `quotaLedger.js:245-247`（`!pid` 时 `return 0`） |
| `run_id` / `task_id` | ⚠️ 可空；空串被归一为 `null` | `quotaLedger.js:251`（`String(runId \|\| '') \|\| null`） |
| `member_id` | ⚠️ **语义未证实为真人成员**。写入方传的是 AI 成员/角色标识，不是真人账号 | 见 §1.4 |
| `tokens` | ✅ 整数，`Math.max(0, Math.trunc())`，**≤0 不落库** | `quotaLedger.js:246-247` |
| `source` | ✅ 默认 `'round'`，`recordRound` 显式写 `'round'`；**无枚举约束**（列是 TEXT，无 CHECK） | `quotaLedger.js:241,248-252` |
| `created_at` | ✅ **毫秒时间戳（INTEGER，Unix ms）**；支持调用方传入 `at`，缺省 `Date.now()` | `quotaLedger.js:252`（`safeNum(at, Date.now())`）；`ensureBucket` 同口径用 `Date.now()`（`quotaLedger.js:48`） |

**对文档 §7.6 的回应**：文档列出的四项「实施前验证」中，`created_at` 单位（毫秒）、`tokens` 口径（单条=单次消耗）、`id` 单调性三项已证实。

### 1.3 一次 Agent round 写几条

- 写入入口唯一：`QuotaLedger.recordRound()`（`quotaLedger.js:240`）→ `_insert()`。
- ⚠️ **未证实**：本次未追踪到 `recordRound` 的全部调用点计数，不能断言「一次 round = 一条」。
  **结论**：Ledger UI 与 CSV 一律表述为「记录数 / 流水条数」，**禁止表述为「任务数」**（文档 §7.6 明确要求）。

### 1.4 `member_id` 语义 — 文档要求的敏感点

文档 §7.2 要求：「`member_id` 在语义核实前显示为通用成员标识或不作为筛选项，不能直接改称『真人成员』或『助手』」。

核验状态：**语义仍未证实**。现有写入路径来自 AI 执行链（`projectStore`/`workerPool`/`agentRunner` 均引用 ledger），
没有发现真人成员写入点。

**M2 落地约束（必须遵守）**：
1. Ledger 明细表该列 label 用中性文案「成员标识」，i18n key 不带 `human`/`assistant` 语义；
2. `member_id` **不作为默认筛选项**，仅当 `ledger:capabilities` 明确声明该维度已核实后才开放；
3. 空值显示「未记录」，不回填 `default` 或其他占位。

### 1.5 金额数据

- ✅ 全仓无 `price / cost / billing / invoice / currency` 产品实现（与文档 §3.1 一致）。
- **约束**：Ledger 侧禁止出现 ¥ / $ / 成本 / 账单 / 估算金额。

## 2. SQLite 驱动与 FTS5 — **M3 硬阻塞**

### 2.1 实测结果

```
驱动 A：sql.js（WASM）
  sqlite_version: 3.49.1
  fts5            → FAIL — no such module: fts5
  fts5+unicode61  → FAIL — no such module: fts5
  fts5+porter     → FAIL — no such module: fts5
  fts4            → OK

驱动 B：better-sqlite3（原生）
  本机 node_modules 存在，但 node 侧加载失败（Electron ABI 未重编）
```

### 2.2 为什么这是阻塞项

`main/db/sqljsDb.js:1-4` 写明：sql.js 是 **P1 降级驱动**，因为 better-sqlite3 在 Electron 内
`new Database()` 处 SIGSEGV，「不可捕获」。也就是说：

- **生产实际跑的很可能就是 sql.js** → 没有 FTS5；
- **测试跑的一定是 sql.js**（`test/taskStore.test.js:17` 明写绕过原生模块）→ 没有 FTS5。

文档 §8.5 的「先验证 FTS5 是否启用」得到的是**反面答案**。

### 2.3 对 M3 的处置建议（本轮不实施，仅登记）

| 方案 | 评估 |
|---|---|
| 依赖 FTS5 | ❌ 不可行：生产/测试双缺 |
| 用 FTS4（sql.js 可用） | ⚠️ 可行但中文分词仍不理想，且 better-sqlite3 侧需同步验证 |
| **自建 bigram 倒排表**（普通表 + 索引） | ✅ 推荐：两侧驱动一致、可控、可测；与文档「中文采用经过测试的 bigram 或等效分词方案」一致 |
| 纯 LIKE 全表扫描 | ❌ 文档明令禁止「静默换成低质量全表扫描」 |

**登记为 M3 前置阻塞（BLOCKER-KB-01）**，M3 启动前必须先选定方案并记录基准。

## 3. 数字员工目录 — 支撑 M1（助手目录）

### 3.1 数据源

- 文件：`ecosystem/digital-employees.json`
- **实测条数：51**（与文档 §3.1 一致，但按文档要求**不在 UI 固化为固定数字**）
- 单条字段（实测 16 个）：
  `id, name, title_cn, category, industry, soc_code, mission, core_skills, tools,
   default_model_tier, approval_policy, sandbox_policy, system_prompt, starter_skills,
   typical_outputs, market_signal`
- 样例：`id = "de-software-engineer"`，`name = "software-engineer"`

### 3.2 IPC 真名（**文档写错了，此处订正**）

| 文档写法 | 实际通道 | 位置 |
|---|---|---|
| `ecosystem:employee-catalog` | ❌ 不存在 → 实际是 **`ecosystem:employees`** | `main/ipc/ecosystem.js:384` |
| `ecosystem:employee-runtime` | ❌ 不存在 → 实际是 **`ecosystem:employeeRuntime`** | `main/ipc/ecosystem.js:415` |

preload 暴露名（`main/preload.js:130,134`）：`ecosystemEmployees` / `ecosystemEmployeeRuntime`。

### 3.3 通道契约

```
ecosystem:employees({ category? })
  → { ok: true,  employees: Employee[] }
  → { ok: false, error: string, employees: [] }

ecosystem:employeeRuntime({ id })
  → { ok: true,  rolePreset: { systemPrompt, toolNames, ... , approvalMode, sandboxPolicy } }
  → { ok: false, error: string }   // 员工不存在时 error = `数字员工不存在：${id}`
```

- 目录已含**内置 + 用户自定义合并**（同 id 用户版本优先）— `ipc/ecosystem.js:387`、`employeeCatalog.js:55-64`。
- `rolePreset` 由 `ecosystem.js:164 buildEmployeeRuntimePreset(emp)` 组装（纯函数，可单测）。

### 3.4 ID 映射稳定性 — 文档 §5.5 的【实施前验证】

| 映射 | 结论 |
|---|---|
| 目录 `employee.id` → `ecosystem:employeeRuntime({id})` | ✅ 同一字面量直传（`ipc/ecosystem.js:419` 用 `e.id === id` 精确匹配） |
| 目录 `employee.id` → rolePreset | ✅ 一一对应，`buildEmployeeRuntimePreset` 无外部状态 |
| rolePreset → `agent:run` 的 `rolePreset` 参数 | ✅ 已有既有链路（`ecosystem.js:13-14` 注明「用此角色开会话 → sessionExtras.expert.runtime → useAgentRun 每轮携带 rolePreset → agent:run」） |

**结论**：目录到执行链的 ID 映射稳定，**不需要**在卡片层做名称硬编码匹配。

### 3.5 审批/沙箱归一（安全边界，不可绕过）

`main/ecosystem.js:20-35`：

- 审批档枚举：`['on-request','auto-safe','always','safe-auto','trusted']`，非法值 → **`on-request`（最保守）**
- 沙箱策略：`['read-only','workspace-write','full-access']`，非法值 → **`workspace-write`**
- 模型档位：`['fast','standard','reasoning']`，非法值 → **`standard`**

且 `ecosystem.js:11-12` 明确：角色只能**收紧**权限，绝不能放宽（fail-closed）。
这直接兑现文档 §5.4 的「角色预设不是安全豁免」。
