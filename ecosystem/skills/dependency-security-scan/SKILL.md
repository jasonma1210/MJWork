## 角色
你负责把漏洞告警转化为真正可执行的升级决策，而不是简单转发告警列表。

## 输入
- 项目依赖清单（lock 文件优先）
- 漏洞扫描结果或允许执行扫描
- 项目的运行环境与兼容性约束

## 方法步骤
1. 收集依赖：使用包管理器的依赖树命令获取完整清单，包含间接依赖。
2. 扫描已知漏洞，记录：受影响包、版本范围、修复版本、CVE 编号与严重度。
3. 判断可达性：在代码库中检索该包是否被引入、危险 API 是否被调用。不可达的直接依赖也要标注，因为构建期与运行期环境不同。
4. 定级：
   - 实际可达且高危 → 立即修复
   - 可达但低危 → 排期修复
   - 不可达 → 记录并设定复检日期
5. 制定修复方案，优先级：
   - 直接升级到修复版本
   - 升级到最新小版本（最小变更）
   - 无法升级时使用 resolutions/overrides 强制版本
   - 实在无法修复时给出配置层缓解措施并记录风险接受
6. 升级后执行完整测试并验证构建产物。

## 输出格式
### 依赖概览（直接依赖数 | 间接依赖数 | 运行时与构建时）
### 高危项（包 | 当前版本 | 修复版本 | 可达性 | 处理方案）
### 中低危项汇总
### 不可修复项与缓解措施
### 验证结果
### SBOM 归档建议

### 注意事项
- 不要盲目执行全量大版本升级，跨主版本升级必须单独验证。
- 锁定文件必须一起更新，避免本地与 CI 版本不一致。
- 强制覆盖版本要写清理由，后续版本发布后需移除。
- 不要在日志或报告中打印完整内部地址。

### 失败处理
- 扫描工具不可用：给出对应命令与替代方案，标注未完成项。
- 修复引入回归：回退到安全版本 + 缓解配置，并记录风险接受人。

## 默认参数与校准（工程基线）

> 以下为**工程通行口径**（具名标准 / 公开的大厂实践），**不是本企业实测值**。首次落地按此开工；跑满 1–2 个迭代周期后用实测数据替换，替换过程按下方"校准规则"留痕。与公司内部规范冲突，以内部规范为准。

### 门槛基线
| 项 | 基线 | 依据 |
|---|---|---|
| 修复 SLA | 严重（CVSS ≥9.0 或已在野利用）≤48 小时、高危 ≤7 天、中危 ≤30 天 | 业界通行做法（漏洞修复 SLA） |
| 复检 | 不可达/不可修复项 ≤90 天复检并记录风险接受人 | NIST SSDF |
| 一致性 | lock 文件与清单同步更新，CI 校验两者一致 | 业界通行做法 |
| SBOM | 每个发布版本归档一份 | NIST SSDF（SBOM 实践） |
| 变更隔离 | 跨主版本升级单独验证，不与安全补丁同 PR | 业界通行做法 |

### 校准规则
- CVSS 只作初筛，最终按可达性定级：实际可达升一级，确认不可达降一级并写明检索依据。
- SLA 起算点必须写明，默认从扫描发现起算；若从公告发布起算，需记录公告时间。
- 复检周期按依赖活跃度调：停止维护的包从 90 天缩到 30 天。
- 高危告警数 >50 条时按"可达 + 运行时依赖"排序分批修，不做一次性全量升级。
